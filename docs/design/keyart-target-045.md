# 045 — 목표 화면(키아트 ③)으로 게임 화면 만들기: 전체 계획과 1단계 설계

- 상태: **1단계 구현 완료, 사용자 확인 대기.** 설계 검토 PASS(r005). 구현 검토는 r001~r003 FAIL 뒤 r004 동작 PASS, r007 스펙 PASS. 결과는 [검증 기록](../reviews/keyart-target-045-review.md). 2단계는 시작 전에 이 문서에 하위 절을 추가하고 다시 검토한다
- 규모: **L2**
  - 런타임 코드 변경: 맵 모드 3D 캐릭터 표시, 배치 데이터 검사(`DSBlockoutData.Validate`), 가림 처리와 셰이더 호환, 전역 표시값 컴포넌트.
  - 새 배치 데이터(소스 원본)와 Tripo 자산 연결도 포함한다.
  - 이 문서는 전체 계획(0~4단계)과 **1단계 구현 기준**을 정한다. 2~4단계는 계획만 적고, 각 단계를 시작하기 전에 이 문서에 하위 절을 추가해 다시 검토한다.
- 검증 기록과 단계별 놓친 것: [045 검증 기록](../reviews/keyart-target-045-review.md). 작업이 끝나면 놓친 것의 워크플로우 갱신 후보를 반영한다.
- 크레딧: 0·1단계는 0. 2단계부터는 단계마다 사용자 승인을 받는다(현재 잔액 755, 2026-11-02 10:4x 조회).

## 사용자 요구와 확정 사항 (2026-11-02)

- 목표 화면은 [041 r002 키아트 `day.png`](../reviews/keyart-041-review.md)(③)다. "키아트 3번대로 작업을 할려고해", "캐릭터까지 모두 넣어야 하니깐 계획을 정리해줘".

  2. 캐릭터와 몬스터를 키아트 스타일(위에서 읽히는 단순한 블록형)로 다시 디자인한다. 일반형 몬스터(초록 덩어리)는 042 모델이 키아트와 거의 같아 그대로 쓴다.

  4. 크레딧은 단계마다 승인한다.
- 키아트 ③을 목표로 하므로 [043 팔레트·셰이더](lowpoly-shader-043.md)(③에서 뽑은 색)도 채택한다. 계획 보고에서 이렇게 해석한다고 밝혔고, 사용자가 추천안을 승인했다.

## 1단계 설계 (구현 기준 후보)

### 1-A. 새 배치 판본

- 생성 도구 `Tools/Proto/keyart_layout_045.py`(새로 만듦)가 018 r001 `Layout.json`을 읽어 새 판본을 만든다. 같은 입력이면 같은 결과가 나와야 한다.
  - 생성 도구는 `output/keyart-target-045/r00N/Layout045.json`(Git 제외)에만 쓰고, SHA와 검사 결과를 `layout-report.json`에 남긴다. Assets에는 쓰지 않는다(검토 D7).
  - 빌드 도구(1-B)가 이 파일의 SHA를 보고서와 대조한 뒤 `Assets/DeadSurvivor/Scenes/Proto045/Layout045.json`으로 복사한다. 폴더는 빌드 도구가 만들고 소유한다.
  - 018 원본과 007 소스는 바꾸지 않는다.
  - 출력: `package` `MAP-KEYART-045`, `revision` `r001`, `source_layout_sha256` = 018 r001 `Layout.json` SHA.
- **OB-001~006의 다각형만 키아트 구조물로 바꾼다.** 나머지 58개, 경계, 원점, 배율, 높이 집합, id 체계는 그대로 둔다. 장애물 64개 제약도 유지된다.

  | id | 새 모양 | 높이 |
  |---|---|---|
  | OB-001 | R1 돌 테두리+덤불(원형) | 16 |
  | OB-002 | R2 반원 테두리+덤불 | 16 |
  | OB-003 | R3 호형 테두리+덤불 | 16 |
  | OB-004 | R4 원형 | 16 |
  | OB-005 | R5 원형 | 16 |
  | OB-006 | P 연못 | 16 |

  - 위치는 키아트 화면을 시작 위치의 카메라 한 화면(px 266.7×183)에 대응시켜 투영한다. 초안은 `output/keyart-target-045/r001/layout-proposal-r001.png`이고, 투영식은 생성 도구에 둔다.
  - 구조물 속은 통과할 수 없다. 키아트에서도 테두리 안은 덤불이 차지한다.
- `rock_center_px`는 새 OB-001의 중심으로 바꾼다. `RockHolder`는 `Bind` 때도 이 위치로 옮겨진다(`DSMapSession.cs:61`). 045에서 바위 시각물은 비우지만 참조는 유지한다(`Bind` 검사 대상).
- RT-003은 대표 구역 안 구간만 키아트 자갈길 위치(시작 위치 남쪽 약 50~60px)로 옮긴다. 시각 기준일 뿐 전투에는 영향이 없다.
- `DSBlockoutData.Validate`는 허용 판본 목록 {(`MAP-BLOCKOUT-018`,`r001`), (`MAP-KEYART-045`,`r001`)}을 받도록 바꾼다. 나머지 검사는 두 판본 모두에 그대로 적용한다. 기존 장면은 018을 계속 쓰므로 동작이 바뀌지 않는다.
- 생성 도구가 확인할 것:
  - 다각형 유효성(`DSMapGeometry`와 같은 규칙을 Python으로 미리 검사하고, Unity `Validate`/`Bind`로 최종 확인)
  - 장애물끼리, 그리고 경계와 겹치지 않음
  - 대표 구역 안에 있음
- **시작·진형 검사(검토 D6):** 중심점만 안전해서는 부족하다. 편대 슬롯이 새 장애물 안에 들어가면 출전이 거부된다(`DSMapSession.cs:111`, `DSMapPartyRules`). Unity 편집기에서 다음을 확인한다.
  - 시작 위치에서 1~4인 진형의 모든 슬롯이 유효함(실제 출전 1·4인)
  - 새 구조물 가까이에서 진형 전환과 부활이 됨(구조물마다 1곳)
  - 적 반경 18과 25로 각 구조물을 돌아 파티에 접근하는 경로가 있음(`DSMapNavigation`). 구조물 사이 통로가 막히지 않았는지 본다
- **북쪽 절반:** 대표 구역의 북쪽 절반(px y100..208)에는 장애물이 없어진다. 1단계에서는 열린 풀밭과 시각 전용 장식으로 둔다. 장애물을 더 두려면 64개 제약을 바꿔야 하므로 직접 플레이한 뒤 정한다.
- **연못의 한계:** 연못도 장애물이라 화살과 시야를 막는다. 막지 않는 물 종류는 데이터 형식 변경이 필요하므로 후속으로 둔다.

### 1-B. 새 본편 장면 `Proto045_Main`

- 빌드 도구 `Tools/Proto/build_keyart_045.cs`(새로 만듦)는 043·044 빌드 스크립트와 같은 안전장치를 쓴다.
  - 실행 전: Play 중이 아님, 미저장 장면 없음, 대상 폴더가 없음(있으면 덮어쓰지 않고 실패).
  - 장면 구성과 선택을 저장했다가 복구한다.
  - 실패하면 이 도구가 만든 파일 목록에 있는 것만 지운다. 입력 배치 파일(`output/…/Layout045.json`)과 다른 폴더는 지우지 않는다(검토 D7).
- 순서:
  1. Map043 장면(043 재질·지면·자갈길·조명)을 `Scenes/Proto045/Proto045_Main.unity`로 복사한다.
  2. `CombatEnabled`=1로 설정한다.
  3. 1-A 결과를 SHA 대조 뒤 장면 폴더로 복사하고, `DSMapSession`의 Layout을 그 파일로, `ExpectedDataSha`를 그 SHA로 바꾼다. 같은 GameObject에 `DSMapPresentation`을 붙인다.

### 1-C. 가림 처리 호환 (043 셰이더 수정, 검토 D2·D3 반영)

- `DSLowPolyPalette.shader`에 두 속성을 CBUFFER 안에 추가한다.
  - `_BaseColor`: 기본 흰색, 알파 1
  - `_DitherFade`: 기본 0
- `_DitherFade`가 1이고 `_BaseColor` 알파가 1보다 작을 때만 화면 디더 패턴으로 픽셀을 버린다. 모든 패스(Forward, ShadowCaster, DepthOnly, DepthNormals)에 적용한다. 블렌드 패스는 추가하지 않는다.
- 043 공용 재질 5개는 `_DitherFade`=0으로 둔다. 그래서 Map043은 가려져도 지금처럼 보인다(D2). 045는 장면 전용 재질 사본에서만 1로 켠다.
- **`DSMapVisibility` 수정(D3):**
  - 재질에 `_DitherFade` 속성이 있고 값이 1이면 투명 큐 이동, URP 투명 키워드, ShadowCaster 끄기를 하지 않는다. 불투명(AlphaTest) 큐에 남겨 깊이·노멀 선행 패스와 SSAO에 그대로 포함되게 하고, `_BaseColor` 알파만 바꾼다.
  - 그 밖의 재질(URP Lit 등 기존 장면 전부)은 지금 코드 그대로 처리한다.
  - 직교 카메라의 가림 판정은 아래 1-D의 카메라 거리 변경 때문에 바뀌어야 한다. `DSMapPresentation`이 있을 때만 "카메라 앞 방향과 평행한 광선"으로 판정한다. 기존 장면은 지금처럼 카메라 위치에서 쏜 광선을 쓴다.
- 확인할 것:
  - 시간에 따라 바뀌는 효과(바람·구름)를 0으로 고정한 Map043 캡처가 수정 전과 픽셀 단위로 같음

  - 디더 상태의 그림자 모양을 캡처로 확인. ShadowCaster의 디더 좌표는 그림자 맵 기준이라 화면 디더와 다르게 보일 수 있다(r002 지적)

### 1-E. 맵 모드 3D 캐릭터 표시

- **조건부 적용(검토 D1 반영):**
  - `DSMapSession`에는 필드를 추가하지 않는다. `DSMapSession`은 전체 스냅샷 계약이 필드 이름과 형식을 정확히 검사하기 때문이다(`DSGame.MapSnapshot.cs:84, 212`). 필드 하나만 추가해도 `FULL_SNAPSHOT_FIELD_COVERAGE`로 실패한다.
  - 대신 같은 GameObject에 새 컴포넌트 `DSMapPresentation`(Runtime, 새로 만듦)을 둔다. 필드는 `Actors`(새 ScriptableObject `DSMapActorSet`), `CameraDistance`다. `DSMapActorSet`은 영웅 id → 프리팹, 몬스터 id → 프리팹, 목표 화면 높이, 체력바 높이, 가림 기준 높이를 담는다.
  - 표시 전용 값이라 시뮬레이션 상태와 `BindingKey`에 넣지 않는다.
  - 조회 시점: `DSWorld`가 처음 맵을 그릴 때 `MapSession.GetComponent<DSMapPresentation>()`로 한 번 찾고, 그 판에서는 고정한다.
  - **이 컴포넌트가 없으면 지금 스프라이트 경로와 카메라 거리 150을 그대로 쓴다.** Map023·038·043·044와 검사 장면, 고정 사례(`IsFixture`)의 동작이 바뀌지 않는다. 고정 사례에서는 컴포넌트가 있어도 쓰지 않는다.
- 새 컴포넌트 `DSMapActorViews`(Runtime, 새로 만듦)는 `DSWorld`가 `DSMapPresentation.Actors`가 있을 때만 만든다. `RenderMap`의 캐릭터 그리기 두 곳(`:28`, `:42`)이 이 컴포넌트를 호출한다.
- **수명 계약(검토 D4 반영):**
  - 키는 id나 팀 순번이 아니라 **개체 참조**다(`Enemy`, `Survivor` 객체, 둘 다 class). 재출전하면 적 id가 다시 시작하고 같은 순번에 다른 영웅이 올 수 있어서다.
  - 매 프레임 이번에 그린 개체만 표시하고, 나머지 표시는 풀로 돌려보낸다(표시와 반환을 한 번에 처리).
  - 로비 등 그리기를 건너뛰는 상태(`DSWorld.Map.cs:25`)에서는 모두 숨긴다. 기존 스프라이트 루트처럼 같은 `visible` 값으로 켜고 끈다.
  - 판이 바뀌면(재출전, 패배, 로비 복귀) 모두 반환한다. `DSWorld`가 파괴될 때 정리한다.
  - 모델은 표시 루트 아래 **시각 전용 자식**에 둔다. 회전·통통 튀기·기울기는 자식에만 준다. Animator는 `applyRootMotion=false`다.
  - **표시 코드는 시뮬레이션 상태(`Enemy`, `Survivor`, `DSGame` 필드)를 읽기만 하고 쓰지 않는다.**
  - 재사용 순간(풀에서 꺼낼 때, 한 프레임 이동이 화면 절반보다 클 때 = 재배치)에는 이전 위치·방향 기준을 초기화한다.
- 영웅(최대 4명):
  - 모델은 지금 스프라이트와 같은 방식(`g.Def(c).id`, `DSWorld.Map.cs:42`)으로 고른다. 같은 개체라도 id가 바뀌면 다시 묶는다.
  - Animator로 대기와 달리기를 나눈다. 기준은 이번 프레임의 위치 변화다.
  - 이동 방향으로 몸을 돌리고, 멈추면 마지막 방향을 유지한다.
  - `flash > 0` 동안 공용 피격 재질로 바꾼다.
  - 죽으면 모델을 숨기고 기존 사망 표시 스프라이트를 쓴다.
- 몬스터(최대 수백 마리, 개체 참조 기준 풀):
  - 뼈대 없는 MeshRenderer와 공용 재질을 쓴다(종류별 재질 1개, 피격 재질 1개).
  - 위치는 보간 없이 바로 맞춘다.
  - 움직이는 방향으로 몸을 돌리고, 코드로 통통 튀는 움직임을 준다(위상은 풀에서 꺼낼 때 정함).
  - 맞으면 공용 피격 재질로 바꾼다. 재질 교체 방식이라 SRP Batcher 묶음이 유지된다.
- 다른 표시: 체력바, 투사체, 자폭 예고 고리, 피해 숫자는 스프라이트 경로 그대로 둔다. 체력바 높이와 가림 기준점만 `Actors` 값을 쓴다.
- 1단계 임시 모델:
  - 영웅 6명 모두 042 영웅 모델(삼각형 2,092개, 예산 초과지만 임시).
  - 몬스터 5종 모두 042 덩어리 모델에 `MonsterDef.color`를 곱해 종류를 구분한다.
  - 목표 화면 크기는 키아트에서 잰 값(영웅 키 약 30px, 일반 몬스터 약 32px, 1280×720 기준)으로 시작해 캡처로 맞춘다.
- 성능 확인(지표만):
  - 편집기에서 웨이브 10까지 진행하고 적 수·삼각형 수·SetPass·배치 수·프레임 시간을 기록한다(PC 품질 단계 + `Mobile_RPAsset`).
  - 몬스터 그림자는 이 결과를 보고 켜거나 끈다.
  - 실기기 성능은 NOT_RUN(사용자)이다.

**실행기 확장(검토 D5):** 044 실행기는 웨이브마다 2~5초만 돌고 `DebugFinish`로 넘긴다. 그래서 후반 생성·경로 문제와 수백 마리 부하를 보지 못한다. 045 실행기에는 다음을 더한다.

- 조사기 `State()`에 `MapSpawnFailures`, 생존 적 수, 3D 표시 수를 추가한다.
- **배치 판정은 맵마다 독립 기준으로 한다(검토 r002 D5).** 일반 플레이의 난수는 시드가 없고 프레임 시간도 실행마다 달라 같은 조건 비교가 성립하지 않는다. 044 측정치는 참고값으로만 함께 기록한다.

  | 기준 | 합격 조건 | 미달 처리 |
  |---|---|---|
  | 생성 실패율 | 웨이브마다 실패 ÷ (생성 + 실패) ≤ 0.20 | FAIL. 044도 같은 기준을 넘으면 그 사실을 함께 적고, 배치 원인인지 위치를 기록해 판단한다 |
  | 장애물 안 적 | 매 기록 시점 0마리(적 중심이 OB 다각형 안) | FAIL |
  | 정체 적 | 장시간 구간에서 살아 있고, 공격 거리 밖이며, 10초 동안 이동 0.5 미만인 적이 생존 수의 2% 이하 | FAIL. 정체 위치를 캡처로 남김 |

- **장시간 부하 구간:** 시간만 늘려서는 수백 마리가 보장되지 않는다(처치되고, 전멸하면 끝난다, `DSGame.Combat.cs:413`). 그래서 검증 전용 주입을 쓴다.
  - 웨이브 10(지속 65초, `PrototypeData.json`)이 시작되면 바로 들어간다. 채우기와 유지를 웨이브 시간 안에 끝내야 한다.
  - **구동 방식과 순서 계약(r004):** `EditorApplication.update`는 게임의 `Update`(시뮬레이션→그리기)와 순서가 고정되지 않으므로 쓰지 않는다.
    - 편집기 전용 런타임 구동기 `DSKeyArt045LoadDriver`(Runtime 폴더, 클래스 전체 `#if UNITY_EDITOR`라 빌드에 들어가지 않음)를 둔다. `[DefaultExecutionOrder(1000)]`로 `DSGame.Update`(기본 순서 0, `DSGame.cs:43`) **뒤에** 실행되게 한다.
    - 조사기가 부하 구간 시작 때 Play 중인 장면에 붙이고, 정리 단계와 Play 종료 때 제거한다.
    - 구동기의 `Update` 한 번은 다음 순서를 지킨다.
      1. **완료된 시뮬레이션 확인:** `DSGame.NormalObservedGameSimulations`(편집기에서 `Simulate`마다 증가, `DSGame.Combat.cs:311`)가 지난 실행보다 커졌는지 본다. 그대로면 이 프레임은 아무것도 하지 않는다. 일시정지·결과 화면 등이 여기에 해당한다.
      2. **대조:** 이번 프레임의 시뮬레이션과 그리기가 끝난 뒤이므로 3D 표시 수와 생존 적 수 + 생존 영웅 수를 비교해 기록한다. 직전 프레임에 주입한 적은 이번 프레임 그리기에 이미 반영돼 있다.
      3. **회복:** 영웅 `hp`를 채운다.
      4. **주입(최종 규칙):** 생존 적이 350 미만이면 `Spawn(extra: true)`를 시뮬레이션당 최대 10회 호출하고, 각 호출 전에 탐색 예산(`mapSpawnSearches`)을 비운다. 판정은 "300 이상 20초 연속"이다. *설계 당시에는 "300 미만이고 예산을 쓰지 않았을 때 1회"였다. 구현에서 바꾼 이유는 아래 "구현 검토(Codex r001) 이후 변경"의 부하 주입 항목에 있다.* 이 값은 이번 `Simulate`에서 초기화된 뒤의 값이다(`DSGame.Combat.cs:325`). 주입된 적은 다음 프레임 그리기부터 대조에 포함된다.
    - 구현 뒤 실제 순서를 확인한다. 처음 10프레임 동안 `Time.frameCount`, 시뮬레이션 수, 그리기 완료 표시(`DSMapActorViews`가 그리기 끝에 남기는 프레임 번호), 구동기 실행을 기록해 "시뮬레이션 → 그리기 완료 → 구동기" 순서를 증거로 남긴다. 시뮬레이션 수는 `Simulate` **진입** 때 늘어나므로 그것만으로는 그리기 완료를 증명할 수 없다(r005). 순서가 다르면 BLOCKED다.
  - **전멸 방지(r003):** 매 프레임 회복만으로는 한 번의 시뮬레이션 안에서 누적 피해로 전원이 죽는 것을 막지 못한다(`DSGame.Combat.cs:413`).
    - 구간 시작 때 영웅의 `maxhp`와 `hp`를 10⁹로 올린다. 한 프레임 피해의 합이 넘을 수 없는 값이다.
    - 매 프레임 `hp`를 다시 채운다(보조).
    - 구간 중 한 명이라도 죽거나 결과 화면으로 넘어가면 주입 실패로 BLOCKED다.
  - **채우기(r003):**
    - 적 생성의 경로 탐색은 시뮬레이션 1회당 1번만 허용된다(`DSGame.MapCombat.cs:46`).
    - (설계 당시) 프레임마다 최대 1회 호출하고, 예산을 이미 썼으면 건너뛴다. **최종:** 시뮬레이션당 최대 10회, 호출마다 예산을 비우고, 350까지 채운다(위 4번).
    - 호출 전후의 `MapSpawnFailures` 차이로 주입 실패를 따로 센다. 일반 생성 실패율(위 표)은 주입을 뺀 10웨이브 진행 기록으로만 판정한다.
    - 생성 규칙 자체는 바꾸지 않는다.
  - **제한 시간:** 웨이브 10 시작 후 35초 안에 생존 적 300 이상에 도달해야 한다. 도달하면 그때부터 20초 동안 유지를 본다.
  - 합격 조건: 생존 적 ≥ 300이 연속 20초 유지되고, 그동안 매 기록 시점(0.5초 간격)에 3D 표시 수 = 생존 적 수 + 생존 영웅 수다.
  - 기록: PC 품질 단계 + `Mobile_RPAsset`에서 프레임 시간(중앙값·95%), 배치·SetPass·삼각형 수(편집기 통계), 생성 실패 수. 모바일 품질 단계 전체가 아니다.
  - 미달 판정:
    - 주입 자체가 성립하지 않으면 BLOCKED다(호출 불가, 영웅 사망, 웨이브 종료 전 미도달 원인이 건너뛴 프레임뿐인 경우).
    - 주입 호출이 생성 검사(경계·장애물·경로)로 거부되어 35초 안에 채워지지 않으면 FAIL이다. 주입 실패율과 거부 위치를 기록한다.
  - 주입은 Play 중 메모리 상태만 바꾼다. 끝나면 Play를 종료해 원상 복구하고, 에셋 변경이 없음을 보호 파일 SHA로 확인한다.
  - 편집기 수치는 실기기 성능이 아니라 비교 지표다. 성능 합격 판정은 하지 않는다.

- 독립 검토:
  - 설계는 지금 Codex에 맡긴다([design-reviewer](../workflows/design-reviewer.md)).
  - 구현 뒤에는 Codex에 [validator-client](../workflows/validator-client.md) 검토를 맡긴다.
  - 3D 표시의 개체 대응·풀 반환은 [algorithm-tester](../workflows/algorithm-tester.md) 관점도 함께 요청한다.
- 초기 실제 연결: 새 배치만 바꾼 장면(시각물 교체 전)을 열고 Play로 시작 화면을 1장 캡처한다. `Bind`와 적 생성이 되는지 먼저 확인한 뒤 나머지를 쌓는다.

## 위험과 알려진 한계

- **같은 그림은 안 된다.** 키아트의 붓질 같은 풀, 부드러운 빛, 깊이감은 일부만 재현된다. 판정은 "나란히 놓았을 때 같은 계열인가"이고, 사용자가 한다.
- **모바일 화면은 PC보다 평평하다.** SSAO와 부드러운 그림자가 없기 때문이다(위 1-D).
- **적 수백 마리의 3D 표시는 실기기에서 무거울 수 있다.** 1단계 지표를 보고 그림자, 단순화, 묶음 그리기를 조정한다.
- **배치를 바꾸면 전투 동선이 달라진다.** 장애물이 시작 화면에 몰리고 북쪽은 열린다. 직접 플레이로 판단해야 한다.
- 임시 영웅 모델은 키아트 스타일이 아니다(큰 모자). 1단계는 구도·색·크기·움직임을 보는 단계이고, 캐릭터 모양은 3단계에서 바뀐다.
- 공격 효과·투사체는 2D 원으로 남는다(4단계).
