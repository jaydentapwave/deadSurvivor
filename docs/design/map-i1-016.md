# MAP-I1-016 기록 실행 껍데기

2026-10-31 · L2 · [I0 결과](../reviews/map-i0-015-review.md) 이후 [착수 명세 I1](map-first-implementation-spec.md)의 로컬 기록 계층을 구현한다. [009 실행/실패 계약](map-harness-implementation.md)의 입력 고정·새 실행·순서·누락·중단 보존을 실제 코드로 만든다. 메인이 구현하며 design-reviewer와 validator-client가 독립 검토한다.

## 범위와 파일

- `Tools/Verify/map_session.py`: `init --plan`, `collect --run --packet`, `finalize --run`, `abort --run --reason cancelled|timeout|interrupted`, `status --run`. 현재 local/all 의미와 `map_check.py` H1은 유지한다. Unity 호출·게임 코드·씬 변경·실제 이동/충돌 계산은 없다.
- `test_map_session.py`: 프로토콜 정상/반례·파일 잠금·중간 프로세스 종료·시간/크기 제한 시험. 기존 Verify 시험도 유지한다.
- 별도 `I1_COLLECTION_PLAN`/`PROTOCOL_FIXTURE_ONLY` envelope 예제를 둔다. 기존 `map v1` request를 부분 검사하고 완료로 승인하는 어댑터가 아니다. 기존 fixtures의 DESIGN_EXAMPLES_NOT_EXECUTABLE_REQUEST 역할을 바꾸지 않는다.

## 입력·기록 계약

plan은 schema_version=1, document_role=I1_COLLECTION_PLAN, scope=PROTOCOL_FIXTURE_ONLY, suite_id/revision, expected_case_ids(비어 있지 않은 유일 ID), cases(case_id/step_count/event_count), inputs(프로젝트 상대경로/SHA-256), wall_timeout_s, max_payload_bytes를 요구한다. 예상 ID와 cases ID가 정확히 같아야 한다. ID/개수/유한 수치·필수/미지원 필드·중복 JSON 키·경로 이탈·심볼릭 링크·파일 크기를 거부한다. 사례≤128, 사례 step/event≤10,000, 전체 payload≤64MiB 등 기록 계층의 안전 한도를 고정한다. 게임 최종 수치가 아니다.

각 init은 UUID run-id와 별도 nonce, KST 시각·monotonic 시작 시각·OS boot 식별값, 원본 plan 바이트/해시, producer(`map_session.py`와`map_io.py`) 지문, inputs 지문과 예상 사례를 새 `output/verification/map-sessions/<UUID>/`에 동결한다. macOS는 kern.boottime의 sec/usec, Linux는 boot_id로 연속성을 확인하고 미지원/확인 불가는 BLOCKED다. 부팅이 달라지면 monotonic 값이 증가했어도 미종료 run의 수집/종료를 차단한다. 기존 run을 덮어쓰지 않는다. `manifest.json`과 최초 journal의 해시 결합, 원본/코드/산출물 무결성을 매번 검사한다. 같은 실행에 대한 CLI 변경은 OS 파일 잠금으로 직렬화하고 충돌을 BLOCKED로 반환한다. Unity 자원 소유를 주장하지 않는다.

packet은 schema_version=1, scope=PROTOCOL_FIXTURE_ONLY, run_id/nonce/case_id, start/end_marker, steps/events를 가진다. 각 marker/step/event도 같은 실행/사례 ID를 포함한다. step은 step_id=0..N-1·observer_sequence=1..N·증가하는 frame_id·payload object, event는 event_sequence=1..M·유효한 step_id·payload object다. marker의 시작/종료 frame 범위가 관측을 포함해야 한다. plan의 개수와 일치하지 않는 빈/누락·다른 nonce·과거 사례·중복·순서 역전은 FAIL이다. payload는 관측 저장용이며 I1이 게임 의미를 판정하지 않는다.

journal.jsonl은 seq/run_id/nonce/phase/시각/단조 경과/PID/details를 가진다. append는 전체 JSONL의 새 파일 fsync→원자 교체로 커밋한다. `READY → COLLECT_PLANNED → ACCEPTED` 순서에서 계획을 원자료 쓰기 전에 기록한다. packet 저장 후 ACCEPTED가 없으면 미완료 작업으로 차단하며 자동 성공 복구하지 않는다. 검증 실패는 REJECTED로 보존하여 나중 취소/누락이 기존 FAIL을 덮지 않는다. 재시작해도 accepted 목록과 오류는 journal에서 재구성한다.

`FINALIZING → FINALIZED`는 마지막 요약/해시를 결합한다. 관측/입력/코드/최종 요약/cleanup 파일이 바뀌거나 종료 도중 파일이 누락되면 status는 성공을 반환하지 않는다. 취소/timeout/interrupt는 새 실행으로 가장하지 않고 해당 run에서 중간 원자료와 종료 이유를 보존한다. producer가 멈춘 기간의 deadline은 다음 명령에서 감지하며 **상주 watchdog은 I1에 없다**. 재부팅 등 monotonic 시간이 거꾸로 되면 BLOCKED다.

| 상태 | collect | finalize | abort | status |
|---|---|---|---|---|
| READY/ACCEPTED/REJECTED | 유효 입력만 수집 | 누락 포함 종료 판정 | 명시 이유로 종료 | 현재 무결성/상태 |
| COLLECT_PLANNED 미완료 | BLOCKED | BLOCKED | 유효 journal/입력일 때 중단 종료 | BLOCKED, 미완료 표시 |
| FINALIZING 미완료 | BLOCKED | BLOCKED | BLOCKED, 자동 완료/수정 금지 | BLOCKED, 부분 출력 보존 |
| FINALIZED(정상/중단 공통) | BLOCKED, 원본 불변 | 기존 검증된 요약을 읽기만 함 | BLOCKED, 종료 이유 변경 금지 | 기존 검증된 요약 |

종료 후에는 현재 deadline/boot 변경을 종료 판정에 다시 적용하지 않는다. 종료 전 무결성·시각 순서는 계속 검증하고, 반복 finalize/status는 파일/시각/종료 이유를 다시 쓰지 않는다. 종료 후 collect/abort 거부는 외부 오류 보고서에만 남긴다.

## 판정·복구 경계

최종 요약은 예상/수집/누락 ID와 개수·거부 이유·pending·입력/증거 지문을 보존한다. 수집 무결성만 `collector_status`로 판정한다. 일반 사례·FI 의미·F/R/B/H/C·실제 Unity와 외부 cleanup은 NOT_RUN이다. cleanup.json은 외부 자원 생성0/Unity 어댑터 미구현을 명시하고 복구 PASS를 꾸미지 않는다.

- 모든 기록이 유효해도 최종 overall status는 NOT_RUN(exit2), collector_status만 PASS다.
- 프로토콜/관측 오류가 있으면 FAIL(exit1), 이후 취소도 이를 낮추지 않는다.
- 환경/입력 지문·누락·중단은 BLOCKED(exit2). 최종 요약이 누락/불완전하면 PASS 불가.
- init/collect의 PASS(exit0)는 그 명령의 기록 작업 성공이며 런타임 성공이 아니다. stdout에 scope·unity_status=NOT_RUN·경로를 표시한다.
- 손상된 run은 기존 증거를 덮어 수정하지 않는다. CLI 오류는 고유 `map-session-errors` 보고서에도 남긴다. 입력/도구 변경이 없고 journal이 유효할 때 pending run을 명시적 abort로 닫을 수 있다. OS lock 해제는 context/finally에 맡기며 외부 Unity 복구를 주장하지 않는다.

## 검증과 완료 기준

정상2사례·새 프로세스 이어 수집·실행 ID 분리, 빈/중복/누락/이전 nonce/순서/marker·원자료 변조·잘못된 schema/path/NaN·입력/코드 변경·deadline·payload 한도·잠금·중간 종료/취소·cleanup/요약 위조를 시험한다. 단위/로컬 → 독립 코드 검토·수정 → 실제 파일 CLI 통합 → Verify 검사기 변경에 필요한 현재 all --screens 1회 → 독립 증거 검토 → 문서/local/gate 순서다. 실패가 생기면 영향 검사를 재실행한다.

I1 완료는 이 로컬 기록 계층의 구현/시험 범위다. Unity 소유권·reload·입력/관찰 연결·실제 cleanup과 full map v1 자료 인수는 후속 I2 연동에서 필요하며, I1의 합성 packet을 실제 프레임/이동/G2 증거로 전용하지 않는다. 이동 계산을 바꾸지 않으므로 이번 algorithm-tester 실행은 해당 없고 I2에서 적용한다.

## 구현된 명령

```sh
python3 -m unittest discover -s Tools/Verify -p 'test_map_session.py' -q
python3 Tools/Verify/map_session.py init --plan docs/design/map-i1-016-plan.example.json
python3 Tools/Verify/map_session.py collect --run <run_id> --packet <프로젝트 안 packet.json>
python3 Tools/Verify/map_session.py status --run <run_id>
python3 Tools/Verify/map_session.py finalize --run <run_id>
python3 Tools/Verify/map_session.py abort --run <run_id> --reason interrupted
```

예제 plan은 로컬 기록 시험 전용2사례이며 실제 map v1 실행 요청이 아니다. 실제 packet 생산자는 I2에서 연결한다. init이 반환한 run_id/nonce와 plan의 예상 step/event 수에 맞는 packet만 수집한다. status/finalize의 정상 프로토콜 결과도 overall NOT_RUN·exit2이며 collector_status를 따로 확인한다. 종료 뒤 finalize/status는 원본을 검증해 읽기만 하고 collect/abort는 거부한다.

중단 시 파일을 저장했으나 ACCEPTED가 없는 경우에도 pending 파일 존재/해시/크기와 packet 계약을 검사한다. abort 요약에 pending 존재 여부와 .pending 임시 파일별 해시를 동결하므로 종료 후 추가/변경/삭제도 거부한다. 파일 손상이나 input/producer 변경을 고쳐서 과거 실행을 성공으로 덮어쓰지 않는다. source가 바뀌면 새 run을 만든다.

OS boot 정보를 읽을 수 없는 실행 환경은 BOOT_ID_UNAVAILABLE로 차단한다. 코드가 재부팅 연속성을 추정해 우회하지 않는다. deadline은 명령 사이와 종료 marker에서 확인하며 상주 watchdog이 아니다. 전체 계획/manifest/packet/journal/cleanup/요약과 실패 진단 원자료는 output에 남고 stdout은 짧은 상태/경로만 출력한다.
