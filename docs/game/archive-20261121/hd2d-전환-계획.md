# HD-2D 전환 계획: 도트 캐릭터 + 3D 배경

- 작성: 2026-11-17, Claude(디렉터). 상태: **진행 중 — 1단계 시안**(2026-11-18 재개). 0단계 답(사용자 11-18 "HD-2D 이어서 하자" 뒤): "계획대로 진행", 비용 "시안은 남은 $88 안에서"(2단계 상한은 시안 뒤), 순서 "HD-2D 먼저". 실행 기록 `.director/runs/20261118-hd2d-lookdev/`. (11-17: "우선 문서를 작성해줘 추후에 다시 작업을 진행할려고해")
- **11-18 02:4x 자율 완성으로 전환**: "온전히 완성된 결과물을 내가 받아서 보고싶어 … 중간중간에 나한테 보고하는 방식이아니라", UI도 옥토패스 결, 추가 비용 $400(멈춤 $827.78), 8방향 포함. 완성 정의·순서·확인 방법·위임 결정은 [완성 실행 계획](hd2d-완성-실행계획.md)이 원본이다. 아래 표의 "사용자가 할 일"(고르기·승인)은 그 문서 4절대로 디렉터가 대신 정한다.
- 사용자 원문:
  - "지금 아트를 봤는데 완전 90년대 게임같은 느낌이야 이걸 hd2d? 방식으로 만들어보는거는 어떄"
  - "B로 좀 제대로된느낌을 한번 내보고 싶어서 , 우리 기존에 만든 3d 형태가 있잖아 거기에다가 추가를해보는건 어떄"
  - "좋아 그러면 처음부터 어떻게 하면 좋을지 끝까지 쭉 계획을 세워줘"
  - "추가적으로 이번 목표를 2.5d을 sutiokit에 적용해서 추후에도 작업할떄 도움이 될 수 있고 자동화될 수 있게 하자"
- 그래서 목표는 둘이다. 이 게임의 전투 화면을 HD-2D로 바꾸는 것(1~8단계)과, 그 방법을 studio-kit의 **2.5D 팩**으로 담아 다음 게임에서도 디렉터가 자동으로 쓰게 하는 것(9단계)이다.
- B는 디렉터가 앞 답변에서 제안한 두 길 중 "진짜 HD-2D(배경을 3D로)"다. A는 "2D 구조를 유지하고 느낌만"이다.
- 바탕: [게임 기획서](gdd.md), [아트 기준서](../art/아트-기준서.md)(r5), [2D 전환 계획](2d-전환-계획.md), [다음 작업](다음-작업.md), 예전 3D 기록([046 전체 맵](../design/map-full-046.md), [049 성능](../reviews/perf-049.md), [043 로우폴리 셰이더](../design/lowpoly-shader-043.md))
- 이 문서는 진행 계획이다. 아트 기준서와 기능 기획서를 대신하지 않는다. 그 문서들은 2·3단계에서 고친다.
- **값과 방법은 [HD-2D 사전 조사](hd2d-사전조사.md)에 있다**(11-17): 결정 D1~D16, 기술 근거, 프로젝트 사실, 카메라 계산, 레퍼런스 관찰, 1단계 작업 지시 초안, 킷 팩 설계 초안. 이 문서와 값이 다르면 사전 조사가 더 새것이다.
- "HD-2D"는 만드는 방식(도트 캐릭터를 3D 공간에 세우고 빛과 흐림으로 깊이를 주는 것)을 가리킨다. 특정 게임의 그림이나 화면을 따라 하지 않는다. 그림의 기준은 계속 우리 컨셉 그림(PE-G001~G004)이다.

## 1. 한눈에

- **목표**: 한 판이 처음부터 끝까지 도는 지금 2D 게임은 그대로 두고, 전투 화면만 "도트 캐릭터 + 3D 배경 + 빛·그림자·흐림"으로 바꾼다.
- **방식**:
  - 게임 규칙과 계산은 지금처럼 2D 바닥 좌표로 둔다. 그리는 쪽만 3D로 옮긴다.
  - 캐릭터, 몬스터, 효과의 도트 그림은 그대로 카메라 쪽으로 세워서 쓴다.
  - 배경은 예전 3D 전체 맵(046)의 배치를 가져와 도트 질감으로 다시 입힌다.
- **단계**:

| 단계 | 하는 일 | 사용자가 할 일 | 돈이 드는 생성 |
|---|---|---|---|
| 0 | 계획 확인 | 이 계획 승인, 비용 상한 | — |
| 1 | 시안: 시험 장면에서 예전 맵 그대로 vs HD-2D판, 카메라 각도 비교 | **고르기** (여기까지는 되돌리기 쉽다) | 없음 |
| 2 | 아트 기준서 개정(r6): 카메라·조명·질감·화면 효과·성능 값 | **승인** | 없음 |
| 3 | 화면 구조 설계와 설계 검토 | — | 없음 |
| 4 | 화면 기반 구현: 3D 렌더러, 카메라, 세운 도트 판, 그림자, 효과 위치 | — | 없음 |
| 5 | 배경 만들기: 땅 질감, 높낮이, 3D 소품, 세운 장식 | 새 3D 모델이 필요하면 **생성 상한 승인** | 필요할 때만(Tripo) |
| 6 | 빛과 화면 효과 다듬기 | — | 없음 |
| 7 | 성능 측정과 줄이기 | — | 없음 |
| 8 | 마감: 판정, 리뷰, 미리보기 | **플레이 후 의견** | — |
| 9 | studio-kit 2.5D 팩: 1~8단계에서 검증된 규칙·도구·유니티 패키지·디렉터 연결을 킷으로 옮김 | **킷을 GitHub에 올릴지** | — |

- **킷에 담는 방식**: 킷은 "실제 프로젝트에서 검증된 것"만 팩으로 담는다(studio-kit `AGENTS.md`). 그래서 이 게임에서 먼저 만들고 검증한 뒤 옮긴다. 다만 다시 쓸 부분은 1단계부터 게임 이름 없이 일반적으로 만들어, 9단계가 옮기기만 하면 되게 한다.

## 3. 목표 화면

| 겹 | 지금(2D) | HD-2D 후 |
|---|---|---|
| 바닥 | 마름모 타일맵(풀 4종, 흙길) | 3D 땅에 도트 질감(지금 풀·흙길 그림을 넓혀서 사용). 가장자리에 언덕, 턱, 개울 높낮이. 가운데는 평평하게 비운다(기준서 3.2) |
| 장식 | 거의 없음 | 3D 소품(돌담, 울타리, 바위, 다리, 표지판, 천막)과 세운 도트 판(꽃, 풀, 덤불) |
| 캐릭터·몬스터 | 도트 스프라이트 | 같은 도트를 카메라 쪽으로 기울여 세운 판. 걷기·공격 프레임과 방향 규칙은 그대로 |
| 그림자 | 발밑 타원 | 대원과 큰 소품은 실제 그림자. 몬스터는 발밑 원(049 교훈) |
| 빛 | 없음(조명 받는 기본 재질만 있고 2D 빛은 없다) | 해(방향 빛)와 하늘빛. 밤 등불은 2단에서 점광으로 |
| 카메라 | 정사영, 도트 고정 카메라(640×360, 48px 단위) | 비스듬히 내려다보는 3D 카메라. 정사영(추천) 또는 좁은 화각 원근 중 1단계에서 고름 |
| 화면 효과 | 없음 | 빛 번짐, 화면 위아래 흐림, 색 보정, 가장자리 어둡게, 떠다니는 입자 |
| 효과·피해 숫자·HP 바 | 2D 스프라이트 | 같은 그림을 세운 판으로 |
| UI | 화면 위 캔버스 | 그대로 |

**카메라 출발값**(1단계 시안에서 정한다. 자세한 것은 사전 조사 D1·D2·4절):

- 지금 바닥은 세로를 절반으로 눌러 그린다(`IsoProjection`, 세로 0.5). 같은 비율이 나오는 카메라 각도는 바닥에서 30°다(sin 30° = 0.5, 계산값). 그래서 **30°가 지금과 같은 구도**다. 레퍼런스 전투 화면은 33~50°이고, 출발값 후보는 약 40°다.
- 추천은 **원근 없는 3D 카메라(정사영) + 화면 위아래 흐림**이다. 이유는 셋이다.
  - 원근이면 화면 위쪽 도트가 작아지고 흔들린다.
  - 유니티 기본 흐림은 정사영에서 맞지 않지만, 화면 위아래 흐림은 어느 카메라에서나 되고 더 싸다.
  - 지금의 보이는 범위 계산을 거의 그대로 쓴다.
- 원근(40°, 화각 8~12°)도 시안에서 같이 찍어 고른다.

## 5. 단계별 계획

공통:
- 만드는 일(장면·코드·그림)은 Codex(`gpt-6.1-sol`, medium)가 한다. 보고 고르는 판단, 기준서, 설계는 디렉터(Claude)가 한다. 리뷰 4종은 Codex 중계다(CLAUDE.md).
- 에디터를 쓰는 일은 하나씩 끝낸다. 그림 만들기처럼 에디터를 쓰지 않는 일만 나란히 돌린다.
- 사용자가 에디터에서 플레이하는 동안에는 테스트나 장면 명령을 보내지 않는다(`test-before-claim.md`).
- 캡처는 디렉터가 직접 열어 본 뒤 보여 준다. 보여 주는 길은 로컬 미리보기 페이지다(`art-core-rules.md` 6절).
- **작업 개선 기록**: 문제·고칠 점·자동화 후보·시간은 [HD-2D 작업 개선 기록](hd2d-작업-개선-기록.md)에 생길 때마다 적는다(사용자 11-18 "계속해서 문서를 남겨줘"). 9단계는 그 문서 3절도 함께 본다.
- **보여 주기 전 자동 관문 (2026-11-18 사용자)**: "아트를 보여주기전에 너가 검증 테스트를 어느정도 설계를해놓고 그 검증 테스트를 모두 통과하지 못하면 나한테 보여줄 필요는 없을 것 같아, 이 검증 테스트도 추후에 studio-kit에 업로드를 해서 사용할 수 있게해줘, 검증 테스트를 만들때 codex, fable에게 검증 테스트 요청으로 받아줘". 설계 요청 `.director/runs/20261118-hd2d-lookdev/steps/gate-design.md`, 답 `docs/game/hd2d-검증-설계/`(Codex·Fable 각 r001). 디렉터가 합쳐 관문 도구로 만들고(킷 갈래 `feat/25d-art`), 시안 2회차부터 관문 통과 뒤에만 미리보기를 연다.
- **킷 메모**: 단계가 끝날 때마다 "킷에 담을 것"을 이 문서 11절에 적는다. 정한 값과 그 근거, 만든 도구, 겪은 문제와 해결이 대상이다. 9단계는 이 메모에서 시작한다.

### 3단계: 화면 구조 설계

렌더 파이프라인을 바꾸는 L2라서 설계 브리핑을 쓰고 설계 검토(design-reviewer, Codex)를 한 번 받는다.

조사 결과(11-17, 코드 직접 확인):
- **좋은 점**:
  - 게임 계산은 이미 바닥 좌표(Vector2)로만 한다. 계산 쪽 클래스는 화면 위치를 건드리지 않는다.
  - 바닥 좌표 → 화면 좌표 변환이 `IsoProjection` 한 곳에 모여 있다.
  - 렌더 설정 두 개(PC·모바일)에 3D 렌더러가 이미 0번으로 들어 있다. 카메라가 1번(2D)을 고르고 있을 뿐이다.
  - 입력은 키보드와 화면 조이스틱뿐이고, 화면→월드 변환이나 2D 물리를 쓰지 않는다.
- **고칠 곳**: 화면 쪽 파일 약 45개 중 월드 공간을 쓰는 약 25개.

| 고칠 곳 | 지금 | 바꿀 방향(설계에서 확정) |
|---|---|---|
| 좌표 변환 `IsoProjection` | (x, y×0.5) 2D | (x, 0, y) 3D 바닥. 세로 누르기는 카메라가 한다 |
| 입력 보정 `PartyMoveMath` | 화면 y×2 | 카메라 각도에 맞춘 보정(30°면 지금과 같음) |
| 보이는 범위 `WorldPresenter.UpdateViewExtent` | 정사영 크기에서 계산. 몬스터 생성 거리와 원정대 이동 제한이 이 값을 쓴다 | 정사영이면 세로 0.5를 sin(각도)로 바꾼다(30°면 같음). 원근이면 바닥 사다리꼴에서 새로 계산한다. **게임 동작에 닿는 곳**이라 시험을 붙인다 |
| 공격 방향으로 고르는 그림 방향 `CombatService` | 2D 투영 | 같은 규칙, 3D 투영 |
| 바닥 `WorldPresenter.BuildField`, `FieldView` | 아이소 타일맵 64×64, 마름모 경계 | 3D 땅 메시와 소품. 경계 규칙은 그대로 |
| 캐릭터·몬스터 `MemberView`, `MonsterView` | 스프라이트, 화면 Y로 앞뒤 정렬 | 세운 판, 깊이로 앞뒤 정렬, 그림자 내는 도트 재질 |
| 효과·피해 숫자·HP 바·화면 흔들림 | 픽셀 단위 이동과 픽셀 맞춤 | 미터 단위, 세운 판 |
| 카메라·장면 짓기 `MainSceneBuilder` | 정사영, 도트 고정 카메라, 2D 렌더러 | 3D 렌더러(0번), 1단계에서 고른 카메라, 화면 효과 볼륨 |
| 재질 | 대부분 `Sprite-Unlit-Default`, 번쩍임은 GUI/Text 셰이더 | 빛 받고 그림자 내는 도트 Lit 재질 하나(사전 조사 D3)와 그 재질의 "흰색 덮기" |
| 렌더 설정(PC·모바일) | SRP Batcher 꺼짐, 모바일 Render Scale 0.8 | SRP Batcher 켬, Render Scale 1.0, 그림자 값(사전 조사 3.1·D7) |
| 판정 경로 `PlayableProbe` | 카메라·타일맵·픽셀 위치를 검사 | 새 화면에 맞게 고친다 |
| 테스트 | 화면 쪽 테스트 약 14개(`IsoProjectionTests`, `FieldDecorTests` 등) | 새 방식에 맞게 고친다. 규칙 테스트 약 35개는 그대로 통과해야 한다 |

- **결과물**: 설계 브리핑과 검토 판정. 필수 지적을 고친 뒤 구현으로 간다.

### 5단계: 배경 만들기

- **전투장**:
  - 046 배치를 새 전투장 크기(바닥 64칸 마름모)에 맞춰 줄이고 옮긴다.
  - 가운데는 비우고 장식은 가장자리에 둔다(기준서 3.2). 가장자리에는 언덕, 턱, 개울로 높낮이를 준다.
- **땅 질감**: 풀, 흙길, 자갈. 지금 그림을 넓혀 쓰고, 모자라면 Codex로 생성한 뒤 도트로 정리한다(유료 아님).
- **소품**(컨셉 PE-G001 기준):

| 종류 | 만드는 방식 | 출처 |
|---|---|---|
| 돌담, 바위, 돌 | 3D | 예전 모델 다시 칠하기 먼저 |
| 나무 | 3D 또는 세운 판(시안에서 고름) | 예전 모델 또는 새로 |
| 울타리, 다리, 표지판·깃발, 천막 | 3D | 새로 만든다. 예전에 없음 |
| 개울·폭포, 연못 | 3D 물(도트 질감) | 예전 연못 배치 |
| 꽃, 풀, 덤불 | 세운 도트 판 | 지금 2D 장식 |

- **새 3D 모델**: 예전 모델로 안 되는 것만 Tripo로 만든다. 요청마다 사용자 승인과 상한을 받는다(`art-core-rules.md` 7절). 그때 3D 소품 도구 묶음(3d-art 팩)을 프로젝트에 깐다.
- **가려짐**: 소품이 캐릭터를 가리면 비쳐 보이게 한다(게임 스펙의 "가려짐 처리").
- **다 됐다고 볼 기준**: 기준서 3.3 범위 대조표의 행마다 차이 0, 최신 게임 캡처를 직접 봄, 판정 경로 통과.

### 6단계: 빛과 화면 효과 다듬기

- 해 방향·색·세기, 그림자 세기, 하늘빛, 안개, 흐림 범위, 빛 번짐, 색 보정, 입자(꽃가루, 먼지, 나뭇잎).
- 효과(폭발, 마법)에 순간 빛을 더할지는 성능을 보고 정한다.
- **기준**: 땅 색을 컨셉 PE-G001 측정값(K7)과 나란히 잰다(`paint.py`). 순간 효과는 연속 캡처로 본다.
- 밤(2단)은 이 빛 위에 등불 점광을 더하는 일이 된다.

### 7단계: 성능

- 모바일 렌더 설정으로 잰다: 웨이브 6, 몬스터 300·400마리. 기준은 프레임 16.7ms 이하(M7)다.
- 넘으면 이 순서로 줄인다(049 교훈):
  1. 몬스터 실제 그림자 끄기
  2. 흐림을 낮은 해상도로
  3. 그림자 거리·단계 줄이기
  4. 소품 합치기
  - 인스턴싱은 049에서 오히려 느려졌으니 재 보고 정한다.
- 실기기 확인은 2단의 휴대폰 빌드와 묶는다. 에디터 숫자는 실기기 숫자가 아니라서 그때까지 "실기기 미확인"으로 적는다.

### 9단계: studio-kit 2.5D 팩

- **목표**: 다음에 사용자가 "HD-2D로", "도트 캐릭터에 3D 배경으로"라고 하면, 디렉터가 이 팩을 깔고 같은 순서(시안 → 기준서 → 화면 구조 → 배경 → 빛 → 성능)를 묻지 않고 진행한다.
- **어디서**: 킷 저장소(`Workspace/studio-kit`)의 별도 작업 갈래. 다른 프로젝트는 킷 스킬을 링크로 쓰고 있어서, 다 될 때까지 기존 스킬은 건드리지 않는다.
- **팩 이름**: `25d-art`(가칭). 2D 팩 `2d-art`, 3D 팩 `3d-art`와 같은 모양이다. 스킬 이름은 `25d-art-setup`처럼 짓는다.
- **담을 것**:

| 묶음 | 내용 | 이번 게임의 출처 |
|---|---|---|
| 규칙(`.ai/rules/25d-*.md`) | 화면 겹 구조, 카메라 각도·화각 정하는 법, 세운 판 규칙(기울기, 발 피벗, 그림자), 땅 질감의 도트 크기를 캐릭터에 맞추는 법, 화면 효과 기본값, 모바일 성능 예산과 줄이는 순서, 가려짐 처리 | 2·3·6·7단계 |

- **기존 팩과의 관계**: 캐릭터·효과 도트는 계속 `2d-art` 팩이 만든다. 새 3D 소품은 `3d-art` 팩(Tripo)을 쓴다. 2.5D 팩은 그 둘을 3D 공간에 세우고 비추는 부분만 맡는다.
- **확인**:
  1. 킷 검사(`scripts/validate.py`)를 전부 통과한다.
  2. 빈 견본 프로젝트에 깔아 보는 설치 시험을 통과한다.
  3. 이 게임에 팩을 다시 깔았을 때 이미 만든 것과 부딪히지 않는다(kept·conflict 보고).
  4. README의 스킬 표를 고치고 버전을 올린다(0.21.0 → 0.22.0).
- **사용자**: 킷을 GitHub에 올릴지 정한다. 올리기 전까지는 로컬 커밋만 한다.
- **후속(이번 범위 밖)**: 다른 게임에서 한 번 더 써 보고 기본값을 굳힌다. 킷도 0.19.0에서 두 번째 검증의 지적을 반영한 적이 있다.
