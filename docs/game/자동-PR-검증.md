## 0. 무엇이 문제였나 (P21)

| 본 것 | 왜 문제 |
|---|---|

| 사용자가 묻고서야 드러났다 | 단계 마감 점검표에 "합치기 방식" 항목이 없었다 |

## 1. 브랜치 구조 (단계가 병렬일 때)

```
main                              ← 사용자 지시로만 (epic PR, 사람이 머지)
 └── epic/<기능>                  ← 원격. 본선 PR이 여기로 바로 머지
      └── claude/<기능>           ← 본선(메인 폴더). 단계 PR이 여기로
           ├── claude/<기능>-<단계>  ← 워크트리 단계 (예: claude/hd2d-fx)
           └── …
```

- 레포 규칙의 이름 맞추기(`claude/test` → `epic/test`)는 **본선**에 적용한다. 워크트리 단계 브랜치는 본선 `claude/<기능>`을 기준으로 PR한다(겹 PR). 킷 규칙에 "단계 브랜치 → 본선 → epic" 두 겹을 명시하는 것이 킷 반영 후보다.
- 이번 이름: 본선 `claude/pack-expedition-2d`, epic `epic/pack-expedition-2d`, 단계 `claude/hd2d-ui`(이미 로컬 합침), `claude/hd2d-fx`(진행 중). 앞으로 단계 브랜치 이름은 `claude/pack-expedition-2d-<단계>`로 맞춘다.

## 2. 단계가 끝날 때의 흐름 (자동화 대상)

| # | 할 일 | 누가 | 자동화 |
|---|---|---|---|
| 1 | 단계 실행기 끝 → 핸드오프·`run.yaml` 읽기 | 디렉터 | `pr_stage.py`가 읽음 |
| 2 | **검증 관문 대조**: `run.yaml`의 gates 하나하나에 증거 파일이 있고, 증거의 소스 지문(커밋)이 PR 머리와 같거나 그 뒤 바뀐 파일이 그 관문 범위 밖인지 | 도구 | 아래 3절 |
| 3 | **열람·판독 기록 대조**: 단계 세션의 본 캡처 기록(경로·해시)과 독립 판독(G20)·마감 리뷰 결과를 PR 본문에. 디렉터는 같은 캡처를 다시 열지 않는다(핵심 규칙 6절, 2026-11-18). 판독·리뷰 없이 온 회차만 디렉터가 연다 | 디렉터 | 도구는 "본 캡처 기록·판독 결과 칸이 비었으면 멈춤"만 |
| 4 | 원격 올리기: **정확한 커밋 값으로** push(`git push origin "<sha>:refs/heads/<브랜치>"`) — 다른 세션이 같은 브랜치에 커밋 중일 수 있다 | 도구 | |
| 5 | PR 만들기: 본문을 핸드오프에서 만든다(단계별 커밋 표, 돌린 검증과 결과, **전체 검사 / 닿는 시험만** 구분, 남은 것) | 도구 | `gh pr create --body-file` |
| 6 | 머지: 2·3이 통과면 바로 `gh pr merge --merge`. 실패면 PR을 열어 둔 채 `needs-fix` 표시 + 디렉터 알림 | 도구 | |
| 7 | 머지 확인: `gh pr view --json state,mergedAt` | 도구 | |
| 8 | 워크트리 정리: 단계 브랜치가 머지된 뒤 `git worktree remove`(Library 포함), 브랜치 삭제 | 도구 | |
| 9 | 본선 → epic: 마일스톤(단계 묶음)마다 같은 2~7로 PR·머지. **epic → main은 사용자 지시로만, 머지는 사람이**(레포 규칙) | 도구 + 사람 | |

## 3. 검증 관문 — PR을 머지해도 되는가

"검증은 했을테니"(사용자)를 사람 기억이 아니라 파일로 확인한다.

| 검사 | 통과 조건 | 실패하면 |
|---|---|---|
| G-compile | 마지막 컴파일 기록이 오류 0, 기록 시점 소스 = PR 머리 | 머지 안 함 |
| G-tests | `run.yaml` gates의 시험(지정 `-testFilter` 또는 EditMode 전체)이 PASS이고 개수가 0보다 큼(Total 0은 실패로 본다 — UI 단계에서 실제로 있었던 함정) | 머지 안 함 |
| G-route | 판정 경로가 gates에 있으면 `report.json`이 PASS | 머지 안 함 |
| G-review | 마감 리뷰 3종의 `VERDICT:` 기록이 PASS(또는 FAIL 뒤 수정 확인 PASS) | 머지 안 함. 단, **다음 단계로 넘긴다는 디렉터 기록**(이유·넘긴 곳)이 있으면 PR 본문에 그대로 적고 머지 |
| G-scope | 마지막 전체 검사 뒤 바뀐 파일 목록 → 그 파일들이 닿는 시험이 돌았는지(핵심 규칙 2절: 게임 동작 파일 / 보이는 파일 나눔) | 본문에 "닿는 시험만"으로 표시, 머지는 함 |
| G-seen | 핸드오프·PR 본문의 "디렉터가 직접 본 캡처" 칸이 비어 있지 않음 | 머지 안 함 |
| G-secret | 바뀐 파일에 키·토큰 모양 문자열 없음, 50MB 넘는 파일 경고(이번: 예전 3D `Meshes046.asset` 74MB·58MB — 100MB 한도 아래) | 키면 머지 안 함, 큰 파일은 본문에 경고 |
| G-conflict | 대상 브랜치와 합칠 때 충돌 없음. 장면 파일 충돌은 **이행 메뉴 재실행**으로 푸는 단계(다음 PR 첫 단위)를 본문에 적음 | 문서 충돌은 디렉터가 손으로, 코드 충돌은 단계 실행기에 되돌림 |

이번 첫 PR(#1)에서 위 표를 손으로 적용한 결과: 4·U단계 전 관문 PASS, 5단계 마지막 수정은 닿는 시험만(리뷰 수정 확인은 5b PR로 넘김 — 디렉터 기록), 합침 장면은 5b 첫 단위에서 확인.

## 4. 함정 (이번에 실제로 밟은 것)

- **zsh에서 `$S:r…`**: `git push origin $S:refs/heads/…`가 `:r` 수식어로 해석돼 refspec이 깨졌다 → 변수는 늘 `"${S}:refs/heads/…"`로.
- **다른 세션이 같은 브랜치에 커밋 중**: 브랜치 이름으로 push하면 그 순간의 머리가 올라간다 → 확인한 커밋 값으로 push.
- **워크트리 실행기의 쓰기 경계**: UI 단계 Codex가 메인 폴더 outbox에 쓰지 못해 워크트리에 썼다 → 지시문의 핸드오프 경로를 워크트리 안으로(디렉터가 옮김).
- **`gh pr merge`가 로컬 브랜치를 바꾸는지**: 이번에는 로컬 브랜치·실행 중 단계에 영향 없음을 확인했다(`--delete-branch`를 쓰지 않음).
- **단계 지시문의 "push 금지" 문구**: 레포의 PR 흐름과 부딪힌다 → "push·PR·머지는 디렉터가 한다(단계 실행기는 하지 않음)"로 바꾼다.

## 5. 도구 초안 — `pr_stage.py` (킷 `director-run/scripts/` 후보)

```
pr_stage.py <run-id> [--base <브랜치>] [--dry-run]
  1. .director/runs/<run-id>/run.yaml + 핸드오프 읽기
  2. 3절 관문 검사 → 표 출력(PASS/FAIL/넘김)
  3. FAIL이면 멈춤(코드 1). 넘김은 디렉터 기록이 있을 때만 통과
  4. 커밋 값 고정 → push → PR 본문 생성(2절 5) → gh pr create
  5. gh pr merge --merge → gh pr view로 확인 → run.yaml에 pr 번호·머지 커밋 기록
  6. 워크트리 단계면 worktree remove + 브랜치 삭제(머지 확인 뒤)
```
- 자체 시험 반례: Total 0 시험, 지문 어긋남, 리뷰 FAIL·넘김 기록 없음, 본 캡처 칸 빔, 키 모양 문자열, 대상이 `main`(항상 거절).
- director-run 실행기(`codex-step.py`)가 단계 `done`을 낸 뒤 이 도구를 부르면 디렉터는 3절 G-seen(캡처 직접 보기)만 하면 된다.
