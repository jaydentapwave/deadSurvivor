## 측정 방법과 한계

- 원자료: 이 프로젝트의 로컬 Claude Code 세션 기록(JSONL). 메시지 본문은 옮기지 않고 시각·도구 이름·분류·크기·토큰 수만 쓴다.
- 시간
  - 도구 시간: 도구 호출 → 결과
  - 백그라운드 시간: 실행 시작 → 완료 알림
  - 에이전트 활동: 도구 시간 + 기록 사이 간격이 2분 미만인 구간
  - 대기: 전체 경과 − (활동 ∪ 백그라운드). 밤 시간과 사용자 응답 대기를 포함한다
- 토큰
  - Claude: 응답마다 기록된 입력·캐시 생성·**캐시 읽기**·출력
  - Codex: 실행 기록 끝의 `tokens used`(ChatGPT Pro 사용량, Claude와 별도)
  - 하위 에이전트: 완료 알림의 사용량(이번 집계에서는 2건만 기록됨)
  - Tripo 크레딧은 검증 기록에 따로 있다(2단계 120, 3단계 170)
- 한계
  - 단계 구분은 사용자 승인 시각과 명령 속 키워드(s2, hero_bruno, v2 등)로 나눈 근사다. 2단계와 3단계 v1은 병렬로 진행돼 시간이 겹친다.
  - 비용(달러)은 계산하지 않았다.

## 18:17 → 19:09 사이 (3단계 v2 마무리)

- 실제 작업 0.83h 증가. 방향 결함(S3-21) 발견 → 원인 측정(`facing_check_045.py`) → 재빌드 → 방향 재측정이 대부분.
- 방향 수정 뒤 전체 Play(10웨이브)를 다시 시작했다가 사용자 요청("전체 검증하지말고, 딱 필요한것만 확인해줘")으로 중지하고, 두 스쿼드만 짧게 확인(`quick_squads_045.py`, 약 1분) + 진단 1회(약 1분)로 바꿈. 전체 Play 1회(약 10분)와 Codex 재검토·시각 판정을 줄였다. T1 개선안(전체 Play는 마감 때 1회)을 실제로 적용한 첫 사례다.
- 짧은 확인도 판정 함수의 측정 결함(S3-22)으로 FAIL이 나서 진단 1회가 더 들었다. 새 판정은 알려진 정상 장면으로 먼저 대조한다(T5).

| T1 | **전체 Play 검증 반복이 실제 작업 시간의 약 40%** | 백그라운드 3.47h + 도구 0.62h / 실제 9.75h. 3단계 v1은 텍스처만 바뀐 수정에도 전체 Play를 다시 돌림(8회) | 실행기가 텍스처·재질 파일까지 지문 대상에 넣어, 시각 자산만 바뀌어도 전체 Play 증거가 무효가 됨. 수정 범위와 무관하게 '10웨이브 전체'를 다시 돌림 | 증거를 **게임플레이 증거**(런타임·장면 구조·충돌)와 **시각 증거**(텍스처·재질 → 렌더 검사)로 나눈다. 시각 파일만 바뀌면 렌더 검사 + 짧은 스모크만 돌린다. 전체 Play는 마감 때 1회 |
