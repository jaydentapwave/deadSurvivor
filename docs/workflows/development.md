# 개발 워크플로우

먼저 [핵심 규칙](core-rules.md)을 읽는다. 검증 단계, 검토 횟수, 세션 운영은 그 문서가 우선한다(2026-11-02).

## 작업 분류

| 규모 | 조건 | 필수 절차 |
|---|---|---|
| L0 | 설명·오탈자·링크 정리 또는 기존 계약 안의 국소 수정. 새 흐름·소유권·스키마 변화 없음 | 관련 원본 확인 → 수정 → 영향 범위 검사 → 결과 기록 |
| L1 | 새 기능/입력 흐름, 여러 부분에 영향을 주는 동작 변경, 워크플로우 도입·변경 | 간단 설계 → 구현 → 검사 → validator-client 독립 검토 → 지적 수정 |
| L2 | 상태 소유권, 데이터 스키마, 도메인 경계, 소스 원본 변경 | 설계 브리핑 → design-reviewer 독립 검토 → 구현 → 검사 → validator-client 독립 검토 |

문서·설정만 바꾸더라도 검사·역할·작업 분류 계약을 도입하거나 바꾸면 L1이다. 여러 조건에 해당하면 높은 규모를 적용한다. 파일 수나 기존 타입 내부 수정 여부보다 상태 소유권·스키마·실행 흐름에 미치는 영향을 우선한다. 작은 수치 수정도 게임 동작을 바꾸면 문서 변경으로 취급하지 않는다. 타입 수가 많다는 이유만으로 L2로 올리지는 않는다.

규모와 검사 범위는 별개다. L0도 런타임 변경이면 컴파일·관련 규칙 검사를, UI/씬 변경이면 실제 프레임·입력·캡처를 수행한다. 계산·배치·회복 공유 변경에는 규모와 관계없이 로직 검증 계약을 적용한다. 문서만 변경하면 링크·소스와의 일관성과 최종 gate를 확인한다. 별도 local 반복은 필수가 아니다. 문서 편집만을 이유로 Unity를 재실행하지 않으며 gate가 현재 의존 지문의 증거를 요구하면 해당 차이를 확인한다.

## 시작할 때 고정할 범위

기존 설계 브리핑에 아래 네 항목을 짧게 적고 작업한다. 현재 과제와 관계없는 미래 단계는 완료 조건에 합치지 않는다.

- **이번에 사용할 수 있게 될 결과와 완료 조건:** 예를 들어 “돌벽 후보 1개를 같은 게임 카메라에서 비교할 수 있음”. 시험 후보 완료와 정식 채택/전체 맵 인수를 구분한다.
- **변경 범위와 후속 항목:** 바꿀 파일/동작, 이번에 다루지 않을 품목·자동화·인수 단계를 명시한다.
- **최소 필수 검사:** 변경→실패 가능성/요구→검사 방법을 연결한다. [변경 범위별 gate 기준](verification-gates.md)에 따라 현재 변경에 필요한 검사와 기존 근거 재사용 조건을 명시한다.
- **첫 실제 연결과 추가 검사 조건:** 어떤 최소 정상 사례로 입력→실행→결과·복구를 먼저 확인할지, 어떤 결함/변경이 생기면 검사를 넓힐지 정한다. 순수 문서 작업이면 첫 연결 시험은 해당 없음이다.

검사기·범용화·추가 진단을 만들기 전 “어떤 현재 요구/결함을 기존 도구로 판정할 수 없는가”를 적는다. 지금의 정확성·데이터 보존·소유권·복구·명시된 완료 조건에 필요하면 최소 범위로 구현한다. 구체적인 근거가 없는 미래 대비는 후속 제안으로 남긴다. 필수 요건을 임의로 후속 처리하지 않는다.

검증 도구 작업이 본래 산출물을 밀어내거나 같은 차단이 재발하면 현재 산출물·막힌 요구·추가 작업의 필요성을 재평가해 진행 보고에 설명한다. 승인된 범위 안의 수정은 계속하고 방향/비용/외부 공개 범위를 바꿔야 할 때만 필요한 확인을 요청한다.

## 실행

1. 요청 범위, 관련 기획과 실제 코드, 완료 기준을 확인한다. 사용자 결정과 실험안을 구분한다.
2. L1/L2는 [설계 양식](../templates/design-brief.md)을 복사해 docs/design에 작업 문서를 작성한다. 기존 규칙 원본이 있으면 갱신하고 중복 문서를 만들지 않는다.
3. L2는 [설계 검토 계약](design-reviewer.md)을 읽는 독립 서브에이전트에게 브리핑과 관련 파일만 전달한다. 읽기 전용으로 검토한다. 수정 필요 지적을 해소한 뒤 구현한다.
4. 메인이 구현을 담당한다. 리뷰어는 파일을 수정하지 않는다. 허용된 개인 폴더 밖에 기록하지 않는다.
5. 구현 중에는 영향 단위 시험을 수행한다. run.py local은 전체 정적 진단이 필요할 때만 실행하고 마감에는 범위를 선택하는 gate를 사용한다. 실행 대상·소유권·복구 전제를 확인한 뒤 최소 정상 사례를 기존 실제 경로에 일찍 연결한다. JSON 생략값·객체 ID·float/double 등 접점 오류를 먼저 확인하고 큰 사례 행렬로 확대한다. 이 작은 연결 시험은 최종 통합/필수 검사를 대신하지 않는다. 전체 게임 검사를 불완전한 중간 코드에서 반복하지 않는다. 작업 중 Play 확인은 [핵심 규칙](core-rules.md)의 짧은 단계로 한다.
6. L1/L2는 [구현 검토 계약](validator-client.md)에 따라 독립 코드 검토·수정을 먼저 수행한다. 이 시점의 미실행 통합/Unity 검사는 NOT_RUN이다. 계산·배치·회복 공유 변경은 [로직 검증 계약](algorithm-tester.md)도 적용한다.
7. 선행 지적 해소 뒤 영향 단계 통합 시험 → [변경 범위](verification-gates.md)에 필요한 최종 all 또는 all --screens를 실행한다. 런타임 변경의 Unity 컴파일·규칙·실제 프레임/입력/캡처 의무는 유지한다. 수정 후에는 해당 지적과 영향을 재확인한다. 의존 지문은 증거 종류(게임 동작/보이는 것)별로 본다. 게임 동작 의존이 바뀌었으면 작업 중에는 짧은 Play, 단계 마감에는 전체 Play를 1회 실행한다(`Tools/Harness/tier.py plan`). 새 실패가 생기면 그 범위를 다시 확인한다.
8. 같은 독립 검토자가 최종 실행 증거와 미실행 범위를 확인한다. 코드 재검토는 바뀐 부분·미해결 지적과 그 영향으로 좁히며 새로운 구체적 결함이 있으면 다시 연다. 코드 검토 PASS만으로 완료를 선언하지 않는다.
9. [검증 양식](../templates/verification.md)으로 docs/reviews에 결과를 기록한다. 필요한 원본 문서와 상태 링크를 갱신하고 최종 gate를 실행한다. gate의 검사별 RUN/REUSE·의존 지문·원자료를 최종 근거로 사용한다. 같은 입력의 local/H1/MAP007을 별도로 반복하지 않는다. 누락·손상·의존 변경·새 실패가 있으면 해당 검사를 다시 실행한다. 중요한 선택은 [결정 양식](../templates/decision.md)으로 docs/decisions에 기록한다.

## 실패·재실행·독립 검토

- 실패는 우선 제품 동작 결함, 검사기 오판/접점 결함, 환경/권한 차단, 시각 품질 미달로 구분한다. 원인을 확인하기 전에 검사 강도나 기준값을 바꾸지 않는다.
- 수정 후 실패한 검사와 영향 범위를 먼저 확인한다. 전체 회귀는 안정된 변경 묶음의 필요한 마감 시점에 실행한다. 완료되지 않은 내부 진단마다 별도 전체 회귀를 의례적으로 붙이지 않는다. 의존 지문 변화·필수 gate 요구·새 실패에 따른 재실행은 유지한다.
- 같은 환경/권한 차단은 원인 확인용 최소 조회까지만 한다. 코드/환경/권한·입력·재현 조건의 변화나 새 진단 가설 없이 같은 전체 검사를 반복하지 않는다. 차단 증거·영향 범위·재개 조건을 남기고 독립적인 작업을 계속한다. 미해결 필수 검사가 있으면 해당 범위는 BLOCKED로 남긴다.
- 검토 지적은 **필수 수정**과 **후속 제안**으로 나눈다. 필수에는 현재 요구/불변식, 구체적 실패 조건 또는 판정 불가 근거, 최소 수정·재검증 방법이 있어야 한다. 필수는 실제로 확인된 결함, 명시된 완료 조건 위반, 데이터 손실·복구 불가 위험으로 한정한다. 그 밖의 미실행 위험·추가 검사 제안·취향·미래 범용화는 후속 목록에 넣고 우선순위는 사용자가 정한다. 같은 주제 검토는 설계 1회 + 마감 1회까지이며, 3회째는 사용자에게 먼저 묻는다(2026-11-02).
- design-reviewer는 설계/소유권, validator-client는 요구·동작/증거, algorithm-tester는 계산 불변식·경계·반례를 담당한다. 역할별 의무는 유지하되 중복 지적은 같은 ID로 묶고 각 역할의 해소 여부를 기록한다. 메인이 필수 지적을 임의로 후속으로 낮추지 않는다.

## 진행 보고와 시간 기록

보고는 사용할 수 있게 된 결과, 현재 진행 중인 일, 다음 완료 조건, 차단/대기를 중심으로 한다. 서브에이전트는 역할과 요청/완료 상태로 설명하고 내부 ID·검사 개수를 제품 진척으로 대신하지 않는다. 최종 응답은 실제 완료/차단/미실행을 구분하며 실행 중인 도구나 등록 작업이 없으면 계속 작업 중이라고 말하지 않는다.

기존 리뷰/실행 기록에 첫 사용 가능한 결과 시점과 구현·검사·검토 대기의 시작/끝을 가능한 범위에서 남긴다. 측정하지 못한 구간은 미측정으로 둔다. 병렬 구간을 합산해 총 경과 시간으로 표현하지 않는다. 전체 검사 재실행은 원인과 바뀐 의존성을 한 줄로 기록한다. 이 기록을 위해 별도 계측 프레임워크를 만들지 않는다.

## 출력과 단계 재사용

도구는 원본 로그/전체 JSON을 output에 보존하고 기본 응답은 상태·검사별 상태·첫 실패·생략 개수·보고서 경로만 출력한다. 먼저 요약을 읽고 필요한 실패 항목만 조회한다. `python3 Tools/Verify/report.py <보고서> --check <검사명>`으로 좁히며 `--verbose`는 원문 전체가 필요한 경우에만 사용한다. 출력 축소는 검사 수/강도나 저장 증거를 줄이는 옵션이 아니다.

자산 schema2의 `init --reuse-from`은 [단계별 의존성](../design/efficiency-013.md)에 따라 새 job에 검증 복사한다. 원본·완료 목록·계약·해시는 매번 검사하고 처리 단계 의존성이 같을 때만 Blender 출력을 재사용한다. Unity 실행/최종 게임 검증은 이 캐시가 대체하지 않는다. gate의 현재 실행 의존성·원자료 요구, hook·설치 baseline과 독립 검토는 유지한다. gate 정적 재사용과 Unity 화면 범위는 [034 규칙](verification-gates.md)을 따른다.

## 도구별 연결

Tripo 정적 소품 요청은 A0에서 [생성 기준](tripo-generation-standard.md)과 [자산 작업 양식](../templates/ai-3d-asset-package.md)을 작성한다. 공급자 옵션과 프롬프트·최종 Unity 실측을 분리하고 자산별 근거/예외·버전·비용/공개 범위를 동결한다.

외부 AI 3D 자산은 [자산 워크플로우 A0~A5](ai-3d-assets.md)와 [자산 하네스 설계](../design/ai-3d-asset-harness.md)를 적용한다. 생성/처리/Unity 후보/시각 인수/채택 등록을 구분한다. Tripo CLI와 기존 Unity CLI를 기본으로 유지하며 참고 저장소 설치를 자동 실행하지 않는다. [012 최소 전송 도구](../../Tools/Assets/README.md)는 부분 구현이며 별도 실행한다. 전체 자산 gate/등록은 미구현이고 기존 local/gate는 자산 시험을 실행하지 않는다. 자산 상태·schema·등록/연결 구현은 L2로 사전 검토한다.

장면·자산을 코드로 다시 만드는 빌더는 [장면 빌더 공통 규칙](scene-builders.md)(소유·순서, 저장 뒤 다시 열어 확인, GUID 유지, 부작용 파일 되돌리기, 046 내용 교훈)을 따른다(2026-11-03, 048).

맵 작업은 [산출물 일관성 규격](map-artifact-contract.md)과 [하네스 설계](../design/맵-워크플로우-하네스-설계.md)의 단계별 필수 증거를 함께 확인한다. 작업 묶음 양식은 L1/L2 설계 브리핑을 대체하지 않는다. 미구현 맵 검사를 기존 local/all PASS로 대체하지 않는다.

레퍼런스 이미지 기반 설계에는 [시각 설계 절차](reference-design.md)를 함께 적용한다. 원본 입력과 결과 비교를 기록하고 문서 검사와 요구 충족·런타임 검증을 구분한다.

Codex: `.agents/skills/ds-workflow/SKILL.md`를 읽어 실행한다. 이 파일과 AGENTS의 명시적 위임 규칙에 따라 collaboration 서브에이전트를 사용한다. 역할 MD 자체가 Codex 에이전트를 자동 등록하지는 않는다. 새 스킬이 목록에 없으면 경로로 읽는다.

Claude: CLAUDE.md를 통해 같은 계약을 읽고 `.claude/agents/`의 역할을 사용한다. 2026-11-02 Claude Code 세션에서 세 역할이 서브에이전트로 인식됨을 확인했다([040](../design/agent-handover-040.md)). 전역 설정이나 자동 주입 훅에 의존하지 않는다.

독립 검토 도구가 없으면 검토 상태를 BLOCKED로 기록하고 가능한 구현·정적 확인을 계속한다. 자기 검토를 독립 검토로 표시하지 않는다. 사용자 승인을 매 단계 요청하는 절차가 아니다.

## 완료 기준

범위 안의 구현, 필수 검사, 독립 검토 지적 해소, 관련 문서 갱신까지 완료해야 한다. 검증 불가 항목은 사유와 다음 조치를 명시한다. 커밋·원격 게시·프로젝트 외 기록은 이 절차로 자동 승인되지 않는다.

## 자동 검사 연결

[검사 누락 방지 hook](verification-gates.md)을 사용한다. 변경 작업 종료 전 `/usr/bin/python3 Tools/Verify/gate.py check`를 실행하고 검사별 RUN/REUSE와 선택 이유·원자료를 확인한다. Git hook은 이 저장소에 활성화했고 Codex Stop은 프로젝트 정의를 신뢰한 환경에서 작동한다. 독립 리뷰와 변경에 필요한 실제 Unity 검증을 유지한다.

## 상태와 근거 갱신

현재 진행과 남은 일은 [현재 상태](../현재상태.md), 개별 실행의 시각·범위·지문은 해당 docs/reviews와 원자료가 담당한다. 설계 문서에는 계약과 구현 경계를 두고 과거 리뷰의 PASS를 현재 소스의 PASS로 다시 쓰지 않는다. 완료한 리뷰의 미래형 마감 문장은 실제 결과로 종결한다.

`report.py --check`는 선택한 하위 검사 상태를 반환한다. 전체 보고서가 FAIL/BLOCKED/NOT_RUN인 경우에도 일부 항목은 PASS일 수 있으므로 전체 상태와 미실행 범위를 함께 확인한다. 출력 요약은 기계 검증·독립 검토·사람의 최종 채택을 대체하지 않는다.
