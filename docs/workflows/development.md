# 개발 워크플로우

## 작업 분류

| 규모 | 조건 | 필수 절차 |
|---|---|---|
| L0 | 문서·수치·기존 타입 내부 수정 | 관련 원본 확인 → 수정 → 영향 범위 검사 → 결과 기록 |
| L1 | 여러 파일에 걸친 새 기능/입력 흐름 | 간단 설계 → 구현 → 검사 → validator-client 독립 검토 → 지적 수정 |
| L2 | 상태 소유권, 데이터 스키마, 도메인 경계, 소스 원본 변경 | 설계 브리핑 → design-reviewer 독립 검토 → 구현 → 검사 → validator-client 독립 검토 |

문서·설정만 바꾸는 워크플로우 도입은 L1로 다룬다. 게임 구조의 재설계를 포함하지 않는다. 타입 수가 많다는 이유만으로 L2로 올리지 않는다.

## 실행

1. 요청 범위, 관련 기획과 실제 코드, 완료 기준을 확인한다. 사용자 결정과 실험안을 구분한다.
2. L1/L2는 [설계 양식](../templates/design-brief.md)을 복사해 docs/design에 작업 문서를 작성한다. 기존 규칙 원본이 있으면 갱신하고 중복 문서를 만들지 않는다.
3. L2는 [설계 검토 계약](design-reviewer.md)을 읽는 독립 서브에이전트에게 브리핑과 관련 파일만 전달한다. 읽기 전용으로 검토한다. 수정 필요 지적을 해소한 뒤 구현한다.
4. 메인이 구현을 담당한다. 리뷰어는 파일을 수정하지 않는다. 허용된 개인 폴더 밖에 기록하지 않는다.
5. 구현 중에는 영향 단위 시험과 `python3 Tools/Verify/run.py local`을 먼저 실행한다. 전체 게임 검사를 불완전한 중간 코드에서 반복하지 않는다.
6. L1/L2는 [구현 검토 계약](validator-client.md)에 따라 독립 코드 검토·수정을 먼저 수행한다. 이 시점의 미실행 통합/Unity 검사는 NOT_RUN이다. 계산·배치·회복 공유 변경은 [로직 검증 계약](algorithm-tester.md)도 적용한다.
7. 선행 지적 해소 뒤 영향 단계 통합 시험 → 필요한 최종 `all --screens`를 실행한다. 런타임 변경의 Unity 컴파일·규칙·실제 프레임/입력/캡처 의무는 유지한다. 수정 후에는 해당 지적과 영향을 재확인하며, 이미 통과한 필수 검사의 의존 지문이 바뀌거나 새 실패/우려가 생기면 다시 실행한다. '한 번만 실행'을 검사 생략 규칙으로 사용하지 않는다.
8. 같은 독립 검토자가 최종 실행 증거와 미실행 범위를 확인한다. 코드 검토 PASS만으로 작업 완료를 선언하지 않는다.
9. [검증 양식](../templates/verification.md)으로 docs/reviews에 결과를 기록한다. 필요한 원본 문서와 상태 링크를 갱신하고 local·최종 gate를 실행한다. 중요한 선택은 [결정 양식](../templates/decision.md)으로 docs/decisions에 기록한다.

## 출력과 단계 재사용

도구는 원본 로그/전체 JSON을 output에 보존하고 기본 응답은 상태·검사별 상태·첫 실패·생략 개수·보고서 경로만 출력한다. 먼저 요약을 읽고 필요한 실패 항목만 조회한다. `Tools/Verify/report.py <보고서> --check <검사명>`으로 좁히며 `--verbose`는 원문 전체가 필요한 경우에만 사용한다. 출력 축소는 검사 수/강도나 저장 증거를 줄이는 옵션이 아니다.

자산 schema2의 `init --reuse-from`은 [단계별 의존성](../design/efficiency-013.md)에 따라 새 job에 검증 복사한다. 원본·완료 목록·계약·해시는 매번 검사하고 처리 단계 의존성이 같을 때만 Blender 출력을 재사용한다. Unity 실행/최종 게임 검증은 이 캐시가 대체하지 않는다. 기존 gate의 현재 지문 증거 요구·hook·baseline과 독립 검토는 그대로 유지한다.

## 도구별 연결

Tripo 정적 소품 요청은 A0에서 [생성 기준](tripo-generation-standard.md)과 [자산 작업 양식](../templates/ai-3d-asset-package.md)을 작성한다. 공급자 옵션과 프롬프트·최종 Unity 실측을 분리하고 자산별 근거/예외·버전·비용/공개 범위를 동결한다.

외부 AI 3D 자산은 [자산 워크플로우 A0~A5](ai-3d-assets.md)와 [자산 하네스 설계](../design/ai-3d-asset-harness.md)를 적용한다. 생성/처리/Unity 후보/시각 인수/채택 등록을 구분한다. Tripo CLI와 기존 Unity CLI를 기본으로 유지하며 참고 저장소 설치를 자동 실행하지 않는다. [012 최소 전송 도구](../../Tools/Assets/README.md)는 부분 구현이며 별도 실행한다. 전체 자산 gate/등록은 미구현이고 기존 local/gate는 자산 시험을 실행하지 않는다. 자산 상태·schema·등록/연결 구현은 L2로 사전 검토한다.

맵 작업은 [산출물 일관성 규격](map-artifact-contract.md)과 [하네스 설계](../design/맵-워크플로우-하네스-설계.md)의 단계별 필수 증거를 함께 확인한다. 작업 묶음 양식은 L1/L2 설계 브리핑을 대체하지 않는다. 미구현 맵 검사를 기존 local/all PASS로 대체하지 않는다.

레퍼런스 이미지 기반 설계에는 [시각 설계 절차](reference-design.md)를 함께 적용한다. 원본 입력과 결과 비교를 기록하고 문서 검사와 요구 충족·런타임 검증을 구분한다.

Codex: `.agents/skills/ds-workflow/SKILL.md`를 읽어 실행한다. 이 파일과 AGENTS의 명시적 위임 규칙에 따라 collaboration 서브에이전트를 사용한다. 역할 MD 자체가 Codex 에이전트를 자동 등록하지는 않는다. 새 스킬이 목록에 없으면 경로로 읽는다.

Claude: CLAUDE.md를 통해 같은 계약을 읽고 `.claude/agents/`의 역할을 사용한다. 새 정의의 앱 내 자동 인식은 별도 확인 대상이다. 전역 설정이나 자동 주입 훅에 의존하지 않는다.

독립 검토 도구가 없으면 검토 상태를 BLOCKED로 기록하고 가능한 구현·정적 확인을 계속한다. 자기 검토를 독립 검토로 표시하지 않는다. 사용자 승인을 매 단계 요청하는 절차가 아니다.

## 완료 기준

범위 안의 구현, 필수 검사, 독립 검토 지적 해소, 관련 문서 갱신까지 완료해야 한다. 검증 불가 항목은 사유와 다음 조치를 명시한다. 커밋·원격 게시·프로젝트 외 기록은 이 절차로 자동 승인되지 않는다.

## 자동 검사 연결

[검사 누락 방지 hook](verification-gates.md)을 사용한다. 기존 local 검사에 더해 변경 작업 종료 전 `/usr/bin/python3 Tools/Verify/gate.py check`를 실행한다. Git hook은 이 저장소에 활성화했고 Codex Stop은 프로젝트 정의를 신뢰한 환경에서 작동한다. 독립 리뷰·실제 Unity 검증 의무를 줄이지 않는다.
