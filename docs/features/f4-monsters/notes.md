## 예전 코드에서 확인한 것

- 유형 고르기: `type ??= d.types[Rng.Next(d.types.Length)]` — 100칸 목록에서 고르게 뽑아 사실상 가중치. 새 구조는 가중치 배열(`typeWeights`)로 같은 뜻을 짧게 쓴다.
- 정규 생성 셈 `Spawned`는 `extra`(버닝) 생성을 세지 않는다. M2 "생성 적 수"를 정규 생성으로 본 근거. 버닝 추가는 웨이브 6에서 약 130마리라, 넣으면 웨이브 6~10이 +34 곡선을 벗어난다.
- 버닝 추가 간격 `(Duration − 4) / max(1, count − 1) / 2`, 낼 수 `min(ceil(10 / 간격), floor((min(Elapsed, 시작 + 10 − 0.0001) − 시작) / 간격) + 1)`, 방향 `burningAngle + (번호 % 2) × π + (난수 − 0.5) × 0.3`, 유형 `난수 < 0.8 ? 일반 : 돌진`. `burningAngle`은 웨이브 시작 때 무작위(`DSGame.Run.cs`).
- 돌진형의 접촉 공격: `UpdateEnemy`에서 돌진형은 `best < 280 && cd <= 0`이면 집결하고 돌아가므로, 접촉 분기(`best ≤ 반지름 + 5 && cd <= 0`)에 닿는 일이 없다. 그래서 돌진형은 접촉 공격을 하지 않는 것으로 옮긴다(가정 MA8).
- 자폭: 점화가 끝나면 `e.hp = 0`으로 바로 지워 `Hit`를 거치지 않는다 → 처치 수에 들지 않는다(MA9). 쓰러진 적은 `UpdateEnemy` 첫 줄에서 돌아가므로 점화 중에 쓰러지면 터지지 않는다.
- 자폭 무리 생성: `bomberSpawnCount++ % 6 == 0`일 때 새 방향, 나머지는 `± 0.12`(폭 0.24).
- 재배치 대기 0.5초는 실제로 옮긴 뒤에만 걸린다(`if (recycleCooldown > 0 || eligible.Count == 0) return;` 뒤에 설정).
- 중장갑의 특별 규칙은 접촉 대기 1.8초(`e.cd = e.type == "armored" ? 1.8f : 1`)와 HP 막대 크기(`DSWorld.cs`)뿐이다. 피해 감소는 없다(MA7).
- 모든 적의 첫 대기는 1초(`DSData.cs` `Enemy.cd = 1`).
- 예전 생성 거리·재배치 상자는 화면 상수 1180×748 기준이다. F1이 이것을 "보이는 바닥 영역"으로 바꿨으므로 재배치도 같은 영역의 반폭·반높이를 쓴다.

## 판정기와 기록기 설계 메모

- `tools/playable.py`의 `report.json`에는 단계 통과·실패만 있고 값이 없다. M2·M3·M5·M7의 값을 콘텐츠 대기열이 표로 대조하려면 값이 남아야 해서, 기록기(에디터 전용)가 JSON 파일을 쓰고 판정기가 읽는다. 기본 출력 폴더 `Logs/playable/latest/`는 판정 시작 때 비워지므로 매번 새 기록이 된다.
- 경로 단계 id는 G1~G8 그대로여야 해서(F1 AC3) 판정 뒤에 "기록 쓰기" 단계를 더할 수 없다. 그래서 기록기가 웨이브 끝·판 끝마다 파일을 다시 쓴다.
- 웨이브 끝 값은 `RunModel.Phase`가 Battle에서 바뀌는 순간 구독으로 읽는다. 매 프레임 살피면 20배 시간에서 봇이 같은 프레임에 다음 웨이브를 눌러 정비 화면을 놓칠 수 있다. 행동별 수는 `MonsterModel`의 이번 웨이브 셈에서 읽는다(살아 있는 몬스터를 프레임마다 보면 큰 프레임에서 놓칠 수 있다).
- M7을 20배 시간으로 재면 한 프레임에 걸음이 20배 들어가 사람이 보는 프레임 시간이 아니다. 그래서 마지막 웨이브만 1배로 돌린다(`UseRealTimeAtWave`). 예전 하네스 규칙(핵심 규칙 1절)대로 `runInBackground`를 켠다 — 실행 중 값(`Application.runInBackground`)이라 Play가 끝나면 프로젝트 설정은 그대로다.
- 판정 기준을 최대값이 아니라 95백분위로 둔 이유: 에디터의 한 번 튀는 프레임(GC, 창 다시 그리기)으로 판정이 흔들리지 않게. 최대값·평균도 기록에 남긴다.
- 흐름 경로 LOAD·SHOW가 낮은 적 수 배율을 쓰는 이유: F1 임시 기본 무기(4명 × 피해 13 × 공격 배수, 0.7초)는 가만히 서서 처치 초당 약 4.3마리(웨이브 1, 적 HP 14)라 웨이브 2 이후 배율 1로는 버티지 못한다(예상: 웨이브 2~3에서 짐. 추측 — 구현에서 잰다). 그래서 버닝 타임·5종 동시 화면은 배율을 낮춰 닿게 하고, 생성 수는 "실행 = 데이터" 판정으로 본다. M2·M3 목표는 데이터 판정과 G7(배율 1)이 본다.
- 생성 난수를 유형·자리 두 갈래로 나눈 이유: 움직일 때 방향 뽑기가 난수를 더 쓰므로, 한 갈래면 같은 시드라도 움직임에 따라 유형 순서가 달라진다. 두 갈래면 M3·생성 수가 시드에만 달린다.
