# 핵심 규칙 (1쪽)

> art 팩 규칙(2D·3D 공통). 2026-11-03 3dkit `workflows/`에서 팩 구조로 옮겼다. 설치하면 프로젝트의 `.ai/rules/art-core-rules.md`가 된다.

작업을 시작할 때 이 문서를 먼저 읽는다. 다른 워크플로우 문서와 부딪히면 이 문서를 따른다. 이전 프로젝트의 핵심 규칙(2026-11-02 하네스 회고에서 만들고 046~050에서 다듬음)을 새 프로젝트용으로 다시 썼다. 각 규칙이 왜 생겼는지는 art 팩 스킬의 `references/교훈-이식.md`에 있다.

## 0. 만드는 일이 먼저다

사용자 원문(2026-11-02): "전체 맵을 구축하는걸 원하는데, 지금 뭔가 계속해서 검증이랑 이상한 테스트?를 하는느낌". 이전 프로젝트에서는 검증 도구를 키우다가 게임 콘텐츠가 밀린 일이 반복됐다.

- 게임·미술 작업은 결과물을 먼저 만들어 사용자에게 보여 준다. 검증은 컴파일, 짧은 Play 1회, 사용자 직접 플레이로 끝낸다.
- 독립 검토, 전체 Play, 새 검사 도구는 사용자가 요청하거나 커밋 전 gate가 요구할 때만 한다.
- 검사가 실패하면 먼저 게임 결함인지 검사 결함인지 나눠 보고한다. 검사 도구를 고치는 작업은 사용자에게 묻고 시작한다.
- 하네스는 콘텐츠와 함께 키운다. 하네스 설계도(3d-art 팩 스킬의 `references/harness-blueprint.md`)의 단계(H0~H4)를 지금 필요한 것까지만 만든다.
- 적용 범위: 아트 작업과 키트 도구는 이 0절과 3절을 따른다. 게임 C# 변경은 프로젝트의 코드 검토 규칙(예: `test-before-claim`, validator-client)을 따른다. 키트 도구의 계산을 바꿀 때는 자체 시험에 반례를 넣어 실제로 돌린다. 이것이 algorithm-tester를 대신한다.
- 다음 할 일을 제안할 때는 게임에 들어가는 일을 앞에 둔다.

## 1. 검증은 3단계, 기본은 짧은 단계

| 단계 | 내용 | 언제 |
|---|---|---|
| 빠른 확인 | 컴파일, 정적 검사, 도구 자체 시험. Play 없음 | 문서·도구만 바뀜 |
| **짧은 Play (기본)** | 1~2분. 시작 → 이동 → 정지 → 콘솔 확인 → 정리, 화면 1장 캡처 | 작업 중 모든 게임·시각 변경 |
| 전체 Play | 게임 한 판 전체, 부하, 화면비 | **단계 마감 1회.** 게임 동작 파일이 마지막 전체 PASS 이후 바뀐 경우만 |

- 전체 Play 실행기는 실행 이유(`FULL_REASON="<이유>"`)가 없으면 스스로 멈추게 만든다. 실행 이유는 기록으로 남긴다.
- 화면 확인·측정용 Play 스크립트를 그때그때 새로 짜지 않는다. 측정 도구(설계도의 `probe`) 하나를 쓰고, 없는 옵션만 그 도구에 더한다.
- Play 중 프레임·성능을 잴 때는 `PlayerSettings.runInBackground`를 켜고 끝나면 원래대로 돌린다. 끄고 재면 편집기가 백그라운드에서 느려져 3fps 같은 값이 나온다. 게임을 그리는 창은 도킹된 Game 창 하나여야 한다.
- 시각·내용 변경이 큰 단계는 마감 보고에 **성능 한 줄**(그리기 호출·set-pass·삼각형·그림자·렌더 시간, 측정 명령)을 넣고 같은 기준으로 잰 이전 값과 나란히 적는다. 기준은 생산 팩의 성능 규칙(3D: `.ai/rules/3d-performance.md`).
- 0.2~0.5초짜리 순간 효과는 정지 캡처 1장으로 판정하지 않는다. 연속 캡처나 상태 숫자(효과 수·종류)로 본다.
- 검증은 짧게 하되 빼지 않는다. 문서·도구·코드를 바꾼 뒤에는 무엇을 어떻게 확인했고 결과가 어땠는지 보고에 적는다. 확인하지 못한 것은 "미확인"으로 따로 적는다.

## 2. 증거는 "게임 동작"과 "보이는 것"으로 나눈다

- 전체 PASS를 기록할 때 게임 동작 파일(런타임 코드·장면·데이터·설정)과 시각 파일(텍스처·재질·셰이더·모델·프리팹·애니메이션)의 해시를 따로 남긴다.
- 시각 파일만 바뀌면 게임 동작 증거는 다시 쓴다. 짧은 Play 캡처와 사용자 확인으로 충분하다.
- 시각 증거는 실제로 캡처한 기록만 인정한다. 화면 없는 실행은 게임 동작 증거만 된다.
- 검사 도구만 바뀌면 그 도구의 자체 시험만 다시 돌린다.
- 이 분리는 비주얼 반복이 많은 이 프로젝트에서 특히 중요하다. 셰이더·조명을 바꿀 때마다 전체 Play를 돌리지 않는다.

## 3. 검토는 주제당 최대 2회

- 같은 주제의 독립 검토(Codex 등)는 **설계 1회 + 마감 1회**까지만 한다. 3회째가 필요하면 먼저 사용자에게 묻는다.
- 적용 범위: 이 상한은 아트 작업과 키트 도구의 독립 검토에 적용한다. 게임 코드의 설계·구현 검토(`design-reviewer`, `validator-client`, `spec-reviewer`)는 프로젝트의 코드 검토 규칙(작업 규모 규칙)을 따르고 이 상한으로 세지 않는다. 코드 검토에서 FAIL 뒤 고쳐 다시 받는 확인을 "3회째라 금지"로 읽지 않는다.
- **필수 수정**은 다음 셋으로 한정한다. 나머지 가능성과 추가 검사 제안은 후속 목록으로 보내고, 우선순위는 사용자가 정한다.
  - 실제로 확인된 결함
  - 명시된 완료 조건의 위반
  - 데이터 손실이나 복구 불가 위험
- 지적은 모아서 한 번에 고친 뒤 마감 검토를 받는다. 지적 하나 고칠 때마다 전체 Play를 다시 돌리지 않는다.
- Codex 검토 결과 파일 이름은 `<주제>-rNNN.md`로 쓴다(hook이 횟수를 센다).
- **수정 확인 검토**: 마감 검토가 필수 수정을 냈으면, 고친 뒤 같은 검토자(들)에게 수정 확인을 한 번 받는다. 위 상한에 세지 않는다.
  - 입력은 지적 원문, 고친 내용(파일·diff), 재현 방법뿐이다. 질문은 둘: 지적마다 고쳐졌는가(재현이 이제 막히는가, 반례 시험이 들어갔는가),
    고치면서 새로 깨진 것이 있는가. 범위 밖의 새 지적은 후속 목록으로만 받는다.
  - 결과 파일 이름은 `<주제>-fix-rNNN.md`(hook은 별도 주제로 센다).
  - 수정 확인은 **한 번**이다. 수정 확인에서도 필수 수정이 남으면 고친 뒤 멈추고, 남은 것과 고친 것을 보여 주고 사용자에게 묻는다(자동으로 다음 회차를 열지 않는다). 사람에게 물을 수 없는 자동 실행 단계에서는 `partial`로 끝내지 말고 열린 질문으로 올린다 — 일을 시킨 쪽이 한 번 더 열지 정한다.
  - 보고에는 마감 검토 판정과 수정 확인 판정을 둘 다 적는다. 수정 확인 없이 "고쳤다"로 마감하지 않는다.

## 4. 단계마다 새 대화

- 단계가 끝나면 [인수인계 양식](../templates/art-handoff.md)으로 현재 상태(프로젝트의 `docs/현재상태.md`)에 인수인계를 쓴다. 새 세션은 아래 기준을 넘었을 때만 제안한다.
- 기준은 프로젝트 설정 `harness.context`다. `warn_tokens`를 넘으면 알리고, **`new_session_tokens`를 넘은 상태에서 새 큰 작업(새 단계, 여러 파일 구현, Play 여러 번)을 받으면 시작하기 전에 인수인계를 쓰고 새 세션을 먼저 제안한다.** 기준 아래에서는 새 세션을 제안하지 않는다. 키트 기본값은 25만/30만이고, 기준은 컨텍스트 창의 약 50%로 잡는다(예: 100만 토큰 창이면 45만/50만). 도구를 부를 때마다 전체 맥락을 다시 읽어 캐시 읽기가 비용의 대부분이 된다(이전 047 세션: 캐시 읽기 약 1.21억 토큰).
- 긴 실행은 백그라운드로 돌리고 완료 알림을 기다린다. 상태를 짧은 간격으로 반복 조회하지 않는다. 기다리는 반복문은 출력 모양(마지막 줄 등)이 아니라 기다리는 건수와 시간 상한으로 끝낸다.
- 여러 확인은 스크립트 하나로 묶어 판정에 필요한 줄만 출력한다.
- 큰 이미지는 하위 에이전트가 보고 메인은 결론만 받는다.

## 5. 규칙은 늘리기만 하지 않는다

- 검사를 하나 추가할 때 뺄 수 있는 검사도 함께 적는다.
- 단계 회고에서 비용이 큰데 결함을 한 번도 잡지 못한 검사는 빼기 후보로 사용자에게 제시한다. 실제로 빼는 것은 다시 넣을 필요가 없다고 확실할 때만 한다.
- 새 규칙은 가능하면 문서 문장보다 도구 기본값이나 hook으로 넣는다.

## 6. 사용자가 먼저 본다

- 시각·체감 변경은 짧은 Play 캡처나 직접 플레이로 사용자에게 먼저 보여 준다. 자동 판정과 독립 시각 판정은 그 뒤에, 필요한 것만 한다.
- 보여 주기 전에, 그리고 "완료"라고 쓰기 전에 **캡처를 직접 열어 본다.** 캡처 파일이 생긴 것, 미리보기·시험 장면이 맞는 것, 코드 리뷰가
  통과한 것은 게임 화면 확인이 아니다. 일을 시킨 쪽(디렉터, 메인 세션)도 넘겨받은 캡처를 직접 연다 — 단계 세션의 "확인함"을 옮겨 적지 않는다.
  보고에는 **본 캡처 목록**(경로와 본 것)을 넣고, 열지 않았거나 필요한 장면이 찍히지 않은 것은 "미확인"으로 따로 적는다.
  출처 사례: 이어 붙인 미리보기만 보고 게임 캡처를 열지 않은 채 "완료"로 보고해, 끊겨 보이는 길을 사용자가 먼저 발견했다.
- **사용자에게 보내는 그림 파일은 모두(시트, GIF, 영상) 만든 쪽이 완성 파일을 다시 열어 본 뒤 보낸다.** 원본 프레임이 정상이어도 내보낸
  파일은 깨질 수 있다. 애니메이션은 디코딩한 프레임을 순서대로 보고 색만이 아니라 **움직임**(의도한 동작으로 보이는가, 팔다리가 번갈아
  나오는가)을 확인한다. 출처 사례: 프레임마다 다른 색표로 저장해 색이 깨진 GIF를 그대로 보냈고("이상하게 된것 같은데"), 그 뒤에는 GIF를
  디코딩하고도 색만 봐서 다리가 움직이지 않는 달리기를 보냈다("발이 안움직이는데"). 둘 다 사용자가 찾았다.
- **보여 주는 기본 경로는 로컬 미리보기 페이지다.** 확인한 시트와 재생 파일을 담은 HTML을 만들어 사용자 컴퓨터의 브라우저로 연다.
  채팅 첨부는 보조다(출처 사례: 첨부로 보낸 시트와 GIF를 사용자가 보지 못했다 — "이미지를 볼 수 있게 해줘"). 웹에 올리거나 공유 링크를
  만드는 일은 프로젝트 `AGENTS.md`의 저장 경계를 따른다.
- 기준서·기획서보다 범위를 줄여 지시하거나 작업했으면 "기준서 번호와 다른 점"을 지시문·핸드오프·보고에 적는다([아트 결정 규칙](art-decisions.md) 5절).
- **"완료"는 기준서 표의 행 단위로 판단한다.** 기준서 3.3절 에셋 목록(과 기획서의 종류·개수 표)의 행마다 "기준 / 지금 게임 / 차이"를 적은 범위 대조표를 현재 상태 문서에 두고, 보고 직전에 파일·데이터에서 다시 세어 고친다. "완료", "전부 반영"은 모든 행의 차이가 0이거나 남은 차이를 사용자가 받아들였을 때(원문과 날짜)만 쓴다. 그 밖에는 "N행 중 M행 반영, 남은 것: …"이라고 쓴다. "게임에 있는 종류에는 다 그림이 있다"는 완료의 기준이 아니다 — 게임 데이터가 기준서보다 적을 수 있다.
  출처 사례: 기준서는 타워 4종·적 6종인데 게임 데이터에는 2종·3종뿐이었고, 진행 메모에 "첫 범위 전부 반영"이라고 적어 사용자에게도 그렇게 말했다. 사용자가 "아트까지 완료된 거지?"라고 물어 표와 대조하고서야 드러났다.
- 미술은 사용자가 아트 디렉터다. 방향·채택은 사용자가 정하고, 에이전트 제안은 제안으로 표시한다.
- 레퍼런스로 정해지는 값과 만드는 방법은 묻지 않는다. 근거와 함께 기준서에 적고 기준서 승인 때 한 번에 확인받는다. 무엇을 묻는지는 [아트 결정 규칙](art-decisions.md)을 따른다.
- 보고에서는 게임에 들어간 것, 시험 장면, 목표를 구분한다. 보고하는 개수·수치는 보고 직전에 파일·카탈로그로 다시 센다.
- 사용자의 지적과 작업 중 생긴 문제는 프로젝트 문제 기록(설정 `harness.problem_log`)에 증상 → 원인 → 조치·규칙 형식으로 바로 적는다.
- JSON 설정·카탈로그를 고칠 때는 다시 쓰기 전에 원본 형식이 그대로 유지되는지 확인한다. 형식이 바뀌면 고칠 줄만 고친다.

## 7. 유료 생성과 비용

- Tripo 등 유료 생성은 요청마다 사용자 승인 원문과 상한을 기록한 뒤 실행한다. 옛 승인을 새 에셋에 물려받지 않는다.
- 네트워크 오류 뒤 자동 재전송하지 않는다(중복 과금 위험). 먼저 상태를 조회한다.
- API 키는 출력·기록하지 않는다.
