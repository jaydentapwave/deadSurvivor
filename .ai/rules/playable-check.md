# 플레이 가능 판정 — 한 판이 처음부터 끝까지 도는가

"기능이 다 구현됐다"와 "켜서 한 판이 된다"는 다르다. 기능마다 검사를 통과해도 화면이 이어지지 않거나, 지고 나서 다시 시작이 안 되는 채로 끝날 수 있다.
이 프로젝트의 **끝났다는 기준**은 판정 경로가 통과하는 것이다. 레포 규칙이 있으면 그것이 우선이다.

- 상태: 새 규칙(킷 0.17.0). 도구는 실제 에디터의 명령 응답 형식에 맞춰 짰고 가짜 명령으로 시험했다. 실제 게임의 한 판을 끝까지 밟은 검증은 아직 없다. 처음 쓰는 프로젝트에서 어긋나는 점이 나오면 이 문서와 도구를 고친다.

## 무엇으로 판정하는가

```bash
python3 -B ./tools/playable.py            # 경로 전체. 0 통과, 1 실패(끊긴 단계 출력), 2 돌릴 수 없음
python3 -B ./tools/playable.py --check    # 경로 파일 형식만(에디터를 건드리지 않는다)
python3 -B ./tools/playable.py --until G3 # 만드는 중: 그 단계까지만
```

- 경로 파일: `./tools/playable/route.json`. 게임 기획서(`docs/game/gdd.md`)의 "플레이 가능 판정 경로" 표와 **단계 번호(G1 …)가 같아야 한다.** 표에 있는 단계를 경로에서 빼거나 합치지 않는다. 기획서가 없는 프로젝트는 "시작 화면 → 한 판 시작 → 끝(이김·짐) → 다시 시작"을 최소 경로로 삼는다.
- 결과: `./Logs/playable/latest/report.json`과 단계별 캡처. 실패하면 끊긴 단계의 화면이 `-fail.png`로 남는다.
- 에디터가 떠 있어야 한다(`tools/editor_ready.py`). 판정은 Play를 켜고 끝나면 반드시 끈다. 이미 Play 중이면 끄고 새로 시작하므로, 사람이 에디터에서 플레이하는 동안에는 돌리지 않는다. 테스트와 다른 에디터 명령도 같다([사람이 플레이하는 에디터](test-before-claim.md)).
- 종료 코드 2(돌릴 수 없음)는 게임의 실패가 아니다. 통과로도 실패로도 적지 않고 `blocked`와 이유를 적는다.

## 판정용 진입점

경로의 `do`·`wait`·`expect`는 C# 식이다. 게임이 **판정용 진입점** 하나를 내놓고 경로는 그것만 부른다.

- 위치와 이름: `Assets/Game/02.Scripts/` 아래 정적 클래스 `PlayableProbe` 하나(레포의 폴더 규칙이 정한 자리). `#if UNITY_EDITOR`로 감싸 빌드에 들어가지 않게 한다.
- **읽기**: 지금 어느 화면인가(`PlayableProbe.Screen`), 한 판의 상태(진행 중·이김·짐), 기획서 목표값을 재는 데 필요한 수(점수, 남은 목숨, 지난 시간).
- **조작**: 사람이 하는 입력과 **같은 길**을 탄다. 버튼은 그 버튼의 `onClick`이나 Presenter의 공개 메서드를 부른다(화면 좌표 클릭은 에디터 창이 포커스를 잃으면 UI 버튼을 못 누른다). 게임 안 조작은 입력 처리가 받는 것과 같은 명령(점프, 이동, 놓기)을 넣는다.
- **한 판 끝내기**: 이기는 길과 지는 길을 각각 실제 규칙으로 끝까지 간다. 자동 플레이(정해진 입력 순서나 단순한 규칙 봇)를 진입점에 두고, 난수는 고정 시드를 받게 한다. 시간이 오래 걸리면 경로의 `time_scale`로 줄인다.

하지 않는 것:

- 승패 상태를 직접 써 넣기(`state = Win`), 결과 화면을 바로 띄우기. 규칙을 거치지 않은 통과는 판정이 아니다.
- 판정 때만 타는 분기를 게임 코드에 넣기(`if (probe) …`). 진입점은 게임을 부르기만 하고, 게임은 진입점을 모른다.
- 판정을 통과시키려고 경로의 단계나 확인을 지우기, `timeout`을 이유 없이 늘리기, `allow_errors` 붙이기. 바꿔야 하면 이유를 보고에 적는다.

## 경로를 쓰는 법

- 단계마다 `wait`나 `expect`로 **도착을 확인**한다. 입력만 넣고 다음으로 넘어가지 않는다.
- 화면이 바뀌는 단계에는 `capture`를 둔다. 화면마다 한 번은 `"capture": "all"`로 화면비 목록(9:16, 9:19.5, 9:21, 3:4. 가로 게임이면 `sizes`를 고친다)을 찍는다. 찍힌 그림이 잘리거나 겹치지 않는지는 그림을 열어 본 쪽이 판단한다([화면 배치](screen-layout.md)). 캡처가 있다는 것만으로 화면이 맞다고 적지 않는다.
- "다시 시작" 뒤에 **두 번째 판이 시작되는 것까지** 확인한다. 첫 판만 되는 게임이 가장 흔한 구멍이다.
- 기획서 목표값 중 한 판에서 잴 수 있는 것(한 판 길이, 끝났을 때 점수 범위)은 `expect`로 넣는다.

## 언제 돌리는가

- 화면 흐름, 한 판의 규칙, 씬 구성, 시작·끝 처리를 바꾼 작업의 마무리에서. 통과를 확인하고 결과를 보고에 적는다.
- 대기열(`queue.yaml`)의 회귀 검사(`regress`)로. 앞에서 되던 한 판이 뒤 항목 때문에 끊기는 것을 잡는다.
- 첫 기능을 만들 때 경로와 진입점을 **먼저** 만든다(대기열이면 `contract` 층). 뒤 기능은 자기 화면·규칙을 경로에 이어 붙인다.

## 보고

- 통과: 밟은 단계 수, 걸린 시간, 캡처 폴더.
- 실패: 끊긴 단계 번호와 이유를 그대로 옮긴다. "거의 됨", "대부분 통과"라고 쓰지 않는다.
- 판정이 보지 않는 것을 같이 적는다: 손맛, 난이도, 보기 좋음, 소리. 사람이 플레이해서 볼 몫이다.
