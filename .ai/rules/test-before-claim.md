# Test-Before-Claim Rules

알고리즘 구현·수정 후 "동작합니다" / "이게 원인일 거예요" 라고 보고하기 전에 반드시 **검증 가능한 테스트 케이스로 확인**한다. 추측과 검증을 분리한다.

## Principles

- 코드를 "써놓은 것"과 "동작 확인된 것"은 다르다.
- validator-client(static review)는 알고리즘 정확성을 입증하지 못한다. 스타일·아키텍처만 본다.
- 사용자에게 런타임 테스트를 떠넘기는 건 디버그 비용을 사용자에게 전가하는 것.
- 추측은 "추측"이라고 명시. 검증된 사실과 분리해서 보고.
- 확인 수준을 섞지 않는다. 정적 리뷰 통과 ≠ 컴파일 통과 ≠ 플레이 동작 통과. 에디터를 못 돌렸으면 "컴파일 미확인", 플레이를 못 했으면 "동작 미확인"으로 보고한다.

## 적용 대상

다음 중 하나라도 해당되면 `algorithm-tester` subagent 호출 의무.

- Loop / 반복문 ≥ 1개 있는 메서드
- Branch / 조건 분기 ≥ 2개 (`if`/`switch`) 있는 메서드
- State machine, generator, parser
- Shuffle, sort, packing, BFS/DFS, graph traversal
- 입출력 형변환 (예: `int[][]` 셔플, deep copy)
- 새로 작성된 비순수 함수 (외부 상태 의존)

## 비적용

다음 작업은 tester 호출 불필요.

- View 렌더 (시각 결과는 사용자 검증 영역)
- DI 등록만 변경
- 단순 필드/속성 추가
- 주석/리네이밍/포맷팅
- 1-2줄 직선 코드 수정

## 절차

1. **메인 에이전트**가 알고리즘 구현/수정.
2. **algorithm-tester** 호출 (auto-route).
3. tester가 3-5개 케이스 검증 — 순수 로직은 standalone 추출 후 **실제 실행**, Unity 의존 코드만 hand-trace.
4. PASS면 → (아키텍처 영향 시 validator-client) → 사용자에게 결과 + 테스트 케이스 출력.
5. FAIL이면 → **메인이 직접 수정** (실패 케이스 기준) → tester 재호출.

## 사람이 플레이하는 에디터

테스트와 에디터 명령은 사람이 쓰고 있지 않은 에디터에만 보낸다. 플레이 중인 에디터에 테스트를 보내면 테스트 실행기가 장면을 저장·생성하려다 에러를 콘솔에 쏟고, 실행 하나가 걸린 채 남아 뒤 명령까지 막는다.

- 사람에게 플레이를 넘긴 뒤에는 "끝났다"는 말을 듣기 전까지 그 에디터에 테스트, 장면 변경, 스크립트 실행(`script eval`), 판정 경로(`tools/playable.py`)를 보내지 않는다. 그동안 고칠 것이 생기면 코드만 고치고, 확인은 플레이가 끝난 뒤에 한다.
- 에디터 명령을 보내기 전에 플레이 중인지 확인한다(`UnityEngine.Application.isPlaying`). 내가 켠 Play가 아니면 끄지 않고 기다리거나 사용자에게 묻는다.
- 테스트를 재시도 반복문으로 돌리지 않는다. 한 번 돌려 실패하면 출력을 읽고 원인을 가른 뒤 다시 돌린다. 백그라운드에서 되풀이되는 실행은 사람이 플레이를 시작한 뒤에도 계속 들어간다.
- 사람이 "에러가 난다"고 하면 게임 코드를 고치기 전에 Editor.log의 에러를 출처별로 나눈다: 게임 코드(스택에 `Assets/Game/`), 테스트 실행기(`TestRunner`, "Test tree is not available", "This cannot be used during play mode"), 에디터·패키지. 테스트 실행기나 에디터 쪽이면 내가 보낸 명령이 원인인지부터 본다.

## Anti-Patterns

- "이게 원인일 거예요" 추측만 하고 사용자에게 테스트 떠넘기기
- 단순 케이스 동작 확인 없이 복잡 케이스/엣지 케이스로 바로 가기
- validator-client 통과 = 알고리즘 정확성 입증이라고 착각
- "이 알고리즘은 명백하니까 테스트 불필요" 같은 자기 정당화
- 사용자가 "안 된다"고 보고할 때마다 새 가설 세우기 (테스트로 검증된 게 없는 상태에서 가설만 늘림)
- 사람이 플레이하는 동안 같은 에디터에 테스트·에디터 명령 보내기, 테스트를 재시도 반복문으로 돌리기

## Required Behavior

- 알고리즘 변경 시: `메인 구현 → algorithm-tester → (FAIL 시 메인 수정 → algorithm-tester) → 보고` 흐름 강제.
- 보고 시 검증 결과(케이스별 input → output, 실행/trace 여부)를 사용자에게 함께 제시. 사용자가 검증 과정을 확인 가능.
- 검증되지 않은 가설은 "추측" 명시. 예: "추측: ratio가 0.6이라 false일 가능성" — 검증 전이면 절대 단언 X.
- 단정형 발화("X는 Y다", "X는 Z만 가능") 전 자문: 근거가 직접 확인된 코드인가, 추측·기억인가? 추측이면 "추측:" 라벨 또는 코드 확인 후 답변. (도메인 동작 단정의 anti-pattern은 `verify-existing-code.md`의 "Domain Behavior" 섹션 참조)
- 사용자가 "동작 안 한다"고 보고하면 **가장 단순한 케이스부터** tester로 다시 검증. 새 가설 세우지 말 것.

## Good

```
사용자: "셔플 알고리즘이 작동 안 해요"
→ algorithm-tester 호출:
  - Case 1: 2병 2색 → trace → PASS
  - Case 2: 4병 4색 → trace → PASS
  - Case 3: BL 1개 + 3병 → trace → FAIL at line N (BL 색이 dest로 선택됨)
→ 메인이 line N의 dest 필터 수정
→ tester 재호출 → 전부 PASS
→ 사용자에게 보고 (트레이스 포함)
```

## Bad

```
사용자: "셔플 알고리즘이 작동 안 해요"
→ "ratio 임계값이 문제일 것 같습니다" (추측)
→ 임계값 변경
→ "이번엔 attempts가 부족할 것 같습니다" (또 추측)
→ attempts 증가
→ 5번 추측 반복, 단 한 번도 실제 케이스 검증 X
```
