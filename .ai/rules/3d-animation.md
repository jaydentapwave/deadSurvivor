# 동작 제작 규칙 (3d-art 팩)

캐릭터·몬스터 동작 클립(걷기, 대기, 공격, 피격 등)을 만들 때 적용한다. 핵심 규칙(`.ai/rules/art-core-rules.md`)과 아트 결정 규칙(`.ai/rules/art-decisions.md`)이 우선한다(art 팩). 모델 자체를 만드는 순서는 `/3d-art-produce`이고, 이 문서는 그 흐름에서 **동작일 때 단계마다 할 일**을 정한다.

- 제정: 2026-11-04. 계기: 걷기 클립 하나를 여섯 번 다시 만들면서 필요한 단계(동작 값 명세, 레퍼런스 자세 대조, IK 뼈대, 게임 카메라 확인, 캡처 도구 확인, 다른 클립 재확인)를 실패한 뒤에야 하나씩 찾았다. 그래서 순서를 먼저 고정하고, 프로젝트마다 다른 동작·무기는 값으로만 다룬다.
- 이 문서에는 **절차와 확인 항목**만 둔다. 동작 값(주기, 보폭, 타격 프레임)은 프로젝트의 아트 기준서 "동작" 절에만 둔다(아트 결정 규칙 1절).

## 1. 규칙 다섯 개

1. **모든 작업 단위는 같은 모양의 단계를 지난다.** 단위는 클립 하나다(`<캐릭터 id>/<클립>`). 2절의 ①~⑨를 차례로 지나고, 단계를 건너뛰지 않는다. 앞 단계로 돌아가는 것은 된다.
2. **확인 순서는 숫자 → 메인 눈 → 사용자.** 자동 검사 숫자가 통과해야 화면을 만든다. 메인이 게임 카메라로 직접 본 것만 사용자에게 보여 준다. 숫자 통과를 근거로 "잘 나온다"고 쓰지 않고, 안 본 것은 미확인으로 따로 적는다.
3. **한 번에 하나만 고치고, 고칠 때마다 저장하고 비교한다.** 시도마다 r번호를 붙이고 원본 파일(`.blend`)을 저장한다. 전후를 같은 카메라로 나란히 본다. 같은 방법이 3번 실패하면 앞 단계(①명세 또는 ②준비)로 돌아가고 사용자에게 알린다.
4. **단계 상태는 파일로 남긴다.** 3절 형식. 새 세션·하위 에이전트는 이 파일에서 이어 간다.
5. **규칙은 키트에, 값은 프로젝트에.** 특정 캐릭터·무기·도구 이름은 키트에 쓰지 않는다. 4절의 동작 종류 중 하나로 분류하고, 값은 기준서에 적는다.

## 2. 단계

`/3d-art-produce`의 모델 단계와 이름을 맞췄다. 정하는 쪽은 아트 결정 규칙 3절을 따른다.

| 단계 | 하는 일 | 산출물 | 통과 조건 | 정하는 쪽 |
|---|---|---|---|---|
| ① 명세 | 동작 종류(4절)를 고르고, 종류별 값을 기준서에서 가리킨다. 레퍼런스 프레임(영상 id·시각)을 고른다. 기준서에 값이 없으면 멈추고 기준서 개정을 제안한다 | 단계 기록의 명세 칸 | 값마다 기준서 번호와 레퍼런스 근거가 있다 | 레퍼런스 값은 에이전트, 레퍼런스에 없는 값은 사용자 |
| ② 준비 | 뼈대 점검(5.1), 장면 틀(게임 카메라·바닥·레퍼런스 판) 열기 | 뼈대 점검 결과 | 점검 항목 전부 통과 | 에이전트 |
| ③ 초안 | **핵심 자세만** 키로 넣는다(blocking). 키는 IK 컨트롤과 몸통에만 넣고 관절 각도를 직접 넣지 않는다. 핵심 자세를 **게임 카메라로** 렌더해 레퍼런스 프레임과 나란히 놓는다. 측면·정면 시트는 보조일 뿐 이 단계의 근거가 아니다. 레퍼런스가 없으면 시트에 없다고 적고 사용자에게 먼저 말한다 | 게임 각도 핵심 자세 비교 시트 1장 | 메인이 시트를 보고 자세 차이와 "각 자세가 무엇을 하는지 읽히는가"를 적었다 | 에이전트 |
| ④ 초안 확인 | 비교 시트를 사용자에게 보여 준다. 자세 고르기를 위임받았어도 시트는 보여 주고 진행한다 | 사용자 원문 | 사용자가 자세를 확인했다. 고칠 점이 있으면 ③으로 | 사용자 |
| ⑤ 제작 | 사이 프레임, 타이밍, 2차 흔들림(부착 부품·머리카락·옷) | 저장된 원본 파일 | — | 에이전트 |
| ⑥ 자동 검사 | 5.2 측정 | 측정 결과 파일 | 종류별 기준 통과 | 기준은 기준서 |
| ⑦ 엔진 반영 | 굽기 → 내보내기(5.3) → 다시 읽어 확인 → Unity 가져오기 → **이미 승인된 다른 클립과 프리팹 배율 다시 확인** | 재측정 결과 | 다른 클립·배율이 승인값 그대로 | 에이전트 |
| ⑧ 게임 화면 | 게임 카메라·게임 크기 연속 프레임 캡처, 짧은 Play(5.4) | 캡처·영상 파일(절대 경로) | 메인이 먼저 보고 문제를 적었고, 아래 "보여 주기 전 질문"에 답했다 | 에이전트 |
| ⑨ 판정·기록 | 사용자에게 보여 주고 판정을 받는다. 지적과 작업 중 문제는 프로젝트의 문제 기록에 더한다 | 사용자 원문, 문제 기록 줄 | 사용자 판정 원문 | 사용자 |

- 이동 동작의 주기·거리 값은 메시 치수를 잰 뒤 확정한다. 한 걸음 길이가 다리 길이를 크게 넘으면 발이 닿지 못해 미끄러진다. 메시 전에 제안한 값은 제안으로 두고, 빌드의 발 닿음 오차(`rig_build.py`의 `ik_reach_error_max_m`)로 확인한다.
- ④는 다 만든 뒤가 아니라 **핵심 자세 단계에서** 받는다. 다 만든 뒤에 "다리가 안 움직인다"는 지적이 나오면 ③부터 다시 해야 하기 때문이다.
- 생성 도구가 만든 동작(Tripo 등)을 쓰더라도 ①과 ⑥~⑨는 같다. ③④는 생성 결과의 핵심 프레임을 뽑아 대신한다.
- 유료 생성이 끼면 `/3d-art-produce` 5절 승인을 따른다.

## 3. 단계 기록

클립마다 프로젝트의 시험 기록 문서(예: `docs/art/lookdev/<단계>.md`) 안에 아래 표를 하나 둔다. 단계를 지날 때마다 해당 줄을 고친다.

```markdown
### 단계: <캐릭터 id>/<클립> (동작 종류: <4절 종류>, 기준 <기준서 번호>)

| 단계 | 상태 | 근거 | 날짜 |
|---|---|---|---|
| ① 명세 | 통과 | 기준서 <번호>, 레퍼런스 <영상 id> <시각> | <날짜> |
| ② 준비 | 통과 | <뼈대 점검 결과 파일> | |
| ③ 초안 | 진행 중 (r2) | <비교 시트 경로> | |
| ④ 초안 확인 | — | | |
| ⑤~⑨ | — | | |

다음 할 일: …
```

- 상태: `—`(안 함) / `진행 중 (rN)` / `통과` / `NOT_RUN`(못 함, 이유) / `되돌아감 → ①`(이유).
- 근거는 파일 경로나 사용자 원문이다. 근거 없이 `통과`로 적지 않는다.

## 4. 동작 종류

기준서 "동작" 절은 이 종류별로 값을 적는다. 새 동작은 이 중 하나로 분류한다. 맞는 종류가 없으면 종류를 더하기 전에 사용자에게 묻는다.

| 종류 | 예 | 기준서에 적을 값 | 종류별 자동 검사 | 눈으로 볼 것 |
|---|---|---|---|---|
| 반복 이동 | 걷기, 달리기, 헤엄 | 주기(초), 주기당 이동 거리, 몸 튐, 팔 흔들기·벌림 | 발 미끄러짐, 바닥 침투, 루프 이음(첫=끝), 이동 속도와 주기·거리의 일치 | 게임 카메라에서 다리·팔이 보이는가 |
| 반복 대기 | 서 있기, 숨쉬기 | 주기, 움직임 크기 | 바닥 침투·뜸(가장 낮은 점), 루프 이음 | 굳어 보이지 않는가, 이동 동작과 이어지는가 |
| 공중 이동 | 날갯짓 대기·이동, 부유 | 떠 있는 높이(몸통 뼈에 굽기), 날갯짓 주기, 몸 위아래, 숙임 | 루프 이음, 이동 속도. 발 미끄러짐·접촉은 해당 없음(날개 역할 없음). 가장 낮은 점은 뜻이 바뀐다(떠 있음이 의도, 공격 끝이 바닥을 뚫는지만 본다) | 게임 카메라에서 그림자가 몸과 떨어져 떠 보이는가, 날갯짓이 끊겨 보이지 않는가 |
| 단발 동작 | 공격, 도구 사용, 줍기, 시전 | 예비동작·타격(유효)·회복 프레임 수, 타격 프레임 번호, 무기·도구 궤적 | 시작·끝 자세가 대기와 같은가, 손에 든 물건의 몸 침투 | 타격 순간이 읽히는가, 회복이 굼뜨지 않은가 |
| 반응 | 피격, 넉백, 쓰러짐 | 길이, 밀려나는 거리, 돌아오는 자세 | 끝 자세가 대기와 같은가(쓰러짐 제외), 바닥 침투 | 무엇에 맞았는지 읽히는가 |

- 단발 동작의 시작·끝 자세를 대기와 맞춰 두면 전환이 튀지 않는다.
- 예비동작이 길수록 상대가 읽기 쉽고, 회복이 길수록 조작이 굼떠진다(7절 Cooper). 프레임 수는 레퍼런스 관찰 값으로 정한다.

## 5. 확인 항목

### 5.1 뼈대 점검 (②)

뼈대를 직접 만들 때(크레딧 0)는 키트 `rig_build.py`(엔진 하나 + 생물마다 모양 파일)를 쓰고, 에셋마다 제작 스크립트를 따로 짜지 않는다. 명령은 `.ai/rules/3d-tools.md`의 "뼈대·동작 직접 제작"에 있다. 이 도구는 동작을 제약 없는 뼈 회전 키로 굽혀 내보낸다(5.3의 굽기를 도구가 한다). 새 형태는 모양 파일만 더한다.

- [ ] 발·손에 IK 컨트롤이 있고, 무릎·팔꿈치 방향 컨트롤(pole)이 있다
- [ ] 회전 방식이 정해져 있다(쿼터니언 또는 오일러 하나로 통일)
- [ ] 기본 자세 뼈 roll·축이 정리돼 있다(엔진에서 머리를 돌리면 몸 전체가 끄덕이는 문제 예방)
- [ ] 변형하지 않는 보조 뼈는 deform이 꺼져 있다
- [ ] 장면 fps가 프로젝트 값과 같다
- [ ] 뼈에 붙는 부착 부품(장신구·장비)이 그 뼈를 따라가고, 흔들려야 하면 스프링 뼈를 쓸지 정했다

### 5.2 자동 검사 (⑥)

명령: `assets.py anim probe <id>`(Unity에서 클립을 표본으로 뽑음) → `assets.py anim metrics <probe.json> --clip C --type move|idle|oneshot|reaction`. 도구는 숫자만 내고 통과 판정은 기준서 값과 대조해 사람이 적는다.

| 항목 | 재는 법 | 기준 |
|---|---|---|
| 발 미끄러짐 | 발이 바닥 가까이(높이 기준 안) 있는 프레임에서 발의 수평 이동 | 사람 키 기준 연구 값은 높이 2.5~5cm, 미끄러짐 2.5cm. 캐릭터 키 비율로 줄여 쓴다. 사람은 21mm 미만도 알아챈다는 실험이 있으니 엄격하게 잡는다 `[방법]` |
| 바닥 침투·뜸 | 프레임별 가장 낮은 정점 높이 | 기준서 값. 전체 프레임을 먼저 읽고 나서 고친다(읽기와 쓰기를 섞으면 키가 없는 프레임만 튄다) |
| 손·물건 침투 | 손·든 물건 정점이 몸통 안에 든 비율 | 프로젝트 게이트 값 |
| 루프 이음 | 첫 프레임과 끝 프레임 뼈 자세 차이 | 반복 종류만. 0에 가까움 |
| 클립 이름·fps·길이 | 내보낸 파일을 다시 읽어 확인 | 명세와 같음 |

- 숫자 통과는 화면 판정이 아니다(1절 규칙 2).
- 새 검사는 실패가 확인된 이전 버전에 먼저 돌려, 그 실패를 잡는지 본다.

### 5.3 내보내기 (⑦)

명령: `assets.py anim fbxcheck <model.fbx> --expect <클립들> --fps <fps>`(다시 읽어 클립 이름·접두·길이·루프 이음·뼈 수를 냄).

- [ ] IK·제약으로 만든 동작은 **굽기(Bake Action)** 했다. 제약은 엔진으로 넘어가지 않는다
- [ ] 클립 하나에 액션 하나, 이름은 명세대로(재저장할 때 붙는 접두 확인)
- [ ] 단위 배율 1.0, 변환 적용, Add Leaf Bones 끔, 컨트롤 뼈가 있으면 변형 뼈만 내보냄
- [ ] 키트의 변환·내보내기 설정을 그대로 쓴다(직접 만든 설정은 축·크기가 달라질 수 있음)
- [ ] 다시 읽어 클립 이름·fps·프레임 수를 확인했다

### 5.4 엔진 화면 (⑦⑧)

명령: 다른 클립·배율 재확인은 `assets.py anim probe <id>` → `assets.py anim recheck <probe.json> <id>`(승인값과 차이, `changed` 목록). `assets.py anim frames <id> --clip C --view game|side_r|side_l|front|feet [--speed S]`(스킨 갱신을 강제한 연속 프레임), 비교 시트는 `assets.py anim sheet <out.png> --row "레퍼런스=<glob>" --row "우리=<glob>"`.

- [ ] 프리팹 배율·키가 승인값 그대로다. 다른 클립을 고쳐도 기본 자세가 바뀌면 크기 계산이 바뀔 수 있다
- [ ] 이번에 안 고친 클립(대기 등)이 그대로다
- [ ] 동작 캡처는 스킨 메시 갱신을 강제한 뒤 찍는다. 갱신 없이 찍으면 뼈는 움직이는데 몸은 멈춘 영상이 나온다. 캡처 도구가 바뀌면 움직이는 것이 확실한 클립으로 먼저 확인한다
- [ ] 짧은 Play에서 프레임 번호가 실제로 늘었다(포커스 없는 편집기는 멈출 수 있음)
- [ ] 실제 게임 장면에서 발이 바닥에 닿는다(캐릭터 컨트롤러의 여유 두께 때문에 뜰 수 있음)
- [ ] 정지 1장이 아니라 게임 카메라·게임 크기 연속 프레임이나 영상으로 본다
- [ ] **보여 주기 전 질문**(메인이 게임 각도 연속 프레임을 보고 시험 기록에 답을 적는다. S14 불합격에서 나옴):
  - 소리 없이 이 각도만 보고 무엇을 하는 동작인지 말할 수 있는가? 위아래 움직임은 위에서 잘 안 읽힌다
  - 든 물건이 몸과 구분되고, 쥐고 있는 것으로 보이는가? 무게가 자세에 드러나는가?
  - 때리는 순간이 머리나 몸에 가려지지 않는가?
  - 천·부속이 자연스럽게 따라오는가, 튀어나오는가?
  - 답이 하나라도 "아니오"면 "잘 보인다"고 쓰지 않고 그대로 보고한다

## 6. MCP로 열린 Blender를 쓸 때

- **바꾸기 전에 저장한다.** 스크립트로 바꾼 것은 되돌리기를 믿을 수 없다. 시도마다 `save_as_mainfile(copy=True)`로 r번호 파일을 남긴다.
- **한 호출에 한 변경.** 여러 뼈·여러 자세를 한 번에 바꾸지 않는다.
- **코드는 파일로 두고 MCP에서는 불러 실행한다.** 같은 코드를 매번 새로 쓰지 않고, 바꾼 값이 기록에 남게 한다.
- **화면 확인은 고정 카메라 렌더 파일로 한다.** 창 스크린샷은 각도가 매번 다르고 맥락을 많이 쓴다. 렌더 전에 카메라를 게임 각도로 고정한다.
- **결과는 dict 하나로 돌려받는다.** 측정을 여러 번 나눠 부르지 않는다.
- **비전 모델 판정은 비교·객관식으로 묻는다.** 개수 세기는 틀리기 쉽다. 영상 판정 모델은 프레임이 멈추거나 섞인 시간 오류에 둔감하다는 연구가 있으니, 동작 판정을 비전 모델 혼자 하지 않는다.

## 7. 근거

- MCP 실무 사례(1인 경험담): [DEV 글](https://dev.to/aleksandr_kossarev_e23623/ai-orchestrated-3d-asset-pipeline-from-jpeg-to-game-ready-glb-without-touching-blender-1akf) — 한 호출 한 작업, 카메라 고정, 3번 실패 시 전략 변경, 증상·원인·해결 지식 문서
- 핵심 자세 먼저, 예비동작·회복: [Cooper, *Game Anim* 발췌](https://gamedeveloper.com/production/the-12-principles-of-animation-in-video-games), [gameanim.com](https://www.gameanim.com/?p=30755)

## 8. 프로젝트가 채울 값

도구는 아래 값을 읽는다. 코드에 프로젝트 값을 넣지 않는다.

| 값 | 위치 | 없으면 |
|---|---|---|
| 역할별 뼈 이름(`hips`, `head`, `foot_l`, `foot_r`, `hand_l`, `hand_r`) | 카탈로그 에셋 `anim.bones` | Humanoid 아바타면 아바타에서 찾고, Generic이면 `NO_BONE_MAP`으로 멈춘다 |
| 부착 부품 이름(가장 낮은 점을 몸과 따로 잼) | 카탈로그 에셋 `parts`의 키 | 모든 렌더러를 몸으로 본다 |
| 캐릭터 키(발 접촉 범위, 옆 카메라 거리) | 카탈로그 에셋 `height` | 1m |
| 게임 카메라(`pitch`, `yaw`, `fov`, `distance`, `target_height`) | `3dkit.config.json` `assets.game_camera` | `anim frames`가 멈춘다 |
| 승인값(프리팹 배율, 클립별 길이·가장 낮은 점, 허용 범위, 사용자 원문) | 카탈로그 에셋 `approved` | `anim recheck`가 멈춘다. 사용자가 결과를 받아들일 때마다 그 측정값과 원문을 적는다 |

## 9. 아직 없는 것

- 단계 건너뛰기를 막는 hook(예: ④ 사용자 원문 없이 ⑤ 시작 금지). 단계 기록을 실제로 몇 번 써 본 뒤 정한다.
