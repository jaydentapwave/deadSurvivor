# 콘텐츠는 데이터로

스테이지, 메뉴, 캐릭터 수치, 보상처럼 **개수가 늘어나는 것**은 코드가 아니라 데이터로 둔다. 레포 규칙이 있으면 그것이 우선이다.

- 상태: 실제 프로젝트 1개에서 검증됨(스테이지 20개를 대기열로 양산, 모두 첫 시도 채택). 맞지 않는 부분은 프로젝트에서 고치고 킷에 알린다.
- 이유: 콘텐츠 하나를 넣을 때마다 코드를 고쳐야 하면 콘텐츠를 여러 개 이어서 만들 수 없고, 넣을 때마다 기존 동작이 깨질 수 있다.

## 규칙

- **콘텐츠 추가에 코드 수정이 없어야 한다.** 스테이지 하나를 더 넣는 일이 데이터 파일을 더하는 것으로 끝나야 한다. 코드를 고쳐야 한다면 시스템이 그 종류의 콘텐츠를 아직 데이터로 받지 못하는 것이다. 콘텐츠를 넣기 전에 시스템부터 고친다(작업 규모는 `work-levels.md`).
- **코드에 콘텐츠 id·이름·수치를 쓰지 않는다.** `if (stageId == 7)` 같은 분기가 필요하면 그 차이를 데이터의 칸으로 만든다.
- **스키마가 먼저다.** 콘텐츠 종류마다 스키마(칸, 형식, 허용 범위, 다른 데이터를 가리키는 칸)를 먼저 정하고 문서로 둔다. 스키마 변경은 L2다.
- **검사 명령을 같이 만든다.** 스키마를 만들 때 데이터를 검사하는 명령도 만든다: 형식, id 중복, 가리키는 대상이 있는가. 개수는 고정값이 아니라 범위로 검사한다. 에디터 없이 터미널에서 돌고 실패하면 exit 0이 아니어야 한다.
- **여러 개를 이어서 만들 콘텐츠는 단위마다 파일을 나눈다.** 스테이지마다 파일 하나, 캐릭터마다 폴더 하나. 한 표에 모두 모아야 하는 데이터면(마스터 시트) 그 표를 고치는 작업들은 순서를 정해 하나씩 한다.
- **수치의 타당성은 눈이 아니라 계산으로 본다.** 진행 속도, 클리어 시간, 재화 흐름처럼 숫자로 판정할 수 있는 것은 시뮬레이터나 자동 플레이로 확인한다. 도구가 아직 없으면 콘텐츠를 늘리기 전에 그것부터 만든다.
- 참고 게임의 데이터를 옮겨 적지 않는다. 수치는 기획서에서 온다.
- **형식과 위치의 출발값.** 레포에 정해진 것이 없으면 콘텐츠 단위마다 JSON 파일 하나, 위치는 `Assets/Game/03.Resources/Resources/Data/<종류>/<id>.json`(Resources 로드)로 시작한다. 마스터 표가 이미 CSV면 그것을 따른다. Addressables·ScriptableObject로 바꾸는 일은 필요가 생겼을 때 L2로 한다.
- **쉬운지만 보지 말고 곡선을 본다.** 수치 판정이 "깰 수 있는가", "너무 쉽지 않은가"뿐이면 모든 콘텐츠가 같은 난이도여도 통과한다(출처 사례: 스테이지 20개가 모두 남은 체력 10/10·최소 타워 2개로 평평했는데 판정을 통과했다). 순서가 있는 콘텐츠는 지표 하나 이상이 순서에 따라 움직이는지 판정이나 회귀 검사에 넣는다: 최소로 필요한 수단의 수, 대표 플레이의 남은 체력·남은 재화, 클리어 시간. 목표 곡선(구간별 범위)은 기획서가 정한다.
- **규칙으로 자동 배치하는 것은 콘텐츠 사이의 반복을 본다.** 좌표만으로 정한 결정적 규칙은 모든 스테이지에서 같은 자리에 같은 것을 놓는다. 콘텐츠마다 달라야 하면 콘텐츠 id를 씨앗에 넣고, 서로 다른 콘텐츠 2개의 화면을 나란히 놓고 확인한다.

## 하지 않는 것

- 지금 하나뿐인 것을 미리 데이터로 빼지 않는다. 두 번째가 실제로 생길 때 뺀다(`scope-discipline.md`).
- 데이터로 표현하려고 코드 안에 작은 스크립트 언어를 만들지 않는다. 칸으로 표현되지 않는 동작은 코드로 두고, 데이터는 어느 동작을 쓸지만 고른다.
