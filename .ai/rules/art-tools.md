# 아트 도구 연결 — Codex (이미지 생성·검토)

art 팩 규칙(2D·3D 공통). 컨셉 이미지 생성과 다른 모델 계열의 검토에 쓰는 Codex 사용법과 함정이다. 확인한 버전은 표에 적고, 버전이 바뀌어 다르게 동작하면 고친다. 3D 생산 도구(Unity CLI·Tripo·Blender)는 3d-art 팩의 `.ai/rules/3d-tools.md`에 있다.

| 일 | 명령 | 주의 |
|---|---|---|
| 검토(읽기만) | `codex exec -s read-only -o <결과 파일> "<지시>"` | 결과 파일 이름은 `<주제>-rNNN.md`(핵심 규칙 3절, 훅이 횟수를 센다) |
| 이미지 생성 | `codex exec -s workspace-write -C <결과 폴더> "<지시>" -i <입력 그림>`. 이미지 생성 도구는 `image_gen__imagegen` | 프롬프트는 `-i` 앞에 둔다. `-i`는 값을 여러 개 받아 뒤에 오는 프롬프트까지 그림으로 먹고 "No prompt provided"로 끝난다(문제 기록 W31). `-C`로 작업 폴더를 결과 폴더로 잡아 쓰기 범위를 그 폴더로 좁힌다. 생성 그림은 `~/.codex/generated_images/<스레드>/`에 저장되므로 결과 폴더로 복사하게 지시하고 경로·해시를 보고받는다 |
| 백그라운드 실행 | 아래 "오래 걸리는 Codex 실행"의 명령을 쓴다 | 입력을 닫지 않으면 "Reading additional input from stdin..."에서 멈춘다(13분, 1시간 대기 확인, 문제 기록 W36) |

## 오래 걸리는 Codex 실행

완료 알림은 프로세스가 끝나야 온다. 멈춘 Codex는 끝나지 않으니 알림도 오지 않고, 사용자가 물을 때까지 아무도 모른다. 그래서 백그라운드 실행에는 **입력 닫기, 시간 상한, 주기 확인**을 항상 함께 건다. 사람이나 에이전트가 기억해서 들여다보는 방식에 맡기지 않는다. 입력 닫기는 3d-art 팩을 깐 프로젝트에서 hook(`guard.py`)이 강제한다. 입력을 닫지 않은 `codex exec`는 실행 전에 막힌다. 2d-art 팩만 깐 프로젝트에는 이 hook이 없으니 아래 실행 명령을 그대로 쓴다. 시간 상한과 주기 확인은 아직 hook이 보지 않는다.

걸린 시간 측정(codex-cli 0.166.0, 이 프로젝트의 이미지 작업 23회, 2026-11-06): 중간값 3.4분, 최대 7.4분. 세션 기록이 가장 오래 멈춘 시간은 39초다. 아래 값은 이 측정에서 정했다.

| 값 | 기준 | 근거 |
|---|---|---|
| 첫 확인 | 시작 3분 뒤 | 입력 대기는 처음부터 멈춰 있어 바로 잡힌다 |
| 이후 확인 | 5분마다 | 세션 기록 최대 공백 39초보다 충분히 길다 |
| 진행 없음 판정 | 다음 확인까지 로그 크기가 그대로 | 5분 넘게 아무것도 기록되지 않은 경우 |
| 시간 상한 | 20분 | 측정 최대 7.4분의 약 3배 |
| 다시 요청 | 실패 1건당 1회 | 두 번째도 실패하면 멈추고 사용자에게 묻는다(`3d-art-produce` 4절, `2d-art-produce` 4절) |

### 실행

결과 폴더에서 실행한다. macOS에는 `timeout`이 없어 `perl`로 상한을 건다. 상한에 걸리면 종료 코드가 142다.

```bash
perl -e 'alarm shift; exec @ARGV' 1200 codex exec -s workspace-write -C "$PWD" "$(cat <프롬프트 파일>)" < /dev/null > <로그> 2>&1
echo "exit=$?"
```

### 주기 확인

같은 폴더에서 별도 백그라운드 명령으로 함께 돌린다. 문제가 생기면 이 명령이 끝나면서 알림이 온다. 상태를 짧은 간격으로 묻는 일(핵심 규칙 4절)이 아니라, 건수와 시간 상한이 있는 대기다.

```bash
LOG=<로그>; prev=-1; wait=180
for i in 1 2 3 4 5; do
  sleep $wait; wait=300
  ps -eo command | grep "[c]odex exec" | grep -qF "$PWD" || { echo "ENDED"; exit 0; }
  grep -q "Reading additional input from stdin" "$LOG" && [ "$(wc -l < "$LOG")" -le 2 ] && { echo "STDIN_WAIT"; exit 1; }
  cur=$(wc -c < "$LOG")
  echo "check $i $(date +%T) log=$cur images=$(find <결과 폴더> -type f | wc -l)"
  [ "$cur" = "$prev" ] && { echo "NO_PROGRESS"; tail -n 3 "$LOG" | cut -c1-200; exit 1; }
  prev=$cur
done
echo "LIMIT_REACHED"; exit 1
```

### 안 되었을 때

순서를 지킨다. **먼저 무엇이 이미 만들어졌는지 보고, 프로세스를 끝내고, 없는 것만 다시 요청한다.** 멀쩡히 끝난 그림까지 다시 만들지 않는다. 그림은 결과 폴더로 복사되기 전에 `~/.codex/generated_images/<스레드>/`에 먼저 저장되니 두 곳을 다 본다.

| 보이는 것 | 뜻 | 대응 |
|---|---|---|
| `STDIN_WAIT`: 로그에 입력 대기 줄뿐, CPU 시간 거의 0 | 입력을 안 닫음. 아직 시작도 안 함 | 끝내고 위 실행 명령으로 다시 요청. 생성은 쓰이지 않았다 |
| `NO_PROGRESS`: 프로세스는 있는데 로그가 그대로 | 원인 모를 멈춤 | 로그 끝과 두 폴더를 보고, 끝낸 뒤 없는 그림만 다시 요청 |
| 종료 코드 142, 또는 `LIMIT_REACHED` | 시간 상한 초과 | 같음. 사용자에게 "상한 초과로 다시 요청함"을 바로 한 줄 알린다 |
| "No prompt provided"로 바로 끝남 | 프롬프트가 `-i` 뒤에 있음(W31) | 프롬프트를 `-i` 앞으로 옮겨 다시 요청 |
| 종료 코드 0인데 결과가 없거나 모자람 | 종료 코드는 결과를 보장하지 않음(W31) | 요청한 파일을 하나씩 세고, 빠진 것만 다시 요청 |
| 로그에 `Selected model is at capacity`, 종료 코드 1 | 모델이 일시적으로 꽉 참(2026-11-06, 6장 중 4장 뒤 발생) | 2~3분 뒤 빠진 그림만 다시 요청. 그때는 통과했다 |
| 로그에 로그인·사용량 한도·네트워크 오류 | 다시 해도 같은 결과일 가능성이 큼(아직 겪지 않음) | 다시 요청하지 않고 로그 끝을 붙여 사용자에게 알린다 |
| 다시 요청도 실패 | 같은 실패 반복 | 세 번째를 시작하지 않는다. 시도, 로그 끝, 이미 나온 그림을 보여 주고 묻는다 |

- 프로세스를 끝낼 때는 결과 폴더 경로로 내 작업인지 확인한다. 같은 컴퓨터에서 다른 세션도 Codex를 돌릴 수 있다. 같은 이유로 `codex exec resume --last`는 쓰지 않는다.
- 주기 확인도 내 작업만 본다. 실행 중인지, 진행이 있는지는 **결과 폴더 경로와 내 로그 파일**로만 판단한다(위 확인 명령이 `$PWD`로 거르는 이유다). `ps`에 보이는 `codex` 프로세스 수, `~/.codex/generated_images/`의 최신 폴더, 다른 프로젝트의 로그로 판단하지 않는다. 생성 그림 폴더에서 내 것을 찾을 때는 프롬프트에 넣어 둔 고유 문구나 스레드 id로 찾는다. 출처 사례: 다른 프로젝트의 Codex를 내 작업으로 보고 "멈춤"으로 잘못 알렸다.
- 끝난 뒤에는 알림이나 종료 코드만 믿지 않고 결과 파일을 직접 세고 연다.
