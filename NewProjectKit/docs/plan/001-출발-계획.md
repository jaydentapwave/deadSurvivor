# 001 출발 계획 — 스타일라이즈드 미드폴리 비주얼

- 상태: **나중 단계 초안(에이전트 제안).** 사용자 정리(2026-11-03)로 새 게임 제작은 3dkit 완성 → studio-kit 반영 뒤 아주 나중에 한다. 새 프로젝트 첫 세션에서 사용자와 함께 확정하고 이 문서를 고친다.
- 작성: 2026-11-03, 이전 프로젝트 Deadsurvivor 세션에서.

## 사용자 결정 (2026-11-03, 원문)

- "전체적으로 좋아, 이 정도 퀄리티면 로우폴리 치고는 굉장히 만족해, 워크플로우나 하네스 셋팅이 완료되었으면 이제 우리는 이 걸 기반으로 지금보다 좀 더 고퀄리티의 게임을 구축해보는게 목표야"
- 품질 축: **비주얼.** "우선 비주얼을 업데이트를 완벽히하면, 그다음은 쉐이더와 urp, 이펙트 이런식으로 디벨롭을 하고 싶어"
- 대상: **새 프로젝트로 재구축.** "아예 새로운 프로젝트에 우리가 만든 워크플로우 및 하네스를 아예 새롭게 구축해보는게 어떨까… 내생각은 전자야"
- 미술: **스타일라이즈드 미드폴리.**

- 키트: "어익후 올린다는 이야기를 한건 아냐야, 우리가 만든 3d kit을 완성시킨다음에 하나이ㅡ 에이전트로 이식시키는게 목표야" → 3D 키트(3dkit) 완성과 하나의 에이전트로 묶기가 함께 가는 목표다. 키트 단계는 `3dkit/README.md` 로드맵(v1 완성 → v2 에이전트 → v3 이식 검증).

## 에이전트 의견 (같은 날, 사용자 채택 전)

- 순서는 사용자 순서(비주얼 → 셰이더 → URP → 이펙트)를 따르되, **맨 앞에 룩데브 장면 하나**를 둔다. 미드폴리 모델의 품질은 목표 셰이더·조명 아래에서만 판단할 수 있다. 모델만 먼저 다 만들면 셰이더를 정한 뒤 다시 만들 위험이 있다.
- URP는 이전 프로젝트도 이미 쓰고 있었다(URP 17.4, Unity 6000.4.3f1). 그래서 "URP 디벨롭"은 파이프라인 교체가 아니라 조명·그림자·후처리·렌더러 기능을 다듬는 일이다. 새 프로젝트는 처음부터 URP 템플릿으로 만든다.
- 하네스는 [설계도](../../3dkit/workflows/harness-blueprint.md)의 단계대로 콘텐츠와 함께 키운다.

## 게임 로직 (결정 필요)

이전 프로젝트에는 게임 규칙·전투·장비·웨이브·진형·UI 코드가 있다(`Assets/DeadSurvivor/Runtime`, C# 44개 파일 약 6,240줄, 규칙 원본 `docs/game/`). 비주얼 단계(P1·P2)는 게임 로직 없이 진행할 수 있지만 P3부터는 필요하다.

| 안 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| A. 그대로 옮기기 | Runtime을 복사하고 네임스페이스만 바꿈 | 가장 빠름 | 맵 실험 코드(Map snapshot·blockout 등)와 2D 시절 구조가 같이 옴 |
| **B. 규칙만 옮기고 표현은 새로 (제안)** | 규칙·데이터 계층(전투 계산, 장비 규칙, 웨이브, 진형, 능력치)을 옮기고, 표현 계층(캐릭터 보기, 효과, 맵, UI)은 미드폴리에 맞게 새로 작성 | 검증된 규칙은 유지, 보이는 쪽은 새 품질 | 경계 정리에 시간 필요(L2 설계 1회) |
| C. 새로 작성 | `docs/game/` 규칙만 보고 다시 구현 | 가장 깨끗함 | 가장 느리고 규칙 불일치 위험 |

## 정해야 할 것 (P0~P2에서)

1. **대상 플랫폼과 성능 예산:** 모바일 유지(이전 기준)인지, PC/콘솔 품질도 목표인지. 미드폴리 규격 숫자가 여기에 달려 있다.
2. **카메라:** 이전은 직교 카메라(크기 6, 55°). 미드폴리는 원근 카메라가 더 잘 보일 수 있다. 룩데브에서 두 가지를 비교한다.
3. **Tripo 크레딧:** 이전 사용량은 몬스터 4종 160, 영웅 6명 v2 170, 공격 동작 20, 영웅 1명 모델·뼈대·동작 85였다. 같은 단가로 영웅 6·몬스터 5·소품 10여 종을 미드폴리로 다시 만들면 **대략 600~900 이상으로 추정**(품질 옵션·재시도에 따라 늘어남, 에이전트 추정). 이전 잔액은 약 285(2026-11-03, API로 다시 조회하지 않음). 정확한 견적은 P2에서 요청표 드라이런으로 낸다.
4. **색 방식:** [에셋 규격](../../3dkit/workflows/asset-standard.md) 3절 A/B/C.
5. **게임 로직:** 위 A/B/C.
6. **글꼴:** UI 글꼴을 처음부터 정적 아틀라스로(동적 글꼴 캐시가 Play마다 바뀌던 문제 방지).

## 위험

- 비주얼 반복마다 검증을 붙이면 이전 프로젝트처럼 콘텐츠가 밀린다. 핵심 규칙 0·2절을 지킨다.
- 미드폴리는 삼각형·텍스처 메모리가 크게 는다. P2에서 성능 한 줄을 먼저 재고 숫자를 정한다.
- AI 생성 모델의 방향·뼈대 반전·텍스처 그림자 같은 문제가 이전에 여러 번 있었다([교훈](../../3dkit/lessons/교훈-이식.md)).
