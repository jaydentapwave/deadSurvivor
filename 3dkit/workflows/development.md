# 개발 워크플로우

먼저 [핵심 규칙](core-rules.md)을 읽는다. 검증 단계·검토 횟수·세션 운영은 그 문서가 우선한다. 이전 프로젝트의 개발 워크플로우에서 맵 하네스·옛 gate 관련 문장을 빼고 줄였다(2026-11-03).

## 작업 분류

| 규모 | 조건 | 필수 절차 |
|---|---|---|
| L0 | 설명·오탈자·링크 정리, 기존 계약 안의 국소 수정, 수치·색·배치 조정 | 관련 원본 확인 → 수정 → 영향 범위 확인 → 결과 기록 |
| L1 | 새 기능/입력 흐름, 여러 부분에 영향을 주는 동작 변경, 워크플로우·검사 도입·변경 | 간단 설계 → 구현 → 검사 → validator-client 독립 검토 → 지적 수정 |
| L2 | 상태 소유권, 데이터 스키마, 도메인 경계, 소스 원본(에셋 카탈로그·팔레트·렌더 파이프라인 설정) 변경 | 설계 브리핑 → design-reviewer 독립 검토 → 구현 → 검사 → validator-client 독립 검토 |

- 여러 조건에 해당하면 높은 규모를 적용한다. 파일 수보다 상태 소유권·스키마·실행 흐름에 미치는 영향을 본다.
- 규모와 검사 범위는 별개다. L0도 런타임 변경이면 컴파일·짧은 Play를, 시각 변경이면 캡처를 한다.
- 비주얼 반복(셰이더 값·조명·색·배치 조정)은 대부분 L0다. 사용자에게 화면을 먼저 보여 주고 검토는 생략한다. 셰이더 구조·렌더 파이프라인 설정·에셋 규격 숫자를 바꾸는 일은 L1 이상이다.

## 시작할 때 고정할 범위

작업 문서 첫머리에 네 가지를 짧게 적는다.

- **이번에 쓸 수 있게 될 결과와 완료 조건:** 예: "영웅 1명이 목표 셰이더로 룩데브 장면에 서 있고 사용자가 캡처를 봄". 시험 후보와 정식 채택을 구분한다.
- **변경 범위와 후속 항목:** 바꿀 파일·동작, 이번에 다루지 않을 것.
- **최소 필수 검사:** 변경 → 실패 가능성 → 검사 방법.
- **첫 실제 연결:** 어떤 최소 정상 사례로 입력 → 실행 → 결과를 먼저 확인할지.

검사기·범용화·추가 진단을 만들기 전에 "어떤 현재 요구나 결함을 기존 도구로 판정할 수 없는가"를 적는다. 근거 없는 미래 대비는 후속 제안으로 남긴다.

## 실행

1. 요청 범위, 관련 기획과 실제 코드, 완료 기준을 확인한다. 사용자 결정과 실험안을 구분한다.
2. L1/L2는 [설계 양식](../templates/design-brief.md)으로 `docs/design/`에 작업 문서를 쓴다. 기존 원본이 있으면 그것을 고치고 중복 문서를 만들지 않는다.
3. L2는 [design-reviewer](design-reviewer.md) 계약을 읽는 독립 하위 에이전트에게 브리핑과 관련 파일만 넘긴다. 필수 지적을 해소한 뒤 구현한다.
4. 메인이 구현한다. 검토자는 파일을 고치지 않는다.
5. 구현 중에는 최소 정상 사례를 실제 경로에 일찍 연결해 확인한다. 큰 사례 행렬은 그 뒤에 필요할 때만 넓힌다. 불완전한 중간 코드에서 전체 Play를 반복하지 않는다.
6. L1/L2는 [validator-client](validator-client.md) 계약으로 독립 검토를 받는다. 계산·배치 변경은 [algorithm-tester](algorithm-tester.md)도 적용한다.
7. 단계 마감에 필요한 검사(핵심 규칙 1절)와 커밋 전 gate([하네스 설계도](harness-blueprint.md) H4)를 실행한다.
8. [검증 양식](../templates/verification.md)으로 `docs/reviews/`에 결과를 남긴다. 중요한 선택은 [결정 양식](../templates/decision.md)으로 `docs/decisions/`에 남긴다. 현재 상태(프로젝트의 `docs/현재상태.md`)를 고친다.

## 실패·재실행·독립 검토

- 실패는 먼저 게임 동작 결함, 검사기 오판, 환경/권한 차단, 시각 품질 미달로 나눈다. 원인을 확인하기 전에 검사 강도나 기준값을 바꾸지 않는다.
- 같은 환경 차단은 원인 확인용 최소 조회까지만 한다. 조건이 바뀌지 않았으면 같은 전체 검사를 반복하지 않는다. 차단 증거와 재개 조건을 남기고 다른 일을 계속한다.
- 원인을 못 찾은 1회 실패는 실패 시점 상태를 기록하게 고친 뒤 한 번만 다시 돌린다. 재현되지 않으면 UNKNOWN으로 남긴다.
- 검토 지적은 **필수 수정**과 **후속 제안**으로 나눈다(핵심 규칙 3절). 메인이 필수 지적을 임의로 후속으로 낮추지 않는다.
- 독립 검토 도구를 쓸 수 없으면 검토 상태를 BLOCKED로 기록하고 가능한 구현·확인을 계속한다. 자기 검토를 독립 검토로 표시하지 않는다.

## 진행 보고

- 보고는 쓸 수 있게 된 결과, 진행 중인 일, 다음 완료 조건, 차단/대기를 중심으로 한다. 검사 개수를 제품 진척으로 대신하지 않는다.
- 첫 사용 가능한 결과 시점과 구현·검사·검토 대기 시간을 가능한 범위에서 남긴다. 측정하지 못한 구간은 미측정으로 둔다.
- 도구 출력은 원본 로그를 `output/`에 보존하고 기본 응답은 상태·첫 실패·보고서 경로만 낸다.

## 도구별 연결

- Codex: `AGENTS.md`를 읽어 실행한다. 대화 없이 실행할 때 `codex exec -s read-only`(검토) 또는 `-s workspace-write`(생성)를 쓰고 `< /dev/null`로 입력을 닫는다(개발 환경(프로젝트의 `docs/개발환경.md`)).
- Claude: `CLAUDE.md`를 통해 같은 계약을 읽고 `.claude/agents/`의 역할을 하위 에이전트로 쓴다.
- 에셋 제작은 [에셋 규격](asset-standard.md)의 정식 경로 하나로만 한다.

## 완료 기준

범위 안의 구현, 필수 검사, 독립 검토 필수 지적 해소, 관련 문서 갱신까지 끝나야 완료다. 검증하지 못한 항목은 사유와 다음 조치를 적는다. 커밋·원격 게시·프로젝트 밖 기록은 이 절차로 자동 승인되지 않는다.
