# 핵심 규칙 (1쪽)

작업을 시작할 때 이 문서를 먼저 읽는다. 다른 워크플로우 문서와 부딪히면 이 문서를 따른다. 이전 프로젝트 Deadsurvivor의 핵심 규칙(2026-11-02 하네스 회고에서 만들고 046~050에서 다듬음)을 새 프로젝트용으로 다시 썼다. 각 규칙이 왜 생겼는지는 [교훈](../lessons/교훈-이식.md)에 있다.

## 0. 만드는 일이 먼저다

사용자 원문(2026-11-02): "전체 맵을 구축하는걸 원하는데, 지금 뭔가 계속해서 검증이랑 이상한 테스트?를 하는느낌". 이전 프로젝트에서는 검증 도구를 키우다가 게임 콘텐츠가 밀린 일이 반복됐다.

- 게임·미술 작업은 결과물을 먼저 만들어 사용자에게 보여 준다. 검증은 컴파일, 짧은 Play 1회, 사용자 직접 플레이로 끝낸다.
- 독립 검토, 전체 Play, 새 검사 도구는 사용자가 요청하거나 커밋 전 gate가 요구할 때만 한다.
- 검사가 실패하면 먼저 게임 결함인지 검사 결함인지 나눠 보고한다. 검사 도구를 고치는 작업은 사용자에게 묻고 시작한다.
- 하네스는 콘텐츠와 함께 키운다. [하네스 설계도](harness-blueprint.md)의 단계(H0~H4)를 지금 필요한 것까지만 만든다.
- 다음 할 일을 제안할 때는 게임에 들어가는 일을 앞에 둔다.

## 1. 검증은 3단계, 기본은 짧은 단계

| 단계 | 내용 | 언제 |
|---|---|---|
| 빠른 확인 | 컴파일, 정적 검사, 도구 자체 시험. Play 없음 | 문서·도구만 바뀜 |
| **짧은 Play (기본)** | 1~2분. 시작 → 이동 → 정지 → 콘솔 확인 → 정리, 화면 1장 캡처 | 작업 중 모든 게임·시각 변경 |
| 전체 Play | 게임 한 판 전체, 부하, 화면비 | **단계 마감 1회.** 게임 동작 파일이 마지막 전체 PASS 이후 바뀐 경우만 |

- 전체 Play 실행기는 실행 이유(`FULL_REASON="<이유>"`)가 없으면 스스로 멈추게 만든다. 실행 이유는 기록으로 남긴다.
- 화면 확인·측정용 Play 스크립트를 그때그때 새로 짜지 않는다. 측정 도구(설계도의 `probe`) 하나를 쓰고, 없는 옵션만 그 도구에 더한다.
- Play 중 프레임·성능을 잴 때는 `PlayerSettings.runInBackground`를 켜고 끝나면 원래대로 돌린다. 끄고 재면 편집기가 백그라운드에서 느려져 3fps 같은 값이 나온다. 게임을 그리는 창은 도킹된 Game 창 하나여야 한다.
- 시각·내용 변경이 큰 단계는 마감 보고에 **성능 한 줄**(그리기 호출·set-pass·삼각형·그림자·렌더 시간, 측정 명령)을 넣고 같은 기준으로 잰 이전 값과 나란히 적는다. 기준은 [성능 절차](performance.md).
- 0.2~0.5초짜리 순간 효과는 정지 캡처 1장으로 판정하지 않는다. 연속 캡처나 상태 숫자(효과 수·종류)로 본다.

## 2. 증거는 "게임 동작"과 "보이는 것"으로 나눈다

- 전체 PASS를 기록할 때 게임 동작 파일(런타임 코드·장면·데이터·설정)과 시각 파일(텍스처·재질·셰이더·모델·프리팹·애니메이션)의 해시를 따로 남긴다.
- 시각 파일만 바뀌면 게임 동작 증거는 다시 쓴다. 짧은 Play 캡처와 사용자 확인으로 충분하다.
- 시각 증거는 실제로 캡처한 기록만 인정한다. 화면 없는 실행은 게임 동작 증거만 된다.
- 검사 도구만 바뀌면 그 도구의 자체 시험만 다시 돌린다.
- 이 분리는 비주얼 반복이 많은 이 프로젝트에서 특히 중요하다. 셰이더·조명을 바꿀 때마다 전체 Play를 돌리지 않는다.

## 3. 검토는 주제당 최대 2회

- 같은 주제의 독립 검토(Codex 등)는 **설계 1회 + 마감 1회**까지만 한다. 3회째가 필요하면 먼저 사용자에게 묻는다.
- **필수 수정**은 다음 셋으로 한정한다. 나머지 가능성과 추가 검사 제안은 후속 목록으로 보내고, 우선순위는 사용자가 정한다.
  - 실제로 확인된 결함
  - 명시된 완료 조건의 위반
  - 데이터 손실이나 복구 불가 위험
- 지적은 모아서 한 번에 고친 뒤 마감 검토를 받는다. 지적 하나 고칠 때마다 전체 Play를 다시 돌리지 않는다.
- Codex 검토 결과 파일 이름은 `<주제>-rNNN.md`로 쓴다(hook이 횟수를 센다).

## 4. 단계마다 새 대화

- 단계가 끝나면 [인수인계 양식](../templates/handoff.md)으로 현재 상태(프로젝트의 `docs/현재상태.md`)에 인수인계를 쓰고, 사용자에게 새 세션을 제안한다.
- 대화 맥락이 25만 토큰을 넘으면 알린다. **30만을 넘은 상태에서 새 큰 작업(새 단계, 여러 파일 구현, Play 여러 번)을 받으면 시작하기 전에 인수인계를 쓰고 새 세션을 먼저 제안한다.** 도구를 부를 때마다 전체 맥락을 다시 읽어 캐시 읽기가 비용의 대부분이 된다(이전 047 세션: 캐시 읽기 약 1.21억 토큰).
- 긴 실행은 백그라운드로 돌리고 완료 알림을 기다린다. 상태를 짧은 간격으로 반복 조회하지 않는다.
- 여러 확인은 스크립트 하나로 묶어 판정에 필요한 줄만 출력한다.
- 큰 이미지는 하위 에이전트가 보고 메인은 결론만 받는다.

## 5. 규칙은 늘리기만 하지 않는다

- 검사를 하나 추가할 때 뺄 수 있는 검사도 함께 적는다.
- 단계 회고에서 비용이 큰데 결함을 한 번도 잡지 못한 검사는 빼기 후보로 사용자에게 제시한다. 실제로 빼는 것은 다시 넣을 필요가 없다고 확실할 때만 한다.
- 새 규칙은 가능하면 문서 문장보다 도구 기본값이나 hook으로 넣는다.

## 6. 사용자가 먼저 본다

- 시각·체감 변경은 짧은 Play 캡처나 직접 플레이로 사용자에게 먼저 보여 준다. 자동 판정과 독립 시각 판정은 그 뒤에, 필요한 것만 한다.
- 미술은 사용자가 아트 디렉터다. 방향·채택은 사용자가 정하고, 에이전트 제안은 제안으로 표시한다.
- 보고에서는 게임에 들어간 것, 시험 장면, 목표를 구분한다.

## 7. 유료 생성과 비용

- Tripo 등 유료 생성은 요청마다 사용자 승인 원문과 상한을 기록한 뒤 실행한다. 옛 승인을 새 에셋에 물려받지 않는다.
- 네트워크 오류 뒤 자동 재전송하지 않는다(중복 과금 위험). 먼저 상태를 조회한다.
- API 키는 출력·기록하지 않는다.
