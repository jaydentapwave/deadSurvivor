# 교훈 이식: 이전 Unity 프로젝트에서 겪은 실패와 그에 따른 규칙

- 목적: 새 Unity 프로젝트(스타일라이즈드 미드폴리, 시각 우선)에서 같은 실수를 되풀이하지 않도록, 이전 프로젝트에서 실제로 겪은 문제를 프로젝트에 묶이지 않는 규칙으로 정리한다.
- 원본 프로젝트: Deadsurvivor (Unity 6000.4.3f1, URP 17.4, 로우폴리 3D 모바일 오토배틀러, Tripo·Codex로 만든 AI 미술, Claude·Codex 에이전트가 unity CLI로 구동)
- 작성일: 2026-11-03

## 읽는 법

- 각 줄은 `증상 → 원인 → 새 프로젝트 기본값/규칙 (원본 ID)` 순서로 쓴다. 원본 문서는 새 프로젝트에 없다. ID는 원본을 추적할 때만 쓴다.
- ID 뜻: 046-n은 전체 맵 단계의 "놓친 것", 047-En은 전투 효과 단계의 에러, 047-Hn은 같은 문서의 하네스 갱신 후보, 048-n과 048-Fn은 하네스 갱신 단계, 049-n은 성능, 050-n은 에셋 규격, P·S0~S3-n은 키아트 목표 화면(045)의 놓친 것이다. 회고1101은 작업 지연 회고, 회고1102-Hn은 하네스 회고, 참조회고-n은 레퍼런스 이탈 회고, 환경은 개발 환경 문서의 도구 표다.
- 원본 문서 경로(원본 프로젝트 기준): docs/design/map-full-046.md, docs/reviews/combat-fx-047-log.md, docs/reviews/harness-update-048.md, docs/reviews/perf-049.md, docs/reviews/asset-standard-050.md, docs/reviews/keyart-target-045-review.md, docs/reviews/harness-retrospective-20261102.md, docs/reviews/work-delays-retrospective-20261101.md, docs/reviews/reference-drift-retrospective-20261102.md, docs/개발환경.md, docs/workflows/ai-3d-assets.md(유료 제출 규칙).
- 표시: [로우폴리]는 로우폴리 화풍에서 나온 값이나 방법이라 미드폴리에서는 다시 정해야 한다. [모바일]은 모바일 기준 수치다. "원인 미확인"은 원본에서도 원인을 밝히지 못했다는 뜻이다.

## 1. 작업 방식 실패 패턴

- 여러 맵 단계가 검증 도구와 판정 수정 위주로 흘러가서 전체 맵이 끝내 만들어지지 않았다. 게다가 맵 데이터 검사가 장애물 수를 64개로 고정해 맵을 넓힐 수조차 없었다 → "검증 PASS = 완료" 구조였고, 검사가 실패하면 검사 도구를 고치는 순환에 빠졌다 → 콘텐츠 작업은 결과물을 먼저 만들고 검증은 컴파일·짧은 Play·사용자 직접 플레이로 최소화한다. 데이터 검사는 콘텐츠 개수를 고정하지 말고 범위(예: 1~120개, ID 중복 금지)로 둔다 (046-1)
- 실제 전체 실행을 연결하기도 전에 관찰기·전체 상태 기록·반례 행렬을 계속 세분화했다. 그래서 사용자에게 보이는 결과에 비해 작업량이 크게 늘었다 → 실제 결함이나 요구와 연결되지 않은 검사를 늘렸다 → 시작 전에 산출물·완료 조건·제외 범위·최소 검사를 적는다. "요청→실제 실행→상태 기록→판정→복구"로 이어지는 작은 실제 경로부터 끝까지 연결한다 (회고1101 §1·§6)
- 10웨이브 전체 Play를 31회 돌려 약 3.5~4시간을 썼다(실제 작업 10.6시간의 35~40%) → 규칙은 "전체는 마감 때만"이었지만 실행기에 전체 모드밖에 없었다 → 검증을 3단계(빠른 확인 / 짧은 Play 기본, 약 65~80초 / 전체는 마감 때 이유를 적어야 실행)로 나누고 이를 도구 기본값으로 만든다. 규칙은 도구 기본값이 되어야 지켜진다 (회고1102-H1)
- 텍스처를 고칠 때마다 전체 Play를 다시 돌려 한 단계에서만 8회가 됐다 → 실행기 지문에 텍스처·재질까지 넣어서 증거가 너무 쉽게 무효가 됐다 → 게임 동작 증거와 시각 증거를 따로 기록하고 재사용한다. 시각 증거는 실제로 캡처한 PASS만 인정하고, 지문 대상은 결과물에 실제로 들어가는 파일로 한정한다 (회고1102-H2, S2-9)
- 독립 검토(Codex)를 27회 했는데 7개 주제 모두 첫 검토에서 FAIL이 나왔다. 한 주제는 3회 연속 FAIL이 났는데도 사용자에게 묻지 않고 약 1시간 동안 되풀이했다 → 검토자가 "근거 있는 미실행 위험"까지 필수로 요구할 수 있어서 끝이 나지 않았다 → 주제당 검토는 설계 1회 + 마감 1회로 제한한다. 필수 수정은 확인된 결함·완료 조건 위반·데이터 손실 위험으로 한정하고, 3회째 검토는 사용자 승인을 받은 뒤에 한다 (회고1102-H3, S3-13)
- 놓친 것이 나올 때마다 검사가 늘기만 했다. 그런데 사용자 눈에 띈 결함(캐릭터가 옆으로 걷기, 넓은 화면 UI의 빈 곳)은 검사가 아니라 사람 눈이 찾았다 → 검사를 빼는 절차가 없었다 → 검사를 추가할 때 뺄 후보도 함께 적는다. 사용자가 캡처와 직접 플레이로 먼저 확인한다 (회고1102-H4)
- 사용자에게 "반드시 필요한 것만 검증"하라는 말을 두 번 들었다 → 규칙이 문서로만 있었다 → 반복되는 낭비(이유 없는 전체 Play, 같은 주제의 3번째 검토, 지나치게 긴 대화)는 hook으로 막는다. hook에 오류가 나면 막지 않고 통과시킨다 (회고1102-H5)
- 응답마다 평균 약 50만 토큰을 다시 읽어 한 단계 합계가 6.38억 토큰이 됐다. 다른 세션에서도 캐시 읽기 1.21억 토큰이 비용 대부분이었다 → 단계를 마칠 때 인수인계하는 절차 없이 대화 하나를 길게 이어 갔다 → 맥락이 25만 토큰을 넘으면 알린다. 30만 토큰 이상에서 새 큰 작업을 시작하려면 인수인계를 하고 새 세션에서 연다 (회고1102-H6, 047-H10)
- 미술이 원본 레퍼런스에서 멀어졌다. 원본은 넓은 녹색 상부에 얇은 회색 외곽인데, 결과물은 큰 회색 다면체로 채워졌다. 그렇게 단순화된 Unity 화면을 다시 다음 생성의 입력으로 넣어 잘못된 해석이 더 강해졌다 → 원본 대신 중간 결과를 기준으로 삼았다(생성 도구 자체가 원인이라는 근거는 없다) → 모든 제작 입력에 실제 원본 경로와 선정 범위를 붙인다. 생성 시안은 스타일 참고일 뿐이고 배치·형태의 원본이 아니다. 실패한 시험 결과를 다음 입력으로 다시 쓰지 않는다 (참조회고-1)
- 화면 대부분을 차지하는 풀밭·흙·길이 준비되지 않은 상태에서 돌벽 하나만 다듬었다 → 보이는 면적보다 단일 소품을 먼저 만들었다 → 화면 면적이 큰 것(지면·큰 덩어리)부터 만든다. 소품은 그 다음이다 (참조회고-2)
- 원본에서 높이·단면을 알 수 없는 부분을 큰 덩어리로 확정했고, 그 시험 치수가 다음 작업의 기준처럼 이어졌다 → 관찰과 구현 제안을 섞었다 → 관찰 / 구현 제안 / 사용자 채택을 따로 적는다 (참조회고-3)
- 원본(위에서 본 시점)과 Unity 화면(55° 근접)을 다른 조건으로 비교해서 형태·밀도 차이를 늦게 발견했다 → 비교 조건이 달랐다 → 같은 영역을 위에서 본 비교와 실제 게임 카메라 화면을 함께 남긴다 (참조회고-4)
- 기능 검사 PASS가 미술도 원본에 맞는다는 뜻으로 읽혔다 → 기능 판정과 시각 판정을 한 줄에 기록했다 → "기능 PASS / 시각 기준 후보 PASS / 사용자 채택"을 따로 기록한다. 원본을 옆에 놓고 하는 시각 판정을 일찍 한다 (참조회고-5)
- 첫 배치는 장애물 46개로 레퍼런스(약 70개)보다 성겼다 → 간격·여유값을 감으로 정했다 → 배치 생성기는 레퍼런스와 개수·밀도를 숫자로 먼저 비교해 보고한다(조정 후 66개) (046-8)
- 원인을 측정하지 않고 추정했다. 적 정체 35%를 "무리에 막혔다"고 해석해 합격 기준까지 바꿨지만 실제 원인은 경로 탐색 예산(프레임당 2회) 대기였다. 텍스처가 안 보이는 원인도 렌더러 탓으로 두 번 추정했지만 실제로는 채움 색 문제였다 → 측정 없이 해석했다 → 기대와 다르면 대조 실험(단색 입력, 광선 추적, 대조 렌더, 코드 확인)으로 어느 단계가 원인인지 먼저 찾는다. FAIL이 나면 기준을 고치기 전에 원인부터 확인한다. 관측할 수 없는 원인은 UNKNOWN으로 남긴다 (S1-11, S3-7, S1-17)
- "몬스터 재질·메시를 1개로 합치자"고 최적화를 제안했는데, 확인해 보니 이미 1개씩이었다 → 자산 구성을 보지 않고 일반론으로 제안했다 → 최적화를 제안하기 전에 자산 구성(메시·재질·그림자 설정)을 출력해 본다 (049-1)
- 1단계 "PASS" 보고를 철회해야 했다. 부하 지표는 PC 설정으로 쟀고, 웨이브마다 3초만 측정했고, 재출전 검사에 같은 영웅을 썼다 → "돌렸다"에서 멈추고 설계의 측정 조건과 대조하지 않았다 → 보고 전에 설계의 검증 표와 실제 측정 조건(설정·구간·대상)을 항목별로 대조한다 (S1-12)
- 사용자의 짧은 답("지금 형태로 그대로 이어가자")을 에이전트 해석대로 기록해 방향이 어긋났다. 시험 렌더를 사용자가 게임 화면으로 오해하기도 했다 → 확인 질문을 하지 않았고 이미지에 상태 표시가 없었다 → 방향을 정하는 결정은 해석을 한 문장으로 되물어 확인한다. 이미지마다 "게임 반영 / 시험 / AI 목표 그림 / 외부 참고"를 적는다. 완료 보고는 약속 범위·한계·범위 밖을 나눠 쓴다 (P1~P3)
- 백그라운드로 실행한 Codex가 13분 동안 시작하지 못했다. 명령 안에서 `&`로 띄운 작업은 하네스가 끝났는지 알지 못했다 → 표준 입력을 닫지 않았고 실행 방식을 섞어 썼다 → 외부 에이전트는 `< /dev/null`로 입력을 닫고 30초 안에 시작 로그를 확인한다. 긴 작업은 하네스의 백그라운드 기능으로만 띄운다 (S0-9, S3-19)
- 문서에는 "실행기가 부작용 파일을 되돌린다"고 썼지만 코드는 아직 연결되지 않았다(독립 검토에서 발견) → 문서를 코드보다 먼저 썼다 → 도구 동작을 설명하는 문장은 연결과 시험을 마친 뒤에 쓴다 (048-5)

## 2. Unity 편집기·CLI 함정 (Unity 6000.4.3f1, unity CLI 1.0.0-beta.15 기준)

- Play 캡처와 화면 검사가 `Sequence contains no elements`로 실패했다. 새로 연 Game 창은 도킹되지 않은 큰 창이라 화면 크기가 맞지 않았다 → 편집기 메인 탭이 Game이 아니라 Device Simulator 모드였다(같은 탭 안에서 전환됨) → Play 검사 전에 메인 탭이 도킹된 Game 창인지 확인한다. Game으로 되돌리려면 `script eval`에서 Simulator 창에 `PlayModeView.SwapMainWindow`(GameView 타입)를 호출한다 (046-10)
- 성능 수치가 실제의 약 2.4배로 나왔다 → Simulator 탭과 떠 있는 Game 창이 둘 다 게임을 그려 편집기 통계가 두 번 집계됐다 → 성능을 재기 전에 게임을 그리는 창이 하나뿐인지 확인한다 (046-13)
- Play 중 프레임 측정이 3fps로 나왔다 → `PlayerSettings.runInBackground`가 꺼져 있어 포커스를 잃은 편집기가 느려졌다 → 측정 도구는 이 설정을 켠 상태로 재고(약 78fps), 측정이 끝나면 원래 값으로 되돌린다 (046-3)
- 장면 생성·캡처·Play를 하고 나면 동적 글꼴 에셋이 2048×2048 캐시로 저장돼 추적 파일이 바뀌었다. 한 단계에서만 5회 이상 반복됐다 → 편집 모드 렌더링으로 채워진 캐시가 다른 저장 동작에 함께 저장됐다(어느 호출이 저장하는지는 원인 미확인). 빌드 도구의 전체 `AssetDatabase.SaveAssets()`도 같은 결과를 냈다 → 자기 산출물만 저장한다(`SaveAssetIfDirty`). Unity에 쓰는 단계마다 직후에 `git status`를 본다. 실행 전에 깨끗했던 부작용 파일만 자동으로 되돌린다. 근본 해결책으로는 빌드에 쓰는 글꼴을 정적 아틀라스로 고정하는 안이 있었다(원본에서는 보류). 새 프로젝트는 처음부터 정적 아틀라스를 검토한다 (046-2, 047-E9, S1-1, 047-H4)
- 검사 직후에는 `git status`가 깨끗했는데, 다음 재컴파일 때 `QualitySettings.asset`과 무관한 재질의 GI 설정이 디스크에 저장됐다 → Play 중 파이프라인 임시 교체 등으로 "변경됨" 표시가 남았다가 나중에 저장됐다 → 프로젝트 설정을 건드린 검증 뒤에는 재컴파일을 한 번 지난 다음 `git status`를 다시 본다. 되돌린 값은 "변경됨" 표시도 지운다 (S1-3, S1-10)
- `capture game_view --save_path output/x.png`로 찍은 캡처가 `Assets/output/x.png`에 저장됐다 → CLI가 경로를 `Assets/` 기준으로 해석한다 → 이 기준에 맞춰 경로를 주고, Assets 아래에 생긴 결과물은 다른 곳으로 옮긴 뒤 지우거나 git에서 제외한다 (046-14)
- CLI 캡처의 `--width/--height`가 실제 해상도를 바꾼다고 믿고 화면비 검증을 했는데, 그 검증은 무효였다 → 옵션의 뜻을 확인하지 않았다 → 화면비 검증은 실제 Game 뷰 해상도를 바꾸고 렌더 타깃 크기를 확인하는 방식으로 한다 (P5)
- `script run`이 진입점을 찾지 못했다 → 같은 이름의 정적 메서드가 둘 있으면 실행을 거부한다 → 진입점 메서드 이름은 파일 안에서 하나만 있게 짓는다 (046-11)
- 측정 코드가 컴파일에 실패했다 → Unity 6.4에서 `FindFirstObjectByType`은 폐기 경고가 컴파일 오류로 처리됐고, `FindObjectsSortMode` 인자도 폐기됐으며, `UnityStats.batches`와 `trianglesLong`은 존재하지 않는다 → `FindAnyObjectByType`을 쓴다. 컴파일 뒤에는 편집기 진단(경고)도 확인한다. 통계는 리플렉션으로 `drawCalls`·`setPassCalls`·`triangles`·`shadowCasters`·`frameTime`을 읽는다 (046-11, 047-E8)
- Claude Unity 플러그인 0.1.6-beta가 옛 명령 이름(`unity command eval`, `editor_play`)을 안내했다 → 플러그인과 CLI 버전이 달랐다 → 실제 CLI의 명령 이름(`unity command script eval`·`script run`, `unity command editor.playmode`)을 쓴다. 이름을 모르면 `unity commands --grep <단어>`로 찾고, 작업 전에 `unity status --until-ready`로 연결 상태를 확인한다 (환경)
- `socket hang up` 연결 끊김과 GameView 크기 불일치로 실행이 실패했다 → 원인 미확인(지속되는 장애로 단정하지는 않았다) → 연결 상태 확인·재시도·원래 장면 복구를 도구에 넣는다. 같은 환경 오류가 반복되면 같은 전체 검사를 다시 돌리지 말고 BLOCKED로 기록해 둔다 (회고1101 §2·§6)
- 회귀 검사는 특정 장면이 열려 있어야만 시작됐다. 화면 없는(백그라운드) 편집기는 처음에 열린 장면이 없어서 복구 단계가 실패했다 → 도구가 장면이 열려 있다고 가정했다 → 도구가 필요한 장면을 직접 열고, 열린 장면이 없을 때도 처리한다 (환경, S2-8)
- 화면 없는 편집기로 바꾸자 캡처가 불가능해졌다. 프레임 끝 콜백도 돌지 않아 UI 로드 측정값이 −1로 나왔다 → 기존 도구가 화면에 의존하는지 점검하지 않았다 → 실행 환경을 바꿀 때는 회귀 도구를 그 환경에서 하나씩 한 번 돌려 의존성을 찾는다 (S3-11)
- 편집기 Play가 PC 품질만 써서 설계에 있던 "모바일 품질 캡처"를 할 수 없었다. 이전 비교 캡처도 PC 품질(SSAO·부드러운 그림자)이었다 → 편집기 빌드 대상이 Standalone이어서 플랫폼별 품질 단계가 적용되지 않았다 → 시각 캡처마다 빌드 대상·품질 단계·렌더 파이프라인 에셋을 기록한다. 목표 플랫폼 화면은 파이프라인 에셋을 임시로 바꿔서 찍는다 (S1-2, S0-8)
- 키아트의 핵심인 그림자가 실제 게임에는 없었다 → 카메라 거리(150)가 그림자 거리(50)보다 멀었다 → 시각 작업 설계에 "실제 게임 카메라·품질 단계·후처리 상태에서 이 효과가 보이는가"를 확인 항목으로 넣는다 (S0-1)
- 셰이더 픽셀 비교가 빈 화면으로 3번 실패했다 → 미리보기 장면에서, 셰이더가 준비되기 전에 렌더했다 → 렌더 비교는 실제 장면에서 한다. 비동기 셰이더 컴파일을 끄고 미리 한 번 렌더한다. 결과가 빈 화면이면 판정하지 않는다(밝은 픽셀 수로 확인) (S1-8)
- 스킨 메시 캐릭터의 키가 의도의 0.696배로 나왔다. 다른 측정에서는 축척이 두 번 적용돼 0.01m가 나왔다 → 스킨 메시의 경계 상자는 실제보다 약 1.45배 크고, `BakeMesh`의 축척 인자 뜻을 확인하지 않았다 → 스킨 메시 크기는 `BakeMesh(true)`로 얻은 꼭짓점에 월드 행렬을 적용해 잰다. 처음 쓰는 엔진 함수는 알려진 모델 2개로 값을 대조해 본 뒤 쓴다 (S3-3, S3-6)
- 저장 확인 검사가 null 참조를 통과시켜 Play에서 3D 표시가 꺼졌다 → 가져오기로 파괴된 Unity 객체가 가짜 null이 되어 `!=` 비교가 틀렸다 → 저장 확인은 객체 비교가 아니라 에셋 경로·GUID·파일 내용으로 한다 (S3-8)
- 편집 모드 표본 재생이나 바인드 포즈로 잰 캐릭터 방향이 Play 때와 달랐다 → 휴머노이드 재생은 Play 중에 몸을 Animator 오브젝트의 +Z 방향에 맞춘다 → 방향·자세 판단은 실제 Play 중에 잰다. 편집 모드 측정값은 Play 측정과 대조한 뒤에만 쓴다 (S3-4, S3-21)
- 편집 모드에서 Play 전용 상태를 조회하다 실패했다 → 실행 조건을 구분하지 않았다 → Play 전용 상태는 Play 중에만 읽는다 (S1-6)
- C#과 Python 경계에서 여러 오류가 났다. Unity JSON에서 생략된 중첩 항목이 null이 아니라 빈 객체로 생성돼 기본 요청을 다른 경로로 잘못 처리했다. GameObject ID와 Transform ID를 섞어 비교했다. float32를 거친 0.0001이 double 최소 기준보다 작아졌다. Python double과 C# float32의 비교 차이를 설정 변경으로 잘못 판단했다 → 경계의 데이터 형식을 확인 없이 가정했다 → 경로 선택은 명시적인 필드로 하고, ID는 한 종류로 통일하고, 수치는 같은 정밀도로 비교한다. 이런 경계 지점은 큰 실행 전에 작은 확인으로 먼저 점검한다 (회고1101 §2·§3)
- `T="python3 도구"; $T ...` 같은 명령이 실패했다 → zsh는 변수 값을 단어로 나누지 않는다 → 셸 명령은 변수에 담지 말고 직접 쓴다(필요하면 함수나 배열을 쓴다) (S2-10)

## 3. AI 3D 에셋(Tripo·Codex)·가져오기

### 유료 생성 안전
- 사용자 승인 문구가 두 단계 동안 모든 고정 요청 파일에 `[REDACTED]`로 남았다 → 승인 문구를 `authorization` 키로 저장했더니 비밀값 가리기 규칙이 이를 HTTP 인증 정보로 보고 가렸다 → 승인 원문은 인증 정보처럼 보이지 않는 키(예: `user_approval`)로 저장한다. 기록을 쓰는 도구는 쓴 내용을 다시 읽어 원문이 남아 있는지 시험한다 (048-F1, 048-1)
- 유료 동작 생성 단계의 승인 원문이 코드 주석에만 있었다 → 승인을 생성 단계에서만 기록했다 → 모든 유료 단계(생성·뼈대·동작·재텍스처)는 승인 원문을 작업 일지에 쓴 뒤에 제출하고, 원문이 없으면 제출을 거부한다. 예산에는 승인 원문·상한·대상 자산 목록을 함께 둔다. 새 에셋은 새 예산을 만들고 옛 승인을 물려받지 않는다 (047-H8, 050)
- 공급자 구동기에 구멍이 있었다. 고정한 인자와 실제 제출 인자가 따로 놀았고, 일부 명령만 잠갔고, 견적이 없으면 기본값 50을 썼고, 초기화 때 네트워크 오류를 그냥 넘겼다 → 반례 시험 없이 바로 썼다(모두 제출 전에 발견해 크레딧 손실은 0) → 유료 구동기는 처음 쓰기 전에 오프라인 반례 시험(네트워크 차단, 임시 폴더)을 만든다 (S2-13)
- 이중 과금 위험(실제 사고가 나기 전에 정한 규칙): 네트워크 오류나 응답 유실 뒤 자동으로 다시 제출하면 같은 작업이 두 번 과금될 수 있다 → 공급자 수락 ID를 받기 전에는 작업이 실제로 접수됐는지 알 수 없다 → 제출 전에 고유 시도 ID와 `SUBMITTING` 상태를 기록하고, 수락 ID는 받는 즉시 저장한다. 응답이 유실되면 `SUBMISSION_UNKNOWN`으로 멈추고, 공급자 조회나 사용자 판단이 있기 전에는 새 POST를 보내지 않는다. CLI/SDK 내부의 자동 재시도 여부를 확인할 수 없으면 그 구동기는 쓰지 않는다. 공급자 쪽 실패·취소도 새 생성 허가로 보지 않는다 (ai-3d-assets 유료 작업 절, S2-13)
- 연달아 제출한 두 작업의 비용이 섞여, 기록은 160이었지만 실제 사용량은 120이었다 → 자산별 잔액 차이로 비용을 계산했다 → 동시에 진행한 유료 작업은 작업별 공급자 보고값이나 전체 잔액 차이로 정산한다. Studio 잔액과 API 잔액은 별개다 (S2-3)
- 다른 에이전트의 콘셉트 이미지가 끝나기 전에 요청을 고정했는데, 그 뒤 이미지가 1024로 줄어 지문이 바뀌었다(구동기가 `FROZEN_INPUT_CHANGED`로 제출 전에 막음) → 작업이 끝났는지 확인하지 않고 산출물을 입력으로 썼다 → 다른 에이전트의 산출물은 지문이 들어 있는 완료 보고를 받은 뒤에만 입력으로 고정한다 (S2-1)
- 뼈대 요청이 HTTP 400(api 2006)으로 거절됐다 → 원본 생성 작업 ID 대신 확인(check) 작업 ID를 넘겼다("앞 단계 ID를 넘긴다"로 잘못 일반화) → 유료 단계를 연결할 때는 지난 성공 기록의 실제 입력값(`original_model_id`)을 기준으로 맞춘다. 거절이 확실할 때(4xx, 작업 ID 없음, 잔액 변화 없음)만 다시 요청한다 (S3-1)
- 새로 클론한 저장소에는 Tripo CLI 0.8.1과 그 상태 파일이 없었다 → git에서 제외된 폴더에 설치했다 → 설치 절차를 문서로 남긴다. `TRIPO_HOME`은 프로젝트 안의 git 제외 폴더로 두고, `TRIPO_ANALYTICS_ENABLED=0`·`TRIPO_NO_UPDATE_CHECK=1`로 설정한다. API 키는 `.env.local`에서 읽고 출력하거나 기록하지 않는다 (환경)
- Codex 이미지 생성 결과가 `~/.codex/generated_images/<스레드>/`에 저장됐다 → 프로젝트 밖의 기본 위치를 쓴다 → 결과를 결과 폴더로 복사하라고 지시하고, 경로와 해시를 보고받는다 (환경)
- 참고 비용(원본 당시 Tripo 크레딧이며 현재 가격은 다시 확인해야 한다): 몬스터 1종 생성 40, 영웅 생성·뼈대·동작 85, 동작 프리셋 2종 20 (046 후속, 045 3단계, 047)

### 모델 방향·뼈대·동작
- 몬스터 모델이 여러 장면에서 옆으로 걸었는데 아무도 몰랐다(눈이 작아서 눈에 띄지 않았다). 새 몬스터 4종도 같은 방향으로 나왔다. 영웅 모델은 정면이 Blender 기준 +X였다 → Tripo 출력의 정면 방향이 일정하지 않은데, 확인하지 않고 회전 보정 0으로 등록했다 → 새 모델마다 정면 카메라로 줄 세우기 캡처를 찍어 방향을 확인하고, 회전 보정값을 파일로 남긴다(이 경우 5종 모두 90°) (046-15, S3-2)
- 모델 오브젝트를 바인드 포즈 기준으로 ±90° 돌려 넣었더니, Play에서 몸이 이동 방향과 68° 어긋났다(편집 모드에서는 정상처럼 보였다) → 휴머노이드 재생 규칙을 확인하지 않았다 → 휴머노이드 모델은 오브젝트를 돌리지 않는다. Play 판정에 "이동 방향 = 몸 방향(±35°)" 항목을 넣는다 (S3-21)
- 다중 시점으로 생성한 모델에 Tripo 자동 뼈대가 메시와 180° 반대로 붙었다(단일 이미지로 만든 모델은 정상) → 뼈로 잰 정면과 메시의 얼굴 쪽을 대조하지 않았다 → 뼈대를 받으면 뼈로 잰 정면 쪽에 실제 눈 텍셀이 있는지 광선으로 확인한다(무료 검사). 원본에서는 메시를 앞뒤로 거울 반전해 맞췄다 (S3-14)
- 정면 이미지 1장으로 만든 영웅의 뒷머리에도 눈이 그려졌다 → 단일 이미지 생성은 뒷면을 추정해서 만든다 → 캐릭터는 다중 시점(정면·옆·뒤)으로 생성하고, 결과는 게임 카메라 각도에서 정면·뒤·옆 렌더로 검사한다 (S3-5)
- Tripo 동작 프리셋이 공격 1회용으로 쓰기에는 너무 길었다(`slash` 6.6초, `shoot` 9.0초). `shoot`은 1초 뒤부터 웅크린 자세였다 → 프리셋은 연속 시연 동작이라 요청하기 전에는 길이와 자세를 알 수 없다 → 받자마자 1/30초 간격으로 손 속도와 골반 높이를 숫자로 보고, 공격 구간만 잘라 쓴다(`slash`는 1.2–2.3초를 2배속, `shoot`은 0.15–0.95초를 1.6배속) (047-E1)
- 공격 동작 FBX를 가져올 때 애니메이션 경고(Import Messages)가 나왔다 → 조사하지 않았다. Humanoid 리타깃 경고라고 추정만 했다(원인 미확인) → 재생은 표본으로 정상임을 확인했지만 경고는 미해결이다. 새 프로젝트는 가져오기 경고를 목록으로 남기고 원인을 확인한다 (047-E6)

### 텍스처·색·삼각형
- 원본 텍스처 2048(가져오기 설정 512~2048, 압축 지정 없음)이 그대로 쓰였다 → 화면에 보이는 크기를 기준으로 정하지 않고 가져왔다 → 게임 카메라에서 실제 화면 크기를 잰 뒤(1080p 기준 영웅 41px, 몬스터 27px) 텍스처 크기를 정한다(원본은 영웅 256, 몬스터 128, Android·iOS ASTC 4×4, 알파 없음) [모바일][로우폴리: 미드폴리는 화면 크기를 다시 잰다] (050 ⑤)
- 첫 맵 자산 화면이 키아트에서 오히려 멀어졌다(돌이 한 띠로 붙고 꽃이 1~2px로 보였다). 첫 영웅은 얼굴이 작았다 → 설계에 화면상 크기와 간격 목표가 없었다 → 생성하기 전에 게임 카메라 기준 화면 크기(px)·간격·예산을 정한다 (S2-7, 045 E 유형)
- Tripo 원본 삼각형 수가 배치 수만큼 곱해져 예산을 넘었다. 면 한도 500인 돌을 약 150곳에 배치하면서 합계를 계산하지 않았고, 외곽 여러 열에 Tripo 나무(개당 1,368)를 배치했다 → 자산별 예산과 화면 전체 예산을 따로 정했다 → 여러 번 배치하는 자산은 "개당 × 배치 수"로 화면 예산을 먼저 계산한다. 필요하면 전처리에 Blender 로컬 축소를 넣는다(이 경우 602 → 159) [로우폴리 수치] (S2-2, 046-9)
- 지면 얼룩이 카키색으로, 자갈길이 초록빛으로 나왔다 → 팔레트 칸 번호만 보고 골랐는데(칸 4가 카키였다), 재사용한 돌 재질에는 윗면 이끼 투영이 켜져 있었다 → 팔레트 칸과 재질 속성을 먼저 출력해서 보고 고른다 (046-5)
- 캐릭터를 공용 팔레트 셰이더로 바꾼 뒤 한 영웅만 정체성 색 비율이 0.9%로 나왔다(다른 영웅은 약 45%). 한 번은 몬스터의 주황색이 영웅 색 쪽으로 끌려갔다 → 원본 텍스처가 기준색보다 조금 진해서 가까운 다른 칸이 그 색을 가져갔다 → 팔레트화 결과에 정체성 칸 비율과 원본 대비 색 차이를 출력한다. 정체성 색 근처의 텍셀은 정체성 칸으로 고정한다 [로우폴리 팔레트 방식] (050-3)
- 어두운 피부 모델에서 색 판정이 피부와 눈까지 머리카락으로 셌다 → 고정 임계값(0.25)을 모델마다 다른 색에 똑같이 적용했다 → 색 판정 기준은 그 모델에서 뽑은 기준색 중 가장 가까운 것으로 정한다 (S3-16)
- 부분 텍스처 수정이 보호 영역 밖의 텍셀까지 바꿨다(공유 텍셀 377개, 좁은 삼각형이 걸친 텍셀 58개) → 바꿀 곳만 정의했고 "경계 포함"을 근사로 구현했다 → "허용 영역 밖 전부"를 보호 영역으로 정의하고 정확한 판정(분리축)으로 구현한다. 저장된 결과를 다시 읽어 영역 밖 변경이 0인지 확인한다 (S3-9, S3-12)
- 기존 모델을 재사용해 프리팹을 만들었더니 FBX 기본 재질(회색)이 그대로 남았다 → 원래 조립 도구가 따로 연결해 주던 것을 확인하지 않았다 → 재사용할 때는 원래 도구가 연결하던 재질·회전·배율을 목록으로 확인한다 (S1-7)

## 4. 성능 측정

- 측정 전 확인: 2절의 `runInBackground`가 켜져 있는지(046-3), 게임을 그리는 창이 하나뿐인지(046-13) 먼저 본다.
- 한 프레임 통계로 잰 set-pass가 41에서 269까지 흔들려 인스턴싱이 좋아 보였다 → `UnityStats`는 마지막 한 프레임 값만 준다 → 성능 수치는 20초 동안 1초마다 읽은 값의 중앙값으로 잰다. 이렇게 다시 재자 인스턴싱 판정이 "손해"로 뒤집혔다 (049-2)
- 그리기 호출이 PC 설정에서는 401, 모바일 설정에서는 167이었다 → 그림자 캐스케이드 4개 같은 PC 렌더 설정이 값을 부풀렸다 → 측정할 때는 목표 플랫폼의 렌더 파이프라인 에셋으로 바꿔서 잰다 [모바일] (049 결과 1)
- 인스턴싱으로 부하 구간의 그리기 호출은 628에서 239로 줄었지만, 렌더 시간은 9.2ms에서 12.1ms로 늘었다 → SRP Batcher가 켜진 URP에서는 그리기 호출 수와 시간이 비례하지 않는다 → 렌더 시간·프레임 시간을 그리기 호출보다 우선 지표로 본다. 인스턴싱은 측정한 뒤에 켤지 정한다(원본은 꺼 둠) (049-3)
- 몬스터의 실제 그림자를 끄고 발밑에 원형 그림자(검정, 불투명도 0.42, 몬스터 높이의 1.15배)를 깔았다. 그러자 7웨이브 렌더 시간은 3.95ms에서 2.49ms로, 부하 구간은 12.9ms에서 9.2ms로 줄었고, 부하 구간의 그림자를 그리는 물체는 259개에서 15개로 줄었다 → 작은 캐릭터가 많을 때 실제 그림자 비용이 컸다 → 원본은 바닥 원형 그림자를 기본값으로 채택했다 [모바일][로우폴리: 캐릭터가 화면에서 27~41px였던 조건이다. 시각 우선 미드폴리는 실제 그림자를 기준으로 두고 목표 기기에서 다시 잰다] (049 결과 2)
- 바닥 원형 그림자를 넣은 뒤 부하 구간 set-pass가 52에서 105로 늘었다. 적 300마리일 때 추정치 75로 예산 60을 넘는다 → 원인 미확인(투명 재질 정렬 때문이라고 추정만 했다) → 투명 재질을 많이 쓰는 대체 효과를 넣을 때는 set-pass도 함께 본다. 원인은 Frame Debugger로 확인한다 (049 후속, 050)
- 같은 도구로 다시 쟀더니 적 수가 163으로 늘어 이전 값과 비교할 수 없었다 → 측정 순서(대기·표본·캡처 후 측정)가 달랐다 → 성능 비교는 정해진 명령 하나(같은 웨이브, 같은 순서, HP 고정)로 잰다 (048-2)
- 같은 조건으로 다시 재도 삼각형 수가 7.2만~7.8만 사이에서 흔들려, 약 1ms 차이가 실제 차이인지 측정 흔들림인지 가릴 수 없었다 → 한 번씩만 비교했다 → 작은 차이는 같은 조건에서 번갈아 여러 번 재거나 Frame Debugger로 본다 (050 성능 메모)
- 설계에 성능 예산(시작 화면 그리기 호출 250, 삼각형 15만)을 넣었지만 측정 단계가 없어서, 예산 초과(355, 약 24.7만)를 늦게 발견했다 → 판정 기준만 정하고 측정 도구는 정하지 않았다 → 판정 기준마다 측정 단계와 담당 도구를 함께 정한다. NOT_RUN 항목은 다음 결정 전에 측정 계획을 잡는다 [수치는 모바일·로우폴리] (S2-14)
- 시작 화면 삼각형이 이전의 2.5배였다 → 외곽 나무를 큰 묶음(240px)으로 합쳐서, 일부만 보여도 묶음 전체를 그렸다. 낮은 돌에도 그림자가 켜져 있었다 → 묶음 메시는 화면보다 작게 나누고(이 경우 120px), 작은 물체의 그림자는 끈다. 이때의 절대값(약 62만 → 29만)은 046-13의 두 번 집계 상태에서 잰 값으로 보이므로 비율만 의미가 있다 (046-9)
- 9,492삼각형짜리 랜드마크라고 보고 새로 만들려던 바위가 실제로는 렌더러가 꺼져 있었다 → 측정 스크립트가 꺼진 렌더러까지 셌다 → 화면 예산을 잴 때는 켜진 렌더러만 센다. 의존성 검사는 꺼진 것도 포함한다 (050-1)
- 효과와 덤불을 크게 추가한 뒤 성능을 다시 재지 않았다 → 마감 항목에 성능 측정이 없었다 → 시각 변경이 큰 단계는 마감 때 성능 한 줄(그리기 호출·set-pass·삼각형·그림자·렌더 시간)을 기본으로 남긴다 (047-H12)
- 모든 수치가 편집기에서 잰 값이고, 실기기 측정은 끝까지 NOT_RUN이었다. 목표 기기도 정하지 않았다 → 사용자 담당으로 미뤘다 → 새 프로젝트는 목표 기기를 먼저 정하고, 편집기에서 잰 값은 비교용으로만 쓴다 (046 검증, 049·050 후속)
- 원본 예산 참고값: 시작 화면 그리기 호출 250·삼각형 15만, 적 1마리 삼각형 1,000(실측 약 350), set-pass 60 [모바일][로우폴리: 미드폴리에서는 새로 정한다] (045, 049)

## 5. 하네스·검사 설계

### 실제로 결함을 잡은 것
- 독립 검토. 045에서는 비교를 하지 않는 검사, 가짜 PASS, 중심점만 보는 검사를 여럿 찾았다. 048에서는 검토 2회로 실제 결함 6건(hook 회귀, 사용자 작업을 덮어쓰는 복원)을 찾았다. 다만 횟수 제한 없이 돌리면 끝이 나지 않았다 (045 A 유형, 048 검증, 회고1102-H3)
- 반례로 먼저 시험해 둔 판정 함수가 실제 결함을 잡았다. 출전 직후 이동 입력이 먹지 않는 결함이었고, 그 원인은 미확인이다 (S3-20)
- 유료 구동기의 입력 지문 검사가 제출 전에 막았다. 오프라인 반례 시험도 크레딧 손실 0으로 구멍을 찾았다 (S2-1, S2-13)
- Unity에 쓴 직후 실행한 `git status`가 부작용 파일 변경을 잡았다 (S1-1, S1-3, S1-10)
- `script run`의 실행 전 컴파일과 편집기 진단이 오류와 폐기 API를 잡았다 (047-E2, 047-E8)

### 잡지 못한 것
- 사용자 눈에 띈 결함은 검사가 아니라 사람 눈이나 독립 시각 판정이 찾았다: 캐릭터 방향이 68° 어긋남, 넓은 화면 UI의 빈 곳, 몬스터가 옆으로 걷기 (회고1102-H4, S3-21, S1-20, 046-15)
- 커밋 전 gate(pre-commit)는 한 단계 동안 커밋이 없어 한 번도 작동하지 않았다 (회고1102-H5)
- 승인 문구가 가려진 문제는 두 단계 동안 어떤 검사도 잡지 못했다. 기록을 다시 읽는 시험이 없었다 (048-1)
- 짧은 Play의 항목별로 실제 결함을 잡았는지 기록이 없어, 어떤 검사를 빼도 되는지 판단할 수 없었다 (048 "뺄 수 있는 검사")

### 규칙
- 실제로 증명하지 않은 것을 PASS로 판정한 경우가 16건이었다. 상태 비교가 루트 객체 번호만 기록하고 끝났고, 출전 명단을 강제하지 않아 3명을 빼도 PASS가 나왔고, 수집한 메시 이름을 판정에 쓰지 않았다 → 검사 도구가 위반을 실제로 잡는지 확인하지 않았다 → 판정 함수는 일부러 만든 위반(반례)과 망가뜨린 입력(음성 대조)으로 먼저 시험한다. 기대하는 대상 집합을 강제하고, 수집한 증거는 판정에 쓰거나 "참고"로 표시한다 (S1-19, S3-17, S3-10, S3-18)
- 정상적으로 달리는 캐릭터를 FAIL로 판정했다. 손 뼈 표본 2개가 51~115° 범위로 흔들렸고, 표본 6개가 달리기 주기의 같은 위상에 겹쳐 평균을 내도 소용이 없었다 → 주기적으로 흔들리는 뼈를 몸 방향의 대리값으로 썼다 → 방향은 골반·루트처럼 주기와 무관한 기준으로 잰다. 위상이 겹치는 경우를 반례로 먼저 시험한다 (S3-22, S3-24)
- 공용 표본 함수에 재시도를 넣었더니, 전체 실행에서 표본을 뽑는 도중에 웨이브가 끝나 2회 연속 중단됐다(각 약 100초 손실) → 수정 후 짧은 단계로만 확인했다 → 공용 판정·조작 함수를 고치면 모든 호출 위치와 그 시점의 남은 시간·상태를 확인한다 (S3-23)
- 짧은 Play가 한 번 `NOT_IN_BATTLE`로 FAIL했다가 다시 돌리자 PASS가 나왔다. 원인은 UNKNOWN이다. 다른 때에는 오류 메시지를 300자에서 잘라서 원인 값이 보이지 않았다 → 실패 시점의 게임 상태를 남기지 않았다 → 실행기는 실패 시점 상태(`state_at_error`)를 기록하고, 메시지에는 판정에 쓴 값만 남긴다 (048-F2, 048-3, S3-8)
- 0.2~0.5초짜리 효과가 정지 캡처 3장에 하나도 찍히지 않았다 → 캡처 시점이 효과가 나오는 시점과 무관했다 → 순간 효과는 연속 캡처(예: 0.1초 간격 6장)나 상태 숫자(효과 수·종류)로 확인한다 (047-E10)
- 문서를 고치려고 쓴 heredoc 본문에 실행기 이름이 들어 있어 hook이 명령을 막았다. 첫 hook은 `echo`로 이름을 언급만 해도 막는 오탐이 있었다 → hook이 명령 문자열 전체에서 이름을 찾았다 → hook은 실제로 실행되는 위치만 본다. heredoc과 따옴표 안의 문장은 제외하되, `bash -c` 본문·셸로 넘기는 heredoc·명령 치환은 계속 검사한다. hook에 오류가 나면 통과시킨다(fail-open) (047-E0, 회고1102 4절)
- hook 범위를 좁히자 예전에 막던 `bash -lc`, 명령 치환, `bash <<EOF`를 놓쳤다(독립 검토에서 발견) → 시험 사례를 관찰된 한 경우에만 맞췄다 → 검사를 좁힐 때는 예전 검사가 잡던 경우를 시험 사례로 먼저 적는다 (048-4)
- 새 도구를 검증 도구 폴더에 두었더니 기존 Unity 증거가 모두 무효가 됐다 → gate가 그 폴더의 모든 .py를 증거 수집기 의존성으로 셌다(문서에 적힌 범위와 달랐다) → 하네스 도구와 검증 수집기는 폴더를 나눈다. 증거 의존성 범위는 문서와 코드에서 같게 맞춘다 (회고1102 5절)
- 정리 단계가 검증 전부터 있던 저장 안 된 변경까지 지울 수 있었다. 같은 초에 실행된 두 복원이 백업 경로를 공유해 첫 사본을 덮어쓰기도 했다 → 정리 범위를 "무관한 전부"로 넓게 잡았다 → 시작 상태를 기록하고 검증이 만든 변화만 되돌린다. 덮어쓰기 전에 고유 경로로 백업하고 기존 백업은 덮어쓰지 않는다. 실행 중에 HEAD나 index가 바뀌면 손대지 않는다 (S1-15, 048 검토 r001·r002)
- 2단계 Play 검증이 도는 중에 3단계용 도구 파일을 고쳐서 실행 전체가 `protected_changed`로 FAIL했다 → 병렬 작업이 지문 대상 파일을 같이 썼다 → 병렬로 작업할 때는 실행 중인 검증의 지문 대상 파일을 검증이 끝날 때까지 고치지 않는다 (S2-9)
- 측정용 임시 스크립트 5종(로비→출전→웨이브 넘기기→HP 고정→캡처·지표 수집→정리)을 매번 새로 작성했다 → 공용 도구가 없었다 → Play 측정 도구 하나(장면·팀·웨이브·HP 고정·캡처 수·간격·성능 지정)를 둔다. 편집기가 이미 Play 중이면 시작하지 않는다(사용자가 플레이 중일 수 있다) (047-H5)
- 효과 종류를 게임 데이터의 색으로 구분했기 때문에, 게임 코드에서 색을 바꾸면 효과가 아무 경고 없이 기본 불꽃으로 바뀌었다 → 종류를 나타내는 필드가 없었다 → 표시 종류는 명시적인 필드로 넘긴다. 그럴 수 없으면 색과 효과의 대응표를 정적 검사로 확인한다 (047-H11)
- 패치 일부가 적용되지 않은 채 경계 시험을 돌려 실제로 작업 폴더 바깥 경로에 파일을 썼다 → 여러 파일 패치 중 일부가 실패했는데도 다음 단계로 넘어갔다 → 패치가 실패하면 다음 단계를 멈춘다. 경계 시험은 고친 코드가 적용됐는지 확인한 뒤에 돌린다 (S1-18)
- 판정에 쓰는 수치(사격형 몬스터의 정지 거리)를 코드 확인 없이 260으로 잡았다(실제는 163.8~231.84). 정체 판정 기준은 밀집 상황에서 의미가 없었다 → 어림값을 썼고 극단 상황을 검토하지 않았다 → 판정에 쓰는 게임 수치는 코드 위치를 인용해서 가져온다. 기준은 밀집·정지·0마리 같은 극단 상황에서도 의미가 맞는지 보고 정한다 (S1-16, S1-5)
- 측정 대상이 실제로 쓰는 객체와 달라서 숙임 각도를 4.9°로 잘못 쟀다(저장된 프리팹으로 재면 34.3°) → 저장 전의 메모리 복제본으로 쟀다 → 측정은 실제로 쓰는 객체로 한다. 다른 방법으로 잰 값과 크게 다르면 멈춘다 (S3-15)
- 시간·토큰 집계 도구가 새 세션을 옛 단계 이름으로 나눴고, 다른 세션의 Codex 31회 기록까지 섞어 셌다 → 단계 구간과 집계 폴더가 고정돼 있었다 → 시간·토큰은 사용자 요청 단위로 자동으로 나누고, 외부 에이전트 로그는 해당 세션 시간 안의 것만 센다 (047-E7, 047-H9)

## 6. 장면 빌더·참조

- 몬스터 빌더를 다시 돌린 뒤 맵 장면의 액터 세트 참조가 비어(`{fileID: 0}`) 캐릭터가 2D 스프라이트로 나왔다 → 빌더가 이전 세트를 지우고 새로 만들어 지정했지만 저장된 장면에는 반영되지 않았다(정확히 어떤 순서 때문인지는 원인 미확인) → 빌더는 저장한 뒤 장면을 다시 열어 핵심 참조를 확인하고, 참조가 비어 있으면 실패로 멈춘다 (046-12)
- 맵 빌더를 다시 돌리면 다른 빌더가 붙인 몬스터 세트·효과·밤 설정이 사라질 상황이었다(사고 전에 발견). 새 에셋 처리 경로도 장면을 직접 고치려다 같은 위험에 빠졌다 → 장면 전체를 소유하는 빌더가 매번 원본 장면을 새로 복사하는데, 다른 빌더도 같은 장면을 고쳤다 → 장면마다 소유 빌더를 하나 정한다. 다른 단계의 변경은 그 빌더를 통해 넣거나(다시 붙이기 포함), 전체 빌드 진입점 하나로 묶는다 (047-E3, 047-H3, 050-2)
- 맵을 다시 빌드한 뒤 장면 GUID가 바뀌어 빌드 설정의 첫 장면 참조가 어긋났다 → 빌더가 장면을 지우고 다시 복사했다(새 에셋이면 새 GUID) → 다시 만드는 빌더는 에셋을 지우지 말고 내용만 덮어써서 GUID를 유지하고, GUID가 바뀌면 중단한다. 빌드 설정의 장면 GUID와 `.meta` GUID가 일치하는지 정적 검사로 확인한다 (047-E11, 047-H13)
- 몬스터·효과 빌더도 자기 자산 폴더를 지우고 다시 만들어서 재질·프리팹 GUID가 바뀌었다(같은 빌더가 참조를 다시 연결하므로 아직 결함은 아니었다) → 같은 원인이다 → 새 프로젝트의 빌더는 처음부터 "삭제 후 재생성"이 아니라 "덮어쓰기" 방식으로 만든다 (048 후속)
- 빌드 장면이 시험 폴더에 있는 에셋 19개에 의존하고 있었다 → 시험 결과물을 정식 위치로 옮기지 않고 그대로 썼다 → GUID가 유지되는 방식으로 옮기고, 이동 뒤 GUID가 같은지와 전체 참조를 다시 대조한다(원본: 파일 532개, 참조 15,111개 중 끊긴 것 0). 빌드 첫 장면이 의존하는 파일 중 시험 폴더 파일이 0개인지를 검사로 둔다 (050 ④)
- 배치 생성 도구와 빌드 도구의 폴더 소유가 충돌했다. 배치 생성기는 출력 위치를 강제하지 않아서 기존 파일 덮어쓰기나 심볼릭 링크를 통한 바깥 쓰기가 가능했다 → 산출물 소유를 정하지 않았고, 쓰기 경계를 코드로 강제하지 않았다 → 도구가 둘 이상이면 누가 어느 폴더를 만들고 소유하는지 설계에 적는다. 쓰기 경계(기존 파일·심볼릭 링크 거부)는 도구 코드에서 검사한다 (S0-7, S1-13)
- 지면 높이 흔들림(0.022m)이 흙·길 높이(0.011m)보다 커서 흙 무늬에 구멍이 보이고 길 위로 지면이 튀어나왔다 → 겹치는 평면의 높이 순서를 정하지 않았다 → 겹치는 평면은 높이 순서를 표로 정한다(원본: 지면 0~0.004, 흙 0.016~0.017, 길 0.018~0.019) (046-4)
- 꽃·풀이 어두운 갈색 점처럼 보였다. 메시 축소 뒤 떨어진 꼭짓점 정리도 빠졌다 → 기존 생성 코드를 옮기면서 메시 후처리(양면으로 그리는 작은 면에 위쪽 법선 적용)와 처리 순서를 빠뜨렸다 → 코드를 옮길 때는 후처리(법선·색), 주석, 순서 조건까지 함께 옮긴다 [로우폴리: 양면 작은 면] (046-6, S2-5)
- 큰 호수가 중심으로 모이는 가는 삼각형들로 보였다 → 작은 연못용 중심 부채꼴 분할을 큰 면에 그대로 썼다 → 큰 면은 동심 고리로 나누고, 안쪽으로 갈수록 꼭짓점 수를 줄인다 [로우폴리: 면 단위 물] (046-7)
- 키 큰 물체를 중심점만 보고 검사해서 메시 일부가 연못 밖으로 나갔다. 고친 뒤에도 기준 평면을 가로지르는 면의 교점을 빠뜨렸다 → 한 종류의 물체에만 메시 검사를 했고, 꼭짓점만으로 판정했다 → 배치 규칙은 적용 대상인 모든 물체에 같은 검사 함수로 적용한다. 높이·평면 기준은 꼭짓점뿐 아니라 면과 평면의 교점까지 본다 (S2-11)
- 맵 전체 빌드를 다시 돌린 뒤에는 에셋 규격 대조 결과가 더 이상 맞지 않았다 → 빌드가 대조 대상 장면을 새로 만들었다 → 소유 빌더를 다시 돌린 뒤에는 규격·참조 검사를 다시 실행한다 (050 후속)

## 7. 미드폴리로 옮길 때 다시 정할 것

- 숫자 예산(삼각형·그리기 호출·set-pass·텍스처 크기)은 모두 로우폴리·모바일 조건에서, 캐릭터가 화면에 27~41px로 작게 보일 때 정한 값이다. 새 화풍·카메라·목표 기기에서 화면 크기(px)부터 다시 잰다.
- 바닥 원형 그림자, 32색 팔레트 셰이더, Blender로 크게 줄이기, 양면 작은 면의 위쪽 법선은 로우폴리용 해법이다. 시각 우선이라면 실제 그림자·노멀맵·더 큰 텍스처가 기본이 될 수 있다. 그때의 성능은 4절 방법(목표 플랫폼 설정, 20초 중앙값, 시간 지표 우선)으로 다시 잰다.
- 인스턴싱이 손해였다는 결과는 SRP Batcher가 켜진 원본 장면과 재질 구성에서 나온 것이다. 미드폴리 재질 구성에서는 다시 측정한다.
- 화풍과 상관없이 그대로 가져올 것: 1절 작업 방식, 2절 편집기·CLI 함정, 3절의 유료 생성 안전과 방향·뼈대 검사, 5절 하네스 원칙, 6절 빌더 규칙.
